## 一、上传并执行增量 SQL（`sql/migration_*.sql`）

### 1.1 先划红线：生产只跑增量，永不跑全量

| 脚本 | 能不能在生产跑 | 为什么 |
|---|---|---|
| `sql/migration_*.sql` | ✅ 能 | 幂等设计（`CREATE TABLE IF NOT EXISTS` / `INSERT IGNORE` / `information_schema` 守卫的 `ALTER`），可反复重跑 |
| `sql/im_schema.sql` | ❌ **绝不** | 开头有 **48 条行首 `DROP TABLE`**，跑一次＝把所有表连用户、聊天、钱包、直播记录一起删光重建。`import-sql.sh` 见 `DROP TABLE` 会 `exit 3` 主动拒收，这道闸不是摆设 |
| `sql/im_data.sql` | ❌ 不要 | 清理段已按种子 ID 段加谓词（`DELETE ... WHERE id < 10000`，运行期雪花 ID 不受害），但它是给**空库**灌演示数据的；在已有库上跑只会把 admin 种子行重写一遍，顺便覆盖掉你改过的文案 |

> 全量两份只用于「空数据卷首次建库」那条路（`sql-init/01_schema.sql` + `02_data.sql`，镜像自己执行）。

### 1.2 动手前先对账：到底缺哪几批

漏跑比错跑更难查——表现是「一部分屏正常、个别屏 1003 或 500」。对照 `md/SQL变更文档.md` 的台账，用一条只读 SQL 看库走到哪儿了：

```bash
docker compose exec mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N im_db -e "SELECT COUNT(*), MAX(id) FROM im_permission; SHOW TABLES LIKE \"im_feedback\"; SHOW TABLES LIKE \"im_schema_migration%\";"'
```

- `MAX(id)=126` → 缺 1.0.2（反馈）及以后；`=127` → 缺 1.0.5（SQL 版本管理，权限点 128）
- 缺哪张表就去找台账里对应那一批的 `★增加` 栏。**别凭印象补跑**：见过只跑 1.0.2/1.0.4 而漏 1.0.3/1.0.5 的库，跳着漏最难猜。

### 1.3 上传脚本（开发机 PowerShell 执行，不是在服务器上）

```powershell
scp -i "D:\文件\密钥\阿里云服务器登录私钥\_GitHub.pem" `
  sql\migration_feedback.sql `
  root@120.78.126.132:/opt/im-docker/scripts/
```

- 目标目录写 `scripts/`：`import-sql.sh` 的用法示例就是这个相对位置，后面执行不用再找路径。
- ★ 这台服务器 `root` **只允许密钥登录**（`PasswordAuthentication no`），不带 `-i` 必是 `Permission denied (publickey)`。
- 别用 `scp -r sql/`：整目录推上去会把 48 条 `DROP TABLE` 的全量脚本也送到眼前，手滑代价极大。

### 1.4 备份（改动面小的话只备相关表，别整库）

```bash
cd /opt/im-docker
docker compose exec mysql sh -c 'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --default-character-set=utf8mb4 im_db im_permission im_role_permission > /tmp/rbac_bak.sql'
docker compose cp mysql:/tmp/rbac_bak.sql ./backup/
```

只动 RBAC 种子就备这两张表（秒级）；带 `CREATE TABLE` 的新表本身不用备（回滚就是删表），但**带 `ALTER ADD COLUMN` 的批次**建议把那张表一起备了。

### 1.5 执行

```bash
cd /opt/im-docker
bash scripts/import-sql.sh scripts/migration_feedback.sql
```

看到 `== 完成。涉及权限点的话记得：bash scripts/clear-perm-cache.sh` 才算跑完（中间那行 `Warning: Using a password on the command line` 是无害噪音，全程都有）。

★ **只能用这个脚本，不要图省事写管道**：

```bash
cat x.sql | docker compose exec -T mysql mysql ... im_db     # ← 禁止
docker compose exec mysql sh -c 'mysql ... < /tmp/x.sql'     # ← 禁止（还得先自己 cp 进去，等于重造 import-sql.sh）
```

`import-sql.sh` 的做法是 `docker compose cp` 把文件**原样字节**拷进容器，再 `mysql --default-character-set=utf8mb4 -e "source /tmp/im-import-<ts>.sql"`。管道那条路的字节流会被按容器 `LANG` 重编码，**中文和 emoji 静默变成 `?`**：不报错、行数还对得上，等发现时脏数据已经上线。

### 1.6 只读验证（跑完立刻做，别急着测功能）

按该批台账条目里的「验证 SQL」原样跑。通用的三条（★ `im_role_permission.permission_id` 存的是 `im_permission.id` 那套 101~128，不是行号）：

```bash
docker compose exec mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" im_db -e "SELECT id,perm_code,deleted FROM im_permission WHERE id>=126; SELECT COUNT(*) AS admin_binds FROM im_role_permission WHERE role_id=1; SHOW TABLES LIKE \"im_feedback\";"'
```

- 对照值：权限点 126/127/128 三行都在、`deleted=0`；`admin_binds`＝ **28**（admin 绑定行 6001~6028）
- 新列有没有加上：`SHOW COLUMNS FROM im_live_video LIKE "category";`
- 中文有没有坏：`SELECT id, HEX(LEFT(name,1)) FROM <含中文的表> LIMIT 1;` —— 正常应是 `E6xxxx` 这类三字节开头；出现 `C3A6...` 就是双重编码，别继续跑下一批，先回头修。

### 1.7 动了权限点，必须清鉴权缓存（否则看着像没生效）

```bash
bash scripts/clear-perm-cache.sh          # 清全部 im:auth:*（连其他后台账号一起）
bash scripts/clear-perm-cache.sh 1000     # 只清 admin 一个人
```

脚本自带「先数 → 同一条 DEL 批量删 → 再数确认 0」三步，正常输出是 `匹配 im:auth:* 的键：4 个` → `清理后剩余：0 个`。

- 为什么绕不过去：[PermissionProviderImpl](file:///d:/daima/Lianshi/spring-boot-duomokuia/im-user/src/main/java/com/im/user/spi/PermissionProviderImpl.java) 的 `im:auth:perm:{userId}` TTL **30 分钟**，且**「登录」这个动作不刷新它**（`logout` 只做 `StpUtil.logout()`，不碰这两个键）。所以**退出重登一定没用**，「等半小时自己就好了」则会把人误导成「代码没生效」。
- ★ 禁 `FLUSHDB` / `FLUSHALL`：这台 Redis 里不止缓存——`im:conv:seq:*` 是会话发号器（清掉会重新从 1 发号、与历史消息撞号），`im:wallet:packet:*` 是红包状态，`im:quick:reply:*` 是常用语的**唯一存储**（库里没有副本）。
- 前端 `im-admin-ui` 自己还缓存一份菜单（`/auth/me` 的响应），所以清完后门的是**刷新页面 `Ctrl+F5`**，不是重启服务。

### 1.8 需要重启容器吗——不需要

| 对象 | 要不要动 | 理由 |
|---|---|---|
| `im-mysql` | ❌ 不用 | `source` 直接写进数据卷，语句执行完就生效 |
| `im-server` | ❌ 不用 | 权限判定只有「Redis 未命中 → 回源查库」两级，**没有 JVM 内缓存**；新表按名查询，也不存在启动期快照 |
| `im-nginx` | ❌ 不用 | 与数据库无关 |

真需要 `docker compose restart im-server` 的只有：① 换了 jar / 镜像 tag（注意 `up -d` 在 tag 没变时不会重建容器）；② 改了 `app/extra/application-prod-extra.yml` 或 `conf/im.env`（`restart` 才重读挂载文件；若改的是 `.env` 本身则 `up -d --force-recreate`）。

> 别把「重启过所以好了」当成结论。真实案例：补完权限点 128 + 清缓存后功能即恢复，而 `im-server` 全程 `Up 2 hours` 压根没重启过——**时间上挨着不等于因果**，误判的代价是下次故障时去重启一个不相关的容器。

### 1.9 症状 → 缺的是什么（对照速查）

| 现象 | 根因 | 处置 |
|---|---|---|
| 后台某屏 `code=1003`（HTTP 仍 200），菜单也少一项 | 该屏的权限点没落库 | 跑对应批次 + 1.7 清缓存 |
| 后台某屏 500，日志 `Table 'im_db.im_xxx' doesn't exist` | 建表的那批没跑 | 补跑该批；★ 顺序上先 SQL 再上依赖它的新后端 |
| 日志 `Unknown column 'category' in 'field list'` | `ALTER ADD COLUMN` 的批次漏了 | 补跑；实体已有该字段，MyBatis-Plus 一定把它列进 SELECT，**不是可选功能而是硬故障** |
| 接口回 `code=1004`「请求的资源不存在」 | 后端没这个路由（跑的是旧代码） | 这才轮到重启/换镜像，与权限无关 |
| SQL 明明跑了、菜单还是旧的 | 没清 `im:auth:*` | 回到 1.7 |

### 1.10 1.0.6 之后走后台，不再手工 source

`sql/migration_schema_version.sql`（权限点 128）跑完后，后台「SQL 版本」页接管后续变更：`sql/versions/` 下 `V<ver>__<name>.sql` / `U<ver>__<name>.sql` 成对提交，页面点**应用**，一键回滚按 LIFO 只回最近一个 `APPLIED` 版本，流水自动进 `im_schema_migration_log`。

要在生产真用它，还差两步（本手册其它章节没写，记在这里）：

1. 把 `sql/versions/` 拷进容器或加一条 bind mount（jar **不自带**这个目录）；
2. 在 `app/extra/application-prod-extra.yml` 里把 `im.admin.schema-dir` 指到容器内绝对路径 —— 这一步属于 1.8 里的 ②，**需要 `restart im-server`**。

否则的表现是：页面能打开、台账能看，但「应用 / 回滚」两个按钮直接拒绝执行。

> ★ 回滚只还原**结构**，V 脚本里 `DROP` / `DELETE` 掉的数据仍只能靠 1.4 的备份找回。
