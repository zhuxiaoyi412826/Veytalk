# 监控告警部署指南（三期：Actuator + Prometheus/Grafana + 慢接口告警）

本文覆盖管理后台三期交付的监控基础设施：**指标暴露、健康检查、慢接口告警**的部署与接法。
所有结论基于本仓库当前代码（Spring Boot 4.0.8 + micrometer 1.17.1），命令均为 PowerShell 写法。

---

## 一、整体数据流（先认清有几本账）

```
                         ┌──────────────────────────────────────────┐
                         │              im-server（单 jar）          │
  浏览器里的监控页 ───────►  /api/admin/monitor/overview（Sa-Token 鉴权）│
                         │        │                                 │
                         │        ▼                                 │
                         │   MeterRegistry（进程内唯一一本账）        │
                         │        ▲                                 │
  Prometheus 抓取 ───────►  /actuator/prometheus（8081，只绑 127.0.0.1）│
                         │                                 │        │
                         │   SlowRequestInterceptor ───────┤ 三通道   │
                         │     ① WARN 日志 → SLOW-API 档    │        │
                         │     ② 内存环形缓冲 → 监控页明细    │        │
                         │     ③ counter im.slow.request.total      │
                         └──────────────────────────────────────────┘
                                        │
                              Prometheus → Grafana / alertmanager
```

关键口径：**后台监控页与 Prometheus 读的是同一个 MeterRegistry，不存在双账本**——
不会出现「页面说健康、Prometheus 说宕了」。但两条通道受众不同：

| 通道 | 消费者 | 保护方式 |
|---|---|---|
| `/api/admin/monitor/**` | 人（浏览器） | Sa-Token 登录 + `system:monitor` 权限点（114） |
| `/api/admin/log/**` | 人（浏览器） | Sa-Token 登录 + `system:log` 权限点（115），单独设点因日志含敏感内容 |
| `/actuator/prometheus`、`/actuator/health` | 机器（Prometheus / 存活探针） | 独立端口 + 默认只绑回环，**不走 Sa-Token**（拦截器只拦 `/api/**`） |

## 二、Actuator 端点保护（已按默认口径配好）

`im-bootstrap/src/main/resources/application.yml` 的 `management` 段：

```yaml
management:
  server:
    port: ${MANAGEMENT_PORT:8081}          # 与业务端口 8080 分离
    address: ${MANAGEMENT_ADDRESS:127.0.0.1} # 默认只监听回环：外部根本连不上
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,metrics  # 白名单制，env/beans 等敏感端点不暴露
  endpoint:
    health:
      show-details: never                  # 聚合状态可看，组件明细不给外人
  metrics:
    tags:
      application: ${spring.application.name}  # 公共 tag，多实例区分靠它
```

为什么这么钉：

- **依赖放 im-admin 而不是 im-bootstrap**：actuator 与 prometheus registry 只服务于后台侧能力
  （监控页 + 抓取通道），放进公共装配层等于给所有部署形态都背上这两个依赖。
- **独立端口**：`/actuator/**` 天然不被 Sa-Token 覆盖（拦截器只拦 `/api/**`），若与业务同端口，
  要么把 actuator 挂进鉴权拦截（Prometheus 抓取还得带 token，得不偿失），要么裸奔。
  分端口 + 绑回环后，「谁能访问 8081」这件事收敛为「谁能登录这台机器」。
- **`http.server.requests` 的分位数默认是关的**（micrometer 不留分位数以省内存），
  监控页要的 P50/P95/P99 由 `AdminMonitorService` 构造时用 MeterFilter 显式打开；
  MeterFilter 只对**之后注册的 timer** 生效，所以放在构造函数而不是等首次请求——
  这也是「监控页刚打开那几秒某些 URI 的 P95 是『—』」的原因：那个 uri 模板的 timer 还没被首个请求注册出来。

### 部署时要动的环境变量

| 变量 | 默认 | 什么时候改 |
|---|---|---|
| `MANAGEMENT_PORT` | `8081` | 端口冲突时 |
| `MANAGEMENT_ADDRESS` | `127.0.0.1` | **仅当 Prometheus 与后端不同机**时改成 `0.0.0.0`，且必须同时上防火墙/安全组白名单，只放行 Prometheus 服务器的 IP |

```powershell
# 启动示例（默认口径，什么都不用传）
java -jar im-bootstrap/target/im-server.jar

# Prometheus 在另一台机 10.0.0.9 时的启动示例（改绑卡 + 防火墙只放行那台机）
$env:MANAGEMENT_ADDRESS='0.0.0.0'
java -jar im-bootstrap/target/im-server.jar
New-NetFirewallRule -DisplayName "prom-scrape" -Direction Inbound -Protocol TCP -LocalPort 8081 -RemoteAddress 10.0.0.9 -Action Allow
```

### 自检（后端起来后直接跑）

```powershell
Invoke-RestMethod http://127.0.0.1:8081/actuator/health      # 期望 status: UP
Invoke-WebRequest  http://127.0.0.1:8081/actuator/prometheus | Select-Object -ExpandProperty Content | Select-String 'im_slow_request_total|jvm_memory_used'
Invoke-WebRequest  http://127.0.0.1:8081/actuator/env         # 期望 404（没在暴露白名单里）
```

## 三、Prometheus 接入

### 3.1 抓取配置（prometheus.yml 片段）

```yaml
scrape_configs:
  - job_name: 'im-server'
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ['127.0.0.1:8081']   # 同机部署；改绑卡后写后端机内网 IP
    # 多实例时优先用服务发现；至少给每个 target 打 labels: { instance: 'im-01' }
```

不同机时 Prometheus 容器/进程要能连到后端 8081（见上节的改绑卡与防火墙）；
同机部署则什么都不用改，这是最省事的默认形态。

### 3.2 本仓库埋好的指标

| 指标 | 类型 | 来源 | 用途 |
|---|---|---|---|
| `im_slow_request_total` | counter | 慢接口拦截器（每次超阈值 +1） | 慢接口告警的主指标 |
| `http_server_requests_seconds_count / _sum / max` | timer | actuator 自动装配 | 请求量、平均耗时；开了分位数后有 `_quantity`（P50/P95/P99 快照） |
| `jvm_memory_used_bytes{area="heap"}` 等 | gauge | actuator JVM 指标集 | 堆占用、线程 |
| `hikaricp_connections_active / _pending` | gauge | actuator HikariCP 指标 | 连接池饱和度 |
| `process_uptime_seconds` | gauge | actuator | 重启检测（突然变小=刚重启） |

注意：micrometer 的 counter 是**首次触发才注册**，`im_slow_request_total` 在没有慢请求时查不到序列，
PromQL 里要用 `sum(im_slow_request_total) or vector(0)` 兜 0（下面规则里已带）。

## 四、告警规则样例（alert.rules.yml）

按「先少而准、再慢慢加」的原则给四条，均为可直接粘贴的 PromQL：

```yaml
groups:
  - name: im-server
    rules:
      # 1. 实例宕了：抓取连续失败（存活探针的机器版，与监控页的健康聚合互为印证）
      - alert: ImServerDown
        expr: up{job="im-server"} == 0
        for: 1m
        labels: { severity: critical }
        annotations:
          summary: "IM 后端实例 {{ $labels.instance }} 抓取失败超过 1 分钟"

      # 2. 慢接口占比：5 分钟内慢请求占比超 5%（绝对量小的时段看占比，防深夜一条慢请求就报警）
      - alert: ImSlowRequestRatio
        expr: |
          rate(im_slow_request_total[5m])
            /
          (sum(rate(http_server_requests_seconds_count[5m])) or vector(0.001)) > 0.05
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "IM 慢接口占比 >5% 持续 5 分钟，去 SLOW-API 日志档或后台监控页看明细"

      # 3. 堆水位：超 90% 持续 5 分钟（OOM 前科最常见的形态；-30s 偏移让抓取延迟不吃亏）
      - alert: ImHeapHigh
        expr: |
          sum(jvm_memory_used_bytes{job="im-server",area="heap"})
            /
          sum(jvm_memory_max_bytes{job="im-server",area="heap",id!=""}) > 0.9
        for: 5m
        labels: { severity: critical }
        annotations:
          summary: "IM JVM 堆占用 >90%，看是否伴随 Full GC 与请求耗时上涨"

      # 4. 连接池排队：有线程在等连接说明池小了或有慢 SQL 占着（与慢 SQL 日志档互为线索）
      - alert: ImDbPoolPending
        expr: sum(hikaricp_connections_pending{job="im-server"}) > 0
        for: 2m
        labels: { severity: warning }
        annotations:
          summary: "IM HikariCP 连续 2 分钟有排队连接，检查慢 SQL（SQL/slow-sql.log）"
```

规则文件挂进 `prometheus.yml`：

```yaml
rule_files:
  - "alert.rules.yml"
```

## 五、Grafana 接入（可选，一页就够）

1. Data Sources → Add → Prometheus → `http://<prometheus-host>:9090`；
2. Dashboards → Import → 输入ID **8563**（"Micrometer via Prometheus"，社区成熟模板，
   对 micrometer 的命名一一对上）→ 选数据源 → Import；
3. 只想看一屏的话不必装 Grafana——后台自带监控页（`/api/admin/monitor/overview`）就是
   同一本账的人读版本；Grafana 的价值在**历史曲线与值班告警**，那是即时快照给不了的。

## 六、慢接口告警的三条消费路径

| 路径 | 在哪看 | 适合谁 |
|---|---|---|
| WARN 日志 | `{LOG_HOME}/SLOW-API/slow-api.log`（默认 `D:/rizi1/IM/SLOW-API/`），logger 名 `com.im.slowapi` | 排障时 grep；也可被 filebeat 类采集器消费 |
| 内存环形缓冲 | 后台「监控告警」页的明细表（`im.admin.slow-request-history` 默认 200 条，**重启清零**） | 值班时快速看一眼 |
| Prometheus counter | `im_slow_request_total` + 上面第 2 条告警规则 | 自动告警、长期趋势 |

阈值调整：环境变量 `IM_ADMIN_SLOW_REQUEST_MILLIS`（默认 1000，单位毫秒）或改
`application.yml` 的 `im.admin.slow-request-millis`。调阈值改的是拦截器判断，
不需要动 Prometheus 规则里的占比逻辑。

## 七、日志管理与本指南的关系

后台「日志管理」页（`system:log` 单独权限点）能尾读七个档：
DEBUG / INFO / WARN / ERROR / 慢SQL / 慢接口 / 图片审核。它只读**当前**档，
没有历史归档检索、不能下载文件——需要全量历史时进服务器拿归档文件 grep，
需要长期曲线时归 Prometheus/Grafana，这是刻意的分工而不是缺功能。

## 八、上线检查清单

- [ ] `127.0.0.1:8081/actuator/health` 回 UP；`/actuator/env` 回 404
- [ ] Prometheus targets 页 `im-server` 全绿
- [ ] 后台监控页四张卡片出数（刚启动时部分 P95 显示「—」是正常的，见第二节分位数说明）
- [ ] 手动制造一次慢请求（把阈值临时调到 1ms 重启，或调一个真慢的接口）验证三条通道同时进数：日志文件有行、监控页明细有行、`im_slow_request_total` 增长
- [ ] 若改过 `MANAGEMENT_ADDRESS=0.0.0.0`：防火墙白名单已只放行 Prometheus 服务器 IP，并从其它机器验证 `Test-NetConnection <后端机> -Port 8081` 不通
