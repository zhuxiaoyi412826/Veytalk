# 更新日志 CHANGELOG

本文件记录 **IM 即时通讯系统** 的所有重要变更（代码、配置、文档均含）。

**约定（务必遵守）**：

- 从现在起，**本项目每一次更新都要在本文件里留一条描述**，无论改动大小。
- 采用 [Keep a Changelog](https://keepachangelog.com/zh-CN/) 风格，版本号遵循 [语义化版本](https://semver.org/lang/zh-CN/)。
- 变更按类型分组：`新增 Added` / `变更 Changed` / `修复 Fixed` / `移除 Removed` / `废弃 Deprecated` / `安全 Security`。
- 每条写清「改了什么、为什么、影响范围」，涉及文件时给出路径。
- **最新的版本放在最上面**；未发布的改动先归到顶部的 `未发布 Unreleased` 区。

  - **慢接口告警三通道**：`SlowRequestInterceptor`（拦 `/api/**`，nanoTime 计时，阈值 `im.admin.slow-request-millis` 默认 1000ms）同一事件三路分发：① WARN 日志走新建 logger `com.im.slowapi` → logback 新增 **SLOW-API 档**（与慢 SQL 同一套规矩：`additivity=false`、不压 .gz、按敏感对待、`neverBlock=false` 故障现场宁阻不丢）；② 内存环形缓冲（`ConcurrentLinkedDeque`，容量 `slow-request-history` 默认 200）供监控页明细；③ Prometheus counter `im.slow.request.total` 供告警规则。`http.server.requests` 的 P95/P99 默认关着，由 `AdminMonitorService` 构造时 MeterFilter 显式打开（filter 只对之后注册的 timer 生效，所以不能等首请求）；监控页与 Prometheus 读同一个 MeterRegistry，不存在双账本。

  - **为什么资金不建新表**（关键取舍）：转账与红包的钱全部落既有 `im_wallet_transaction`，只是 `type` 多三个取值 `transfer`/`packet`/`refund`（`VARCHAR(16)` 容量足够，列定义与索引一字未改）。需要新存储的只有「会变的状态」：谁领了、还剩多少——这些放 Redis Hash `im:wallet:packet:{packetId}`（字段 `meta`/`splits`/`count`/`sum`/`c:{userId}`），领完就没人再读，TTL 自清。**已写明代价**：Redis 是唯一领取态存储，被清后「没领过的人」会重新得一次机会；但**退款金额不依赖 Redis**（见下），所以不会凭空造钱也不会把发送人的钱弄丢。
  - **账本即幂等锁**：过期退款不读 Redis 计数器，而是把同一 `packetId` 下 `type IN ('packet','refund')` 的流水行**求和**：`SUM(amount) < 0` 就是还有人没领，`-SUM(amount)` 即应退额；退完那一组行归零，自动退出下一轮扫描集——所以写入 `refund` 行本身就是幂等，重启/重跑不会退两次。`WalletTransactionMapper.selectExpirablePackets` 一条 GROUP BY 兼作扫描与去重。
  - **退款任务为什么是 5 分钟而不是每秒**：那张账本只有 `idx_user_time(user_id, create_time)`，而查询是按 `type` + `create_time` 筛、**没有索引可走**；频率高了就是周期性的全表扫描，所以 `RedPacketRefundTask` 取 `fixedDelay = 300_000L`，并在类注释里如实写明。`refundExpired` **刻意不加 `@Transactional`**：每笔 credit 自开事务，一笔失败不连累整批；且**不看开关**（在飞红包必须能退，不能因为运维关掉转账就让别人的钱烂在池子里）。
  - **事务与顺序**：`send` / `credit` / `debit` 都是 `@Transactional(REQUIRED)`，所以转账外层一个事务就能保证「扣款 + 入账 + 消息」原子。红包故意把 **Redis 建池放在 `debit` 与 `messageSpi.send` 之后**（本事务最后一步副作用）：反过来会留下「钱未扣、池子在」的无中生有；回滚最多留下一个无人可寻的孤儿 Hash（`packetId` 从未出现在任何消息里），TTL 自清。
  - **领取的两道闸门**：`hSetIfAbsent`（HSETNX）做「一人一份」，`hIncrement`（HINCRBY）的返回值直接当「第几个名额」——`hSet` + `hHasKey` 两步不是原子的，并发下会多发钱。超领则回退 `count` + `hDelete` 该字段再拒（抢不到名额的人不能占位）。**过 `expireAt` 一律拒领**，否则与退款叠加就是凭空造钱；同时检查退款互斥锁 `im:wallet:packet:refund:{packetId}`（`setIfAbsent` 10 分钟）。注释里写清：**退款与领取同秒的竞态只能压低、不假装绝对无**。

  - **结算的两个坑**：① 已结算的会话**不再重算热度**——那几个计数键可能在 TTL 之后被清，届时增量算成 0 会把定格好的胜负改写成平局；② 重复结算幂等，直接返回定格值。结果面板把热度/票数定格进会话，事后回看不依赖会过期的计数器。
  - **前端倒计时做锚点校准**：记住最近一帧到达时刻与它报的剩余秒数（`pkExpireAt`），本地每秒算差值、帧到达时重设锚点——漏帧只是重校准，不会把倒计时带偏；走到 0 就停表**等服务端 `end` 帧**，本地不擅自判平局（否则会「先显示平局再跳出真结果」）。面板挂在画面上沿居中（正好压在分屏中缝上方），主播侧同位置是「提前结束」（只有对阵主播能停，其余 `LIVE_FORBIDDEN`），观众侧是「挺我方 / 挺对方」；结果帧后面板留 15 秒再收起。投票按人头计、**不校验是不是本房观众**（跨房串票的收益远低于每次投票都扫一遍连接表的成本），限流 10 次/分钟。
