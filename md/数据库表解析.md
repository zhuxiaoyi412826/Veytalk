## 一、全局设计约定

所有表共享以下几条贯穿全库的约定，理解它们后单表就只剩业务差异：

| 约定 | 说明 |
|---|---|
| **主键 BIGINT + 雪花算法** | 所有主键为 `BIGINT`，由 MyBatis-Plus 雪花算法（Snowflake）在应用侧生成，**不使用数据库自增**。目的是便于将来分库分表，且 ID 全局趋势递增、可暴露粗略的时间先后。 |
| **逻辑删除 `deleted`** | 只对「需要保留历史的主表」启用（用户、角色、权限、会话、群组、文件、面试会话；消息主表除外）。取值 `0` 未删除 / `1` 已删除。MyBatis-Plus 自动在查询上追加 `deleted=0`。反之，**流水表一律不带 `deleted`**（映射到 `AuditEntity`）：远程审计、面试问答与事件只增不删，**举报工单只改 `status` 不删行**（软删一张工单在合规视角上等于证据消失），关系表则物理删除。 |
| **关系表物理删除** | 好友、群成员、会话成员等**关系表不启用逻辑删除**——因为唯一键若保留已删除行，会导致「删了好友/退了群却无法重新添加」。群成员是例外，用 `status` 软状态保留历史（见下文）。 |
| **时间列 DATETIME** | `create_time` / `update_time` 由 MyBatis-Plus 自动填充，同时数据库给出 `DEFAULT CURRENT_TIMESTAMP` 与 `ON UPDATE CURRENT_TIMESTAMP` 兜底，即使绕过应用直接写库也有正确时间。 |
| **字符集 utf8mb4** | 全库统一 `utf8mb4` / `utf8mb4_general_ci`，完整支持 emoji 与生僻字。 |
| **状态位 TINYINT** | 各类 `status` / 布尔标记统一用 `TINYINT`（0/1/2…），比 `BOOLEAN` 更利于表达多态状态。 |

## 三、实体关系（ER）概览

系统未建物理外键（`FOREIGN_KEY_CHECKS=0` 便于重建脚本），关系靠应用层与索引维护。逻辑关系如下：

```
im_user ──< im_user_role >── im_role ──< im_role_permission >── im_permission
   │
   ├──< im_friend >──（自关联：user_id ↔ friend_id，双向两行）
   ├──< im_friend_request（from_user_id / to_user_id）
   │
   ├──< im_conversation_member >── im_conversation ──< im_message
   │                                      │                  ├──< im_message_read
   │                                      │                  ├──< im_message_delete
   │                                      │                  ├──< im_message_reaction（贴表情：一人一消息一表情一行）
   │                                      │                  ├──< im_message_vote（一人一选项一行）
   │                                      │                  └──< im_message_favorite（user_id 维度，同一消息可被多人各收藏）
   │                                      ├──< im_message_essence（conversation_id 维度，一条消息至多一行）
   │                                      └──（type=2 群聊）── im_group ──< im_group_member
   │
   ├──< im_file（uploader_id）
   │
   ├──< im_remote_device（user_id 为设备归属人；识别码模式固定为 0）
   │        └──（device_id）im_remote_session ──< im_remote_audit_log
   │                └──（inviter_user_id 控制方视角 / invitee_user_id 被控方视角，双向查询同一会话）
   │
   └──< im_interview_session ──┬──< im_interview_message（seq 会话内序号）
                                └──< im_interview_event（violation 决定是否计入会话计数）
```

`im_report` 是唯一一张**逻辑上跨四张目标表**的工单表（它不属于任何业务模块，只归 im-admin）：

```
im_report
   ├─ reporter_id / reported_user_id / handler_id ──> im_user（三个都是用户 ID，同样不建外键）
   └─ (target_type, target_id) ──> 多态指向 im_user / im_message / im_live_room / im_group
         提交那一刻由各目标模块的 ReportTargetSpi 反查责任人并抓证据快照落 evidence（JSON 列），
         之后对象被撤回 / 关播 / 解散都不影响工单继续处理——所以这条关系是「快照」而不是「活引用」。
```

**权限模型**：经典 RBAC——`用户 →(im_user_role)→ 角色 →(im_role_permission)→ 权限点`。一个用户可有多角色，一个角色可有多权限点，多对多通过两张关联表落地。

**会话模型**：`im_conversation` 是「一个聊天窗口」的抽象（单聊/群聊统一），`im_conversation_member` 是「每个用户在该会话里的私有状态」（未读数、置顶、免打扰、本端是否隐藏）。二者一对多。

## 四、用户与权限模块（im-user）

### 4.1 `im_user` — 用户表

系统的账号主体，一行一个用户，承载登录凭证与个人资料。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 用户 ID（雪花） |
| `username` | VARCHAR(32) | 否 | — | 登录账号，全局唯一 |
| `password` | VARCHAR(255) | 否 | — | 密码密文（Argon2id / BCrypt），**永不明文存储** |
| `nickname` | VARCHAR(32) | 否 | — | 昵称 |
| `avatar` | VARCHAR(512) | 是 | NULL | 头像访问地址 |
| `gender` | TINYINT | 否 | 0 | 性别：0 未知 / 1 男 / 2 女 |
| `signature` | VARCHAR(255) | 是 | NULL | 个性签名 |
| `phone` | VARCHAR(20) | 是 | NULL | 手机号，可空但**非空时唯一** |
| `email` | VARCHAR(64) | 是 | NULL | 邮箱 |
| `status` | TINYINT | 否 | 1 | 状态：1 正常 / 0 禁用 |
| `last_login_time` | DATETIME | 是 | NULL | 最近登录时间 |
| `last_login_ip` | VARCHAR(64) | 是 | NULL | 最近登录 IP |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |
| `deleted` | TINYINT | 否 | 0 | 逻辑删除：0 未删除 / 1 已删除 |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `uk_username` | 唯一 | `username` | 保证登录账号全局唯一，登录/注册查重直接命中 |
| `uk_phone` | 唯一 | `phone` | 手机号唯一。MySQL 唯一索引允许多个 NULL，故未填手机号的用户不受约束 |
| `idx_nickname` | 普通 | `nickname` | 支持按昵称模糊搜索用户（加好友场景） |

### 4.2 `im_role` — 角色表

RBAC 的角色定义。种子数据内置四种角色：`admin`（超级管理员）、`user`（普通用户，注册即默认绑定）、`moderator`（后台·举报处置）、`operator`（后台·用户管理与角色分配）。后两者是后台二期（`sql/migration_admin_phase2.sql`）新加的示范角色，用于演示细粒度分级；`admin` 持有全部细粒度点。角色只作分组容器，真正的访问控制落在权限点（`im_permission`）上。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 角色 ID |
| `role_code` | VARCHAR(64) | 否 | — | 角色编码，如 `admin` / `user` |
| `role_name` | VARCHAR(64) | 否 | — | 角色名称 |
| `description` | VARCHAR(255) | 是 | NULL | 角色说明 |
| `status` | TINYINT | 否 | 1 | 状态：1 启用 / 0 停用 |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |
| `deleted` | TINYINT | 否 | 0 | 逻辑删除 |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `uk_role_code` | 唯一 | `role_code` | 角色编码唯一，Sa-Token 按 code 加载角色 |

## 五、好友关系模块（im-friend）

### 5.1 `im_friend` — 好友关系表（双向各一行）

好友关系用**双向冗余两行**表达：A 加 B 为好友，会同时插入 `(A→B)` 与 `(B→A)` 两行。这样每一方都能独立维护自己的备注名、分组、拉黑状态，互不影响。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 主键 |
| `user_id` | BIGINT | 否 | — | 用户 ID（本端视角的「我」） |
| `friend_id` | BIGINT | 否 | — | 好友用户 ID（本端视角的「对方」） |
| `remark` | VARCHAR(32) | 是 | NULL | 我对好友的备注名 |
| `group_name` | VARCHAR(32) | 否 | `默认分组` | 好友分组名 |
| `status` | TINYINT | 否 | 1 | 状态：1 正常 / 2 已拉黑（我拉黑了 friend_id） |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 建立时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `uk_user_friend` | 唯一 | `user_id, friend_id` | 保证同一方向不会重复建立好友关系 |
| `idx_friend` | 普通 | `friend_id` | 反查「谁把我加为好友」 |

> **为何拉黑是单向 `status=2` 而非删行**：拉黑只影响本端（我不接收对方消息），对方视角的关系仍在，故用状态位而非物理删除，避免破坏双向对称性。

### 5.2 `im_friend_request` — 好友申请表

好友申请的全生命周期记录（待处理/已同意/已拒绝/已过期）。**保留全部历史**，不做逻辑删除。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 主键 |
| `from_user_id` | BIGINT | 否 | — | 申请人 ID |
| `to_user_id` | BIGINT | 否 | — | 被申请人 ID |
| `verify_message` | VARCHAR(255) | 是 | NULL | 验证消息（申请附言） |
| `source` | VARCHAR(32) | 是 | NULL | 来源：search / qrcode / group |
| `status` | TINYINT | 否 | 0 | 状态：0 待处理 / 1 已同意 / 2 已拒绝 / 3 已过期 |
| `handle_time` | DATETIME | 是 | NULL | 处理时间 |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 申请时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |
| `pending_flag` | TINYINT **（生成列 VIRTUAL）** | — | 由 `status` 计算 | 待处理标记：`status=0` 时为 1，否则为 NULL |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `uk_from_to_pending` | 唯一 | `from_user_id, to_user_id, pending_flag` | **精妙点**：见下方说明 |
| `idx_to_status` | 普通 | `to_user_id, status, create_time` | 「我收到的申请」列表：按被申请方过滤 + 状态 + 时间排序 |
| `idx_from_status` | 普通 | `from_user_id, status, create_time` | 「我发出的申请」列表：按申请方过滤 + 状态 + 时间排序 |

> **`pending_flag` 生成列 + 唯一索引的巧思**：需求是「同一对用户最多只能有一条**待处理**申请，但要保留所有历史记录」。直接把 `(from_user_id, to_user_id)` 设为唯一键会导致历史记录无法留存。方案是引入虚拟生成列 `pending_flag = IF(status=0, 1, NULL)`：待处理时为 1，处理后为 NULL。**MySQL 唯一索引允许多个 NULL 值**，因此：
> - 待处理时 `(A, B, 1)` 唯一 → 同一对用户第二条待处理申请插入失败；
> - 处理后 `pending_flag` 变 NULL → `(A, B, NULL)` 不触发唯一约束，可无限保留历史。

## 六、会话模块（im-conversation）

| `last_msg_time` | DATETIME | 是 | NULL | 最后一条消息时间，会话列表排序依据 |

| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

| `is_top` | TINYINT | 否 | 0 | 是否置顶：1 是 / 0 否 |
| `top_time` | DATETIME | 是 | NULL | 置顶时间 |
| `is_muted` | TINYINT | 否 | 0 | 是否免打扰：1 是 / 0 否 |
| `is_deleted` | TINYINT | 否 | 0 | 本端是否隐藏该会话：1 隐藏 / 0 显示 |

## 七、消息模块（im-message）

### 7.1 `im_message` — 消息表（兼离线消息持久化队列）

系统数据量最大的表。每条消息一行，`content` 存正文或附件文件 ID，`extra` 存结构化扩展信息（JSON）。它同时充当**离线消息队列**——用户不在线时消息落库，上线后按 seq 补拉。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 消息 ID（雪花） |
| `client_msg_id` | VARCHAR(64) | 否 | — | 客户端消息 ID，与发送者一起构成幂等键 |
| `conversation_id` | BIGINT | 否 | — | 所属会话 ID |
| `from_user_id` | BIGINT | 否 | — | 发送者 ID，**0 表示系统通知** |

| `extra` | JSON | 是 | NULL | 扩展信息：附件元数据、@ 列表等（见[扩展说明](#十二扩展说明)） |
| `seq` | BIGINT | 否 | — | 会话内自增序列，游标分页与未读计算依据 |
| `is_recalled` | TINYINT | 否 | 0 | 是否已撤回：1 是 / 0 否 |
| `recall_time` | DATETIME | 是 | NULL | 撤回时间 |
| `send_time` | DATETIME | 否 | — | 发送时间（服务端落库时间） |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `uk_from_client` | 唯一 | `from_user_id, client_msg_id` | **幂等核心**：同一客户端消息 ID 只落库一次，网络重试重复提交触发唯一键冲突 |
| `idx_conv_seq` | 普通 | `conversation_id, seq` | 历史消息游标分页：`WHERE conversation_id=? AND seq<? ORDER BY seq DESC` |
| `idx_send_time` | 普通 | `send_time` | 按时间范围查询/清理 |

> **撤回是软状态**：消息撤回不删行，而是置 `is_recalled=1` + `recall_time`，前端渲染为「xx 撤回了一条消息」，保留可追溯性。

### 7.2 `im_message_read` — 消息送达/已读回执表

记录每个接收者对每条消息的送达与已读时间，支撑「已读/未读」显示与群消息回执统计。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |

| `delivered_time` | DATETIME | 是 | NULL | 送达时间 |
| `read_time` | DATETIME | 是 | NULL | 已读时间 |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |

### 7.3 `im_message_delete` — 消息单端删除表

| `message_id` | BIGINT | 否 | — | 消息 ID |
| `user_id` | BIGINT | 否 | — | 执行删除的用户 ID |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 删除时间 |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `uk_msg_user` | 唯一 | `message_id, user_id` | 防止同一用户对同一消息重复删除 |
| `idx_user_msg` | 普通 | `user_id, message_id` | 拉取消息列表时按用户过滤已删除项 |

### 7.4 `im_message_reaction` — 消息表情回应表

| `create_time` | DATETIME | 否 | 回应时间 |

索引：`uk_msg_user_emoji(message_id, user_id, emoji)` 保证「一人对一条消息的同一表情只计一次」（再点为取消，物理删行）；`idx_message(message_id)` 供反查一条消息的全部回应。

### 7.5 `im_message_vote` — 消息投票选项记录表

一行 = 「某人把某条投票消息的某个选项投了一票」。多选投票一人就是多行。

| 字段 | 类型 | 允许空 | 含义 |
|---|---|---|---|
| `id` | BIGINT | 否 | 主键 |
| `message_id` | BIGINT | 否 | 投票消息 ID |
| `user_id` | BIGINT | 否 | 投票人 ID |
| `option_index` | INT | 否 | 选项下标（从 0 开始） |
| `create_time` | DATETIME | 否 | 投票时间 |

重新投票是**先清本人这一批行再写新行**（整体替换语义），所以不设改票流水。投票定义（标题/选项/多选/匿名/截止）在 `im_message.extra`，票数只由本表实时聚合，**不往消息行里回写计数列**：否则并发投票要上锁，而聚合只是一条 `GROUP BY`。

### 7.6 `im_message_essence` — 群精华消息表

群主/管理员把有价值的一两条消息沉淀给全群看，是**群维度的公开标记**。

| 字段 | 类型 | 允许空 | 含义 |
|---|---|---|---|
| `id` | BIGINT | 否 | 主键 |
| `conversation_id` | BIGINT | 否 | 所属群会话 ID（聚合维度） |
| `message_id` | BIGINT | 否 | 被标为精华的消息 ID |
| `mark_user_id` | BIGINT | 否 | 标记人（群主/管理员） |
| `create_time` | DATETIME | 否 | 标记时间（面板按此倒序） |

索引：`uk_message(message_id)` 一条消息至多一行（取消即删），`idx_conversation(conversation_id)` 供「本群全部精华」分页。单聊不能设精华（会话类型在服务层校验，表上不做约束）。

### 7.7 `im_message_favorite` — 消息收藏表

与精华长得几乎一样，**差在维度**：精华按 `conversation_id` 聚合、全群可见；收藏按 `user_id` 聚合、只有本人可见。

| 字段 | 类型 | 允许空 | 含义 |
|---|---|---|---|
| `id` | BIGINT | 否 | 主键（雪花） |
| `user_id` | BIGINT | 否 | 收藏人 ID（聚合维度 + 权限边界） |
| `conversation_id` | BIGINT | 否 | 所属会话 ID（冗余列） |
| `message_id` | BIGINT | 否 | 被收藏的消息 ID |
| `create_time` | DATETIME | 否 | 收藏时间（列表按此倒序） |

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `uk_user_message` | 唯一 | `user_id, message_id` | 一人对一条消息只有一行；**同一条消息可以被多人各自收藏**，A 取消不伤 B |
| `idx_user_time` | 普通 | `user_id, create_time` | 「我的收藏」分页主查询：本人按收藏时间倒序，顺带覆盖 `conversation_id` 过滤前的收敛 |

> **`conversation_id` 是故意冗余的**（能从 `im_message` join 得到）：一是「只看本会话的收藏」要按它直接过滤，不能为了过滤去 join 消息大表；二是「清空聊天记录」要按会话批量清掉收藏行，级联删除不 join。
>
> **为什么这三张标记表都建表而不放 Redis**（本项目的默认偏好是零 DDL）：它们记的都是**没有寿命的用户数据**，Redis 里现有的兄弟键（限流、心跳、PK 会话、红包领取态）都有明确 TTL，唯独这些没有——要么永不过期（挤内存，且换实例/flushdb 就静默全丢），要么设 TTL（等于给用户数据判死刑）。另外「按用户/会话倒序分页」与「整页批量判定哪些已标记」两种访问模式都要吃索引，ZSet 撑得住前者、撑不住后者（要 N 次 ZSCORE）。
>
> **消息的两种「删」都不给收藏列表留幽灵行**：用户单端删除一条消息（`im_message_delete`）或清空整个会话时，服务层会跟着删掉本人的收藏行，否则收藏列表会出现点不开的条目且 `total` 虚高；账号注销走 `MessageUserDataEraseSpiImpl` 一并物理清除。

## 十、远程控制模块（im-remote）

三张表回答三个问题：**有哪些机器能被控**（设备）、**谁在什么时候控了谁**（会话）、**期间做了哪些动作**（审计日志）。设备由 Agent 上线时注册，会话由邀请-授权流程产生，中继转发结束后收尾落库。

> **密钥类字段一律不落库**：控制端一次性 ticket、会话级 `aesKey`、路由用的 device 对象都是实体里的 `@TableField(exist = false)` 内存字段。审计库一旦能解密历史流量，它自己就变成了最敏感的那份数据。

### 10.1 `im_remote_device` — 被控端设备表

Agent 安装后首次上线写入一行，此后上线只更新状态与心跳时间。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 主键（雪花） |
| `user_id` | BIGINT | 否 | — | 设备归属用户 ID；**识别码模式的设备不归属任何账号，固定为 `0`** |
| `device_id` | VARCHAR(64) | 否 | — | Agent 安装时生成的设备唯一标识，重装系统前不变 |
| `device_name` | VARCHAR(128) | 是 | NULL | 设备名（计算机名），列表展示用 |
| `os` | VARCHAR(128) | 是 | NULL | 操作系统描述（`os.name` + `os.arch`） |
| `access_code` | VARCHAR(16) | 是 | NULL | 识别码（ToDesk 式接入码）；非空时任意登录用户可凭码发起邀请（仍需弹窗同意） |
| `status` | TINYINT | 否 | 0 | 状态：0 离线 / 1 空闲 / 2 忙 / 3 拒绝接入 |
| `last_online_time` | DATETIME | 是 | NULL | 最近一次心跳在线时间 |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `uk_user_device` | 唯一 | `user_id, device_id` | 一台机器一行：同一设备反复上线只更新这行，不会越积越多 |
| `idx_device` | 普通 | `device_id` | 中继按设备标识路由连接 |
| `idx_access_code` | 普通 | `access_code` | 凭识别码反查设备（发起邀请前的唯一入口） |

> **没有 `deleted` 列**：设备下线是状态变化（`status=0`）而不是删除——历史会话仍要能把设备名读回来。整表映射到 `AuditEntity`（仅 `create_time` / `update_time`）。

### 10.2 `im_remote_session` — 远程会话表

一次「邀请 → 授权 → 中继 → 结束」的完整过程对应一行，是控制端「我的会话」与被控端「连接记录」两个列表的数据源。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 会话 ID（雪花） |
| `invitee_user_id` | BIGINT | 否 | — | 被控方（设备归属人）用户 ID |
| `device_id` | VARCHAR(64) | 否 | — | 被控设备标识 |
| `inviter_user_id` | BIGINT | 否 | — | 控制方用户 ID |
| `permission` | VARCHAR(16) | 否 | `operate` | 权限：readonly 只读 / operate 可操作，被控端授权时可降档 |
| `status` | VARCHAR(16) | 否 | `inviting` | 状态：inviting 待授权 / active 进行中 / rejected 被拒绝 / ended 已结束 |
| `start_time` | DATETIME | 是 | NULL | 会话开始（中继建立）时间 |
| `end_time` | DATETIME | 是 | NULL | 会话结束时间 |
| `end_reason` | VARCHAR(32) | 是 | NULL | 结束原因：inviter-end / invitee-end / timeout / rejected / offline / control-offline |
| `bytes` | BIGINT | 否 | 0 | 中继转发总字节数（双向合计），**内存累加、收尾才落库** |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 邀请创建时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `idx_inviter_time` | 普通 | `inviter_user_id, create_time` | 控制方视角的会话列表倒序分页 |
| `idx_invitee_time` | 普通 | `invitee_user_id, create_time` | 被控方视角的会话列表倒序分页 |
| `idx_status` | 普通 | `status` | 捞出进行中的会话（断线清理、超时判定） |

> **两处与全库惯例不同的选择**：
> ① `status` 用 `VARCHAR` 而非约定的 `TINYINT`——会话状态要跨 Agent、中继、Web 三端在日志与协议里反复出现，字符串的可读性收益大于省下的 1 字节。
> ② `bytes` 不做每帧累加：中继数据帧频率极高，逐帧 `UPDATE` 会把会话行变成热点行，因此只在内存里累加、会话结束时一次性写库（代价是异常中断的会话流量统计缺失）。

### 10.3 `im_remote_audit_log` — 远程会话审计日志

只增不改不删的动作流水：文件删除、进程杀掉、命令执行、电源操作、输入被拦截等敏感动作各一行。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 主键（雪花） |
| `session_id` | BIGINT | 否 | — | 所属远程会话 ID |
| `action` | VARCHAR(32) | 否 | — | 动作标识：session-start / session-end / file-rm / ps-kill / exec / power / input-blocked … |
| `detail` | VARCHAR(1000) | 是 | NULL | 动作详情（路径、命令、拦截原因等），**写入前截断到 1000 字符** |
| `actor` | VARCHAR(16) | 是 | NULL | 触发方：inviter 控制端 / invitee 被控端 Agent / system 服务端流程事件；加列前的历史记录为 NULL |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 记录时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间（流水实际不会被更新，此列仅因 `AuditEntity` 统一带出） |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `idx_session_time` | 普通 | `session_id, create_time` | 审计详情页主查询：一个会话的全部动作按时间排开 |

> `actor` 是这张表最有价值的一列：同一次「命令被拒绝」，控制端发起、被控端拦截、服务端超时三种来源的定责结论完全不同。

## 十一、RAG 智能面试官模块（im-ai）

面试原本是全无状态的：对话历史由前端 `Interview.vue` 持有，刷新即丢，事后无法复盘，也没地方记「候选人中途切了几次屏」。这三张表把它变成可审计的业务——**会话元信息 + 逐轮问答 + 操作与违规事件流水**。监考阈值与开关见 `im.ai.proctor`（`ImAiProperties.Proctor`）。

> **信任边界**：前端只上报「发生了什么」，**算不算违规、是否强制结束全部在服务端按配置判定**。客户端上报的 `violation` 标志一律不被采信，否则改一个布尔值就能绕过监考。

### 11.1 `im_interview_session` — AI 面试会话表

一场面试一行，是「我的面试记录」列表与审计详情页的入口。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 面试会话 ID（雪花） |
| `user_id` | BIGINT | 否 | — | 候选人用户 ID |
| `title` | VARCHAR(64) | 否 | `后端 Java 全栈面试` | 面试题目 / 岗位名称 |
| `status` | TINYINT | 否 | 0 | 状态：0 进行中 / 1 正常结束 / 2 违规达阈值强制结束 / 3 未完成（刷新、关页、中途离开） |
| `start_time` | DATETIME | 是 | NULL | 开始时间（服务端收到开始请求的时刻） |
| `end_time` | DATETIME | 是 | NULL | 结束时间 |
| `duration_seconds` | INT | 否 | 0 | 面试时长（秒）：服务端拿 `end - start` 算，**不信客户端自报的计时** |
| `turn_count` | INT | 否 | 0 | 问答轮数（面试官提问数，等同于候选人作答数） |
| `violation_count` | INT | 否 | 0 | 违规总次数（下行四类合计 + 未单独列类的违规事件） |
| `blur_count` | INT | 否 | 0 | 切屏次数：标签页/窗口被最小化或切到其它应用（`window.blur` 与 `visibilitychange` 只计一次） |
| `copy_count` | INT | 否 | 0 | 复制次数：面试中复制题目去搜答案 |
| `paste_count` | INT | 否 | 0 | 粘贴次数：最典型的作弊信号——答案不是当场敲的 |
| `fullscreen_exit_count` | INT | 否 | 0 | 退出全屏次数（仅当处于全屏监考模式时才会产生） |
| `end_reason` | VARCHAR(32) | 是 | NULL | 结束原因：user-end 自行结束 / violation-limit 违规达上限 / reload / close / timeout |
| `screen` | VARCHAR(32) | 是 | NULL | 客户端屏幕分辨率（宽x高）；排「切屏误报」时用，分屏/双显会拉高误报率 |
| `client_info` | VARCHAR(255) | 是 | NULL | 浏览器 UA 摘要（只留引擎与版本，不落完整 UA） |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |
| `deleted` | TINYINT | 否 | 0 | 逻辑删除 |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `idx_user_time` | 普通 | `user_id, create_time` | 「我的面试记录」倒序分页 |
| `idx_status` | 普通 | `status` | 收尾进行中的会话（刷新/断电会留下永久 `status=0` 的行） |

**四类计数与事件类型的对应关系：**

| 事件类型 | 默认是否计违规 | 计入哪一列 |
|---|---|---|
| `visibility-hidden`（切标签页/最小化） | ✅ | `blur_count` |
| `blur`（窗口失焦） | ✅ | `blur_count` |
| `paste` | ✅ | `paste_count` |
| `fullscreen-exit` | ✅ | `fullscreen_exit_count` |
| `copy` | ❌（`count-copy=false`） | `copy_count`（留痕不计） |
| `cut` / `contextmenu` | ❌ | 无单独列，开关打开时只进 `violation_count` |
| `session-start` / `turn-submit` / `session-end` | ❌ 流程事件永不计 | — |

> **为什么把计数冗余在会话表上**：列表页要一次把「切屏 3 次」显示出来，不能为 20 行列表跑 20 次 `GROUP BY`。冗余可能与流水不平（上报丢失、并发累加），所以**审计定性一律以 `im_interview_event` 为准**，这些计数只用于展示与阈值判断。累加走 `UPDATE ... SET x = x + n` 的原子写法，避免「读-改-写」在并发上报时丢计数。
> **`status=3 未完成` 怎么产生**：不加定时任务——候选人下次开始面试时，服务端先把他所有 `status=0` 的会话补记为未完成（关闭页面无从通知，这是浏览器端的硬限制）。

### 11.2 `im_interview_message` — AI 面试问答记录表

逐轮留存的问答副本，用于事后复盘「他到底答了什么」。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 主键（雪花） |
| `session_id` | BIGINT | 否 | — | 所属面试会话 ID |
| `seq` | INT | 否 | — | 会话内序号，从 1 递增；**排序以此列为准，不用 `create_time`（同毫秒会并列）** |
| `turn_no` | INT | 否 | 0 | 属于第几轮：提问行是本题题号，作答行是题号减一；与 `role` 共同构成幂等键 |
| `role` | VARCHAR(16) | 否 | — | 角色：assistant 面试官提问 / user 候选人作答 |
| `content` | TEXT | 否 | — | 正文，写入前按 `im.ai.max-message-chars` 截断 |
| `char_count` | INT | 否 | 0 | 正文字符数：审计时看作答长度分布，不必把正文读回来 |
| `elapsed_ms` | BIGINT | 否 | 0 | 候选人从收到本题到提交的耗时（毫秒）；`role=assistant` 固定为 0 |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 创建时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `uk_session_turn` | 唯一 | `session_id, turn_no, role` | **幂等**：前端因网络抖动重传同一轮时，提问行与作答行各自撞回原键并被静默跳过 |
| `idx_session` | 普通 | `session_id` | 读一个会话的完整对话 |

> **问答单独成表**而不是往会话表塞一个 JSON 大字段：审计要能回答「他是在答第几题时切屏的」，整段 JSON 既撑爆行又只能全量读回。
> **入库顺序**：前端一次上报同时带「上一答 + 新题」，服务端**先写作答再写提问**，`seq` 才与真实对话一致；反过来先写提问会得到 Q1、Q2、A1 这种读不通的序列。对话历史本身仍由前端持有并每轮完整发给模型，这张表只是不参与对话组装的审计副本。
> **幂等键为什么不用 `seq`**：`seq` 由服务端 `maxSeq + 1` 现算，重传一次就会算出一个新值，拿它当幂等键等于没加（真机验证里同一轮重报会得到 `seq=4、5` 两行新数据）；而 `turn_no` 是前端报的「这是第几题」，重试才能撞回同一把键。也不给 `seq` 建唯一键：并发上报可能算出同一个 seq，若约束拦下，撞键那一行会被当成「已存在」静默丢弃——顺序略受影响远比丢一条问答好。

### 11.3 `im_interview_event` — AI 面试操作与违规事件流水

监考看到的每一个动作都在这里留一行，是判断「这次面试结论是否可信」的唯一依据。

| 字段 | 类型 | 允许空 | 默认值 | 含义 |
|---|---|---|---|---|
| `id` | BIGINT | 否 | — | 主键（雪花） |
| `session_id` | BIGINT | 否 | — | 所属面试会话 ID |
| `user_id` | BIGINT | 否 | — | 候选人 ID（冗余一份：审计常按人查，不必先 join 会话表） |
| `event_type` | VARCHAR(32) | 否 | — | 事件类型：visibility-hidden / blur / copy / paste / cut / contextmenu / fullscreen-exit / session-start / turn-submit / session-end |
| `violation` | TINYINT | 否 | 0 | 是否计入违规：1 计入会话表计数并参与阈值判断，0 仅记录现象（由服务端按配置写入） |
| `turn_no` | INT | 否 | 0 | 当时进行到第几轮，0 表示尚未开始问答；回答「他在答哪题时切屏」 |
| `detail` | VARCHAR(500) | 是 | NULL | 补充信息（离开多久、粘贴多少字符、从哪个元素粘的等），写入前截断到 500 字符 |
| `event_time` | DATETIME(3) | 否 | — | 事件发生时刻（**客户端上报的本地时间，带毫秒**） |
| `create_time` | DATETIME | 否 | CURRENT_TIMESTAMP | 服务端落库时间 |
| `update_time` | DATETIME | 否 | CURRENT_TIMESTAMP ON UPDATE | 更新时间（流水不会被更新） |

**索引：**

| 索引名 | 类型 | 列 | 用途 |
|---|---|---|---|
| `PRIMARY` | 主键 | `id` | 主键定位 |
| `idx_session_time` | 普通 | `session_id, event_time` | 审计详情页主查询：一个会话的全部事件按时间排开 |
| `idx_user_time` | 普通 | `user_id, create_time` | 跨会话看同一个人的违规习惯 |
| `idx_session_violation` | 普通 | `session_id, violation` | 只看违规：把流程事件排除在索引之外 |

> **两个时间都要留**：`event_time`（客户端本地墙上时间）与 `create_time`（服务端落库时间）的差，就是上报延迟或者候选人改了系统时间的证据。事件由前端 3 秒攒批上报、页面隐藏时立即补发，因此这个差值正常在一到数秒内。
> **`event_time` 用 `DATETIME(3)`**：切屏、复制这类动作可能在同一秒内连着发生多次，秒级精度会把它们压成一条。

## 十二、扩展说明

### 12.1 `im_message.extra` JSON 字段结构

`extra` 列为 `JSON` 类型，映射到 `com.im.common.domain.MessageExtra`（`@JsonInclude(NON_NULL)`，只序列化非空字段）。它把「附件元数据」「@ 提醒」「系统通知动作」等非通用信息从主表列中解耦出来，避免为每种消息类型都加一堆稀疏列。

| JSON 键 | Java 类型 | 含义 |
|---|---|---|
| `fileId` | Long | 关联文件 ID（指向 `im_file.id`） |
| `fileName` | String | 文件原始名 |
| `fileUrl` | String | 文件访问地址 |
| `fileSize` | Long | 文件字节数 |
| `contentType` | String | MIME 类型 |
| `ext` | String | 扩展名，不含点 |
| `width` | Integer | 图片宽度（像素） |
| `height` | Integer | 图片高度（像素） |
| `duration` | Integer | 语音时长（秒） |
| `atUserIds` | List\<Long\> | 被 @ 的用户 ID 列表 |
| `atAll` | Boolean | 是否 @ 全员 |
| `action` | String | 系统通知动作标识，前端据此决定交互 |
| `watermark` | Boolean | 图片/文件是否带发送者水印：为真时接收端查看该附件会叠加发送者昵称水印 |
| `flash` | Boolean | 是否闪照（仅图片）：阅后即焚，销毁后服务端不再可下载原图 |
| `flashSeconds` | Integer | 闪照查看时长（秒，1~60，缺省 5）；倒计时由前端执行 |
| `flashViewedBy` | List\<Long\> | **闪照已消费查看的用户 ID 名单**（服务端权威，落库）：每人各有一次查看机会，互不影响 |
| `flashViewed` | Boolean | **对当前查看者是否已销毁**（瞬态、**不落库**）：下发前按 `viewerId` 从 `flashViewedBy` 现算，名单含自己即为 true |
| `ocrText` | String | 发送端 OCR 提取的图内文字（已过敏感词遮蔽），供接收端「图内文字」展示 |
| `callMediaType` | String | 通话媒体类型（仅通话记录 `MsgType.CALL`）：audio / video |
| `callScreenRecorded` | Boolean | 通话是否录屏留存（仅通话记录）：为真时 `content` 指向的录制文件含屏幕画面 |
| `callParticipantCount` | Integer | **参与人数（仅群通话记录）**：有值就是群通话，气泡写「群语音通话 · 4 人」；旧记录与 1:1 无此字段自然回落成「语音通话」。刻意只存人数不存参与者 ID 清单——成员退群后那份清单会变成假名单 |
| `transferAmount` | Long | **转账（type=12）**：金额（积分，正数）。服务端在扣款成功后写入，**不接受客户端上报** |
| `transferToUserId` | Long | 转账：收款人用户 ID |
| `transferToNickname` | String | 转账：收款人昵称快照（发送时定格，付款方气泡无需再查库就能写「转给谁」） |
| `transferMemo` | String | 转账：附言（已 XSS 清洗与敏感词遮蔽，可空；空白归一为 NULL） |
| `packetId` | Long | **红包（type=13）**：红包 ID，兼作 Redis 键与账本流水的 `ref_id`，领取时按此寻址 |
| `packetAmount` | Long | 红包：总额（积分，正数） |
| `packetCount` | Integer | 红包：份数；私聊恒为 1（独占），群聊可多份拼手气 |
| `packetGreeting` | String | 红包：祝福语（可空，默认「恭喜发财，大吉大利」） |

**按消息类型使用不同的键子集：**

- **文本消息（type=1）**：`extra` 通常为 NULL；群聊里若 @ 了人，则填 `atUserIds` / `atAll`。
- **图片消息（type=2）**：`content` 存文件 ID，`extra` 填 `fileId` / `fileName` / `fileUrl` / `width` / `height`；**闪照**额外填 `flash` / `flashSeconds` / `flashViewedBy`（见下）。
- **文件消息（type=3）**：`extra` 填 `fileId` / `fileName` / `fileUrl` / `fileSize` / `contentType` / `ext`。
- **语音消息（type=4）**：`extra` 填 `fileId` / `fileUrl` / `duration`。
- **转账消息（type=12）**：`extra` 填 `transferAmount` / `transferToUserId` / `transferToNickname` / `transferMemo`，`content` 存附言（无则存「转账」）以便会话内关键词检索复用同一份正文。**这些字段全部由服务端写入**（`TransferContentHandler` 只校验与定格，不参与扣款）。
- **红包消息（type=13）**：`extra` 填 `packetId` / `packetAmount` / `packetCount` / `packetGreeting`。**「谁领了、还剩多少」不进 `extra`**（那是会变的状态，落进消息就得反复改历史行），由前端点开时向 `GET /api/wallet/packet/{packetId}` 现取（领取态在 Redis Hash，零 DDL）。
- **系统通知（type=5）**：`from_user_id=0`，`extra` 填 `action`（如 `recall`、`join_group`）供前端识别交互类型。

> **闪照的「每人各看一次、互不影响」语义（仅单聊）**：服务端只在 `extra.flashViewedBy` 存一份权威名单，**不把任何人的已阅状态烤进共享的 `flashViewed`**（那个字段不落库）；下发时 `MessageConvert.flashForViewer` 按 `viewerId` 拷贝一份、为每人算出他自己的 `flashViewed`，已阅者还会被置空 `fileUrl` 防二次拉图。因此同一条闪照，发送端与接收端看到的销毁态可以不同。
>
> **销毁 = `im_file` 记录逻辑删（非物理删）**：只有会话**全员**都进过 `flashViewedBy` 才调 `FileService.destroy` 置 `im_file.deleted=1`，此后 `download` / 预签名直链均取不到字节；**存储字节刻意不删**（秒传按 MD5 去重、多行记录共享 `objectKey`，删字节会误伤他人同内容文件），残留字节属无引用垃圾。`im_message` 行本身不动，仅 `extra` 追加名单。无 DDL（`extra` 是 JSON 列），存量闪照无 `flashViewedBy` 视作无人看过。
>
> **防截图仅 Electron 桌面端**：`flash` 预览期间主进程 `setContentProtection`（Windows `SetWindowDisplayAffinity`）把窗口从截屏/录屏输出里抹黑；浏览器/手机无对应 Web API，做不到。

> `MessageExtra.hasMention()` 方法：当 `atAll=true` 或 `atUserIds` 非空时返回 true，供会话模块判断是否需要**打破免打扰**（即使会话设了 `is_muted`，被 @ 时仍提醒）。

### 12.2 关键设计模式速查

| 模式 | 落地位置 | 解决的问题 |
|---|---|---|
| **幂等键** | `im_message.uk_from_client`、`im_conversation.uk_biz_key`、`im_interview_message.uk_session_turn` | 网络重试/重复提交不产生重复数据 |
| **标记附属表按维度选键** | `im_message_reaction`/`vote`/`favorite`（一人一行）与 `im_message_essence`（一群一行）| 同一行为在不同维度上的可见范围不同，唯一键就得挂在该维度上；收藏与精华同构、只差 `user_id` 与 `message_id` 谁在前 |
| **虚拟生成列 + 唯一索引** | `im_friend_request.pending_flag` | 「唯一约束」与「保留历史」二者兼得 |
| **双向冗余** | `im_friend`（两行） | 好友双方各自独立维护备注/分组/拉黑 |
| **软状态 vs 物理删除** | 群成员 `status` / 好友物理删 | 按「是否需要保留历史」分别选择 |
| **冗余摘要** | `im_conversation.last_msg_*` | 会话列表页免 join 消息大表 |
| **游标分页** | `im_message.idx_conv_seq`（seq 游标） | 海量消息深翻页不用 OFFSET，性能稳定 |
| **存储抽象** | `im_file.storage_type/bucket/object_key` | 本地/MinIO 双实现共用一张表 |
| **单端删除表** | `im_message_delete` | 「删除」只影响本人，不动主表与他人视图 |
| **事件流水 + 冗余计数** | `im_interview_event` / `im_interview_session.*_count` | 明细可定性追责，汇总可低成本展示；定性只认流水 |
| **服务端定权** | `InterviewAuditService`：违规标志、阈值判定、时长计算 | 客户端只报现象，改不了结论 |
| **密钥不落库** | `RemoteSession` 的 ticket / aesKey 为 `@TableField(exist=false)` | 防止审计库变成能解密历史流量的地方 |
| **原子累加** | `InterviewSessionMapper.incrementCounters`（`SET x = x + n`） | 并发上报不丢计数 |

### 12.4 表数量小结

- **物理表 25 张**，分布于 9 个模块：用户权限 5、好友 2、会话 2、消息 3、群组 2、文件 1、远程控制 3、RAG 面试官 3、直播礼物与钱包 4。
- 主表（用户、角色、权限、会话、群组、文件、面试会话）启用逻辑删除 `deleted`；关系表与消息表按业务特性选用物理删除或软状态位；远程与面试的流水表（审计日志、问答、事件）只增不删。
- 远程控制三表不参与 IM 消息链路，`sql/im_data.sql` 里没有它们的种子数据，由 Agent 上线与会话流程写入；面试三表预置了 4 场演示会话（见 12.3）。
- 种子数据的导入方式统一用 `mysql -e "source sql/xxx.sql"`：Windows PowerShell 下 `<` 不可用，`Get-Content | mysql` 又会被管道把中文刷成 `?`。
- 种子脚本的清理段只删自己的 ID 段（IM 表 `id < 10000`，面试三表 `2300~2399` / `3300~3399` / `9300~9399`），
  跟运行期写入的雪花 ID（19 位，量级 10^18）是两个不相交的区间，所以对有真实数据的库也能重跑；
  整表 `DELETE` 是禁止的（早期版本就是这样把已注册账号与聊天记录清掉的）。
- 全库无物理外键，关系由应用层与索引维护，符合互联网应用「弱化外键、便于水平拆分」的通行实践。

## 十三、直播礼物与钱包模块（im-user / im-live）

D 组第二项（直播连麦 + 礼物打赏）引入的**虚拟积分/币体系**。不涉真实货币：充值走**模拟支付桩**（`PaymentSpi` + `MockPaymentSpi`，`@ConditionalOnProperty` 门控，接真实支付以 `@Primary` 覆盖），余额即「积分」。连麦本身是瞬时态，走 Redis **不建表**。钱包三表在 im-user（余额/目录/账本），送礼流水在 im-live（房间维度业务）。

### 13.1 `im_user_wallet` — 用户钱包（im-user）

一行一个用户，**主键即 `user_id`**（与 `im_user.id` 同值，非雪花，无需另外索引）。启用逻辑删除。

| 列 | 类型 | 说明 |
|---|---|---|
| `user_id` | BIGINT PK | 用户 ID（与 `im_user.id` 同值） |
| `balance` | BIGINT | 积分/币余额，**非负** |
| `total_recharged` | BIGINT | 累计充值到账 |
| `total_consumed` | BIGINT | 累计消费（送礼等） |
| `sign_last_date` | DATE | 最近签到自然日，**按天去重** |
| `deleted` | TINYINT | 逻辑删除 |

> **防超扣关键**：扣款走条件 UPDATE `... WHERE user_id=? AND balance >= ?`，在数据库层兜住并发超扣，应用层再校验一次；扣款与写 `im_wallet_transaction` 同事务。真实用户首次访问钱包时由服务端自动建 0 余额行。

### 13.2 `im_gift` — 礼物目录（im-user）

运营可增删改，前端礼簿按 `status=1` 且 `sort` 升序渲染（`idx_status_sort`）。逻辑删除。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | 礼物 ID |
| `name` | VARCHAR(32) | 礼物名称 |
| `icon` | VARCHAR(512) | 图标（表情符号或图片地址） |
| `price` | INT | 单价（积分） |
| `kind` | VARCHAR(16) | `normal` 普通 / `effect` 特效 |
| `sort` | INT | 排序，小的在前 |
| `status` | TINYINT | 1 上架 / 0 下架 |

> **种子数据**（`im_data.sql`）：ID 段 `5001~5008`（小心心❤️1 / 棒棒糖🍭10 / 大啤酒🍺52 / 加油鸭🦆66 / 玫瑰花🌹99 / 烟花🎆520 / 火箭🚀1314 / 星球🪐5200），清理段按 `id BETWEEN 5000 AND 5999` 限定，不整表清空。

### 13.3 `im_wallet_transaction` — 钱包账本流水（im-user）

充值/送礼/签到/后台调整/转账/红包/红包退回逐条流水，**只增不改**（继承 `AuditEntity`，不带 `deleted`）。索引 `idx_user_time(user_id, create_time)`。

> **转账与红包不建新表**：资金变动全部落在这张既有表里，只是 `type` 多了三个取值（`VARCHAR(16)` 容量足够，**无需任何 DDL**）。列定义与索引一字未改，因此存量库不需要跑 `ALTER`；`sql/im_schema.sql` 里那句 `type` 列注释只影响全新建库，纯 cosmetic。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | 流水 ID（雪花） |
| `user_id` | BIGINT | 钱包归属用户 |
| `type` | VARCHAR(16) | `recharge`/`gift`/`checkin`/`adjust`/**`transfer`**/**`packet`**/**`refund`**（常量收口在 `ImConstants.WALLET_TX_*`，手打错一次账本就归类错乱） |
| `amount` | BIGINT | 变动额（**有符号**，支出为负）：转账与发红包产生负额行，收款/领取/退款产生正额行 |
| `balance_after` | BIGINT | 交易后余额快照 |
| `ref_id` | BIGINT | 关联业务 ID，**语义随 `type` 变**：`gift` 存送礼记录/房间 ID；`transfer` 存**对方用户 ID**（双向流水互相指向对方）；`packet`/`refund` 存**红包 ID** |
| `remark` | VARCHAR(128) | 备注 |

> **账本即过期退款的唯一依据**：红包没人领时退多少，不靠 Redis 里的计数器，而是把同一个 `packetId` 下 `type IN ('packet','refund')` 的行**求和**：`SUM(amount) < 0` 就是还有人没领，`-SUM(amount)` 即应退额；退完那一组行归零，自动退出下一轮扫描集——所以这条 `refund` 行本身就是幂等锁，Redis 被清也不会退错。`UserWalletMapper.debitBalance` / `creditBalance` 都是条件 UPDATE，用户之间转积分**不动 `im_user_wallet.total_consumed`**（那一列只算「向平台买服务」的送礼）。

### 13.4 `im_gift_record` — 送礼流水（im-live）

一行一笔送礼，**只增不改**。冗余礼物名/图标/成交单价，礼物后续下架或改价不影响历史展示与对账。索引 `idx_room_time(room_id, create_time)`（房间热度/收礼榜）、`idx_receiver_time(receiver_id, create_time)`（主播收礼明细）。**两个索引已双双被「主播数据面板」用上**（`GET /api/live/anchor/stats`：按场次聚合走前者、按主播 + 时间窗聚合与两个榜单走后者），面板因此做到零 DDL，不必另建汇总表（机理见 `md/直播.md` §16）。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | 送礼记录 ID（雪花） |
| `sender_id` | BIGINT | 送礼人 |
| `receiver_id` | BIGINT | 收礼主播 |
| `room_id` | BIGINT | 直播间 ID |
| `gift_id` | BIGINT | 礼物 ID |
| `gift_name` / `gift_icon` / `unit_price` | — | 冗余快照 |
| `count` | INT | 数量 |
| `total_price` | BIGINT | 总价 = `unit_price * count` |

> 送礼链路（im-live `GiftServiceImpl`）：校验直播中 → count 夹 [1, `max-gift-count`] → `WalletSpi.deduct` 原子扣款（不足回 `WALLET_BALANCE_NOT_ENOUGH`）→ 写本表 → 房间累计热度记 Redis（供后续 PK）→ 事务提交后广播飘屏帧。扣款与落库同事务，广播在事务提交后。

## 十四、管理后台模块（im-admin）

im-admin 是**第 11 个业务模块**，也是它唯一的业务表。一张 `im_report` 同时充当举报处理队列与可追责的历史台账。

> **为什么这个项目默认偏好（零 DDL）在这里让位**：与它同批的「直播回放存档」「转账红包」都做到了零 DDL，「消息收藏」和这张表没有。原因是举报同时要满足两件事，而 Redis 一件都满不了：
>
> 1. **「三天后回来看结果」**——工单要活过 Redis 的 TTL，也要活过重启；
> 2. **「这个主播被投诉过几次」**——这是个要按人、按时间、按状态分页的聚合，每类查法都要一个联合索引（共四个）。
>
> 收藏至少只服务「我自己看」，举报则是**用来追责的持久记录**，两者都选了建表。代价直说：旧库不跑 `sql/migration_report.sql` 就没有这张表。

### 14.1 `im_report` — 举报工单（im-admin）

一行一张工单。**无 `deleted` 列**（实体 `Report` 继承 `AuditEntity`）：处置只改 `status`，行永不删也不软删。建表语句已在 `sql/im_schema.sql`，存量库跑 `sql/migration_report.sql`。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | 举报 ID（雪花） |
| `reporter_id` | BIGINT | 举报人，**一定是登录者本人**（取 token 里的 uid，不接受前端传入） |
| `target_type` | VARCHAR(16) | `user` / `message` / `room` / `group`，取值收口在 `ReportTargetType` 枚举 |
| `target_id` | BIGINT | 被举报对象 ID，单独看没有意义，必须与 `target_type` 合读 |
| `reported_user_id` | BIGINT NULL | **责任人**：消息→发送者、房间→主播、群→群主、用户→本人。提交时由 SPI 反查后落库，而不是处理时再查（对象会被删）；取不到就为空，此时只能走「不处理 / 驳回」 |
| `reason_code` | VARCHAR(32) | 理由码（枚举 `ReportReason`），**自由文本不允许当分类用** |
| `reason_text` | VARCHAR(500) NULL | 补充描述，部分理由必填；写入前过敏感词遮蔽与长度截断 |
| `evidence` | JSON NULL | 证据快照，见 §14.2。实体靠 `@TableName(autoResultMap = true)` + `Jackson3TypeHandler` 才能反序列化（与 `im_message.extra` 同一个坑） |
| `status` | TINYINT | `0` 待处理 / `1` 已受理 / `2` 已驳回 / `3` 已处置，见 §14.3 |
| `disposition` | VARCHAR(32) NULL | 处置动作码（`ReportDisposition`），与 `status=3` 同时写 |
| `handle_remark` | VARCHAR(500) NULL | 处置说明，回给举报人并留档（`im.admin.handle-remark-required` 默认必填） |
| `handler_id` | BIGINT NULL | 处理人（管理员）ID，**受理那一刻就写**，意思是「这单有人认领了」 |
| `handle_time` | DATETIME NULL | 进入**终态**的时刻。受理不写它，所以 `status=1` 且本列为空就是「已认领但还没结论」，不用另加一列区分 |
| `create_time` / `update_time` | DATETIME | 全库统一约定，举报时间与最后变动时间 |

**四个索引逐一对应一个后台页面动作**：

| 索引 | 服务谁的查询 |
|---|---|
| `idx_status_time(status, create_time)` | 工单队列默认按「待处理 + newest」排（不建它每次翻页都全表扫） |
| `idx_reporter_time(reporter_id, create_time)` | `GET /api/report/mine`、以及日配额「今日已提几条」 |
| `idx_target(target_type, target_id)` | 同一个对象被报了几次（重复举报提级） |
| `idx_reported_user(reported_user_id, create_time)` | 看板「被举报榜」与用户页「未处置工单数」（两者都跳 `reports?keyword=<userId>`） |

> **为什么不建唯一键**：`uk(reporter_id, target_type, target_id)` 会把「隔几天再报一次」永久挡死，而「上次报了没处理、我再报一次」在举报场景里是合理诉求。去重闸门因此放在 Redis，只挡一段时间（见 §14.4）。

### 14.2 `evidence` JSON 列的形状

列内容就是 `im-common` 的 `ReportTargetDTO` 序列化结果（由各归属模块的 `ReportTargetSpi.resolve` 产出）：

| 键 | 说明 |
|---|---|
| `targetType` / `targetId` | 与列同值，冗余一份是为了这份快照单独拿出来也能读 |
| `reportedUserId` | 责任人（与列同源，一次反查两处用） |
| `title` | 一句话标识：昵称 / 「消息·来自某某」 / 直播标题 / 群名称 |
| `excerpt` | 内容摘要，**由各模块自己截断**（`im.admin.excerpt-max` 默认 200 字），落库前 im-admin 再夹一道兜底；无正文的对象（如用户）为空 |
| `meta` | 其余快照字段，**键直接用中文标签**（「所属会话」「开播时间」这类），值是已格式化的字符串 |
| `dispositions` | 提交那一刻该对象可执行的处置动作码（模块没装配就是空） |

三条设计取向与它们的代价（都写在 `ReportTargetDTO` 的 javadoc 里）：

- **快照而不是活引用**：举报天然滞后于内容——消息会被撤回、直播会关播、群会解散。等管理员处理时再去查对象，十有八九查到「不存在」，工单成废纸。代价是这份数据**有隐私与体积代价**，存的是「管理员判案需要的最小内容」而不是全文；这也正是不把它放进消息表 / 房间表、只在举报这条链上产生的原因。
- **`meta` 用中文键而不做英文码表**：这张 Map 唯一的消费者是后台工单详情那一段「键值对」展示，**没有任何代码按键取值**。用英文键等于把一份字段名翻译表复制到后台前端，归属模块加一个快照字段要改两处、还容易漏。代价是这些键**不能当契约引用**：将来谁要按键取值，请改成结构化字段，而不是去 parse 这份 Map。
- **`dispositions` 存快照而不每行回查 SPI**：后台列表直接渲染有效下拉。代价是模块后来才装上时，**旧工单的下拉仍然是空的**——那种情况按「重新举报一次」处理，不改动已落库的证据。

### 14.3 状态机

```
0 待处理 ─受理 accept()─▶ 1 已受理 ─handle()─▶ 3 已处置
   │  │                      │  └─reject()─▶ 2 已驳回
   │  └────reject()───────────┘
   └─ handle()/reject() 也可直接进终态
```

三条硬约束（都在 `ReportService` 里，不靠前端禁用按钮兼容）：

1. `accept()` **只允许 `status=0`**，且只写 `handlerId`、不写 `handleTime`；
2. `reject()` / `handle()` 要求 `requireNotFinished`（`0` 或 `1`），重复处置回 `REPORT_ALREADY_HANDLED(14006)`；
3. **没有超时自动关闭**——`已受理` 是纯人工状态，没人受理就一直是待处理（所以队列页默认按待处理排序，而不是把它藏起来）。

终态后不允许再改：判错了另开一张工单，不改历史工单，否则「谁在什么时候以什么理由处置过」这条追责线就断了。

### 14.4 与表配套的 Redis 键（都不落 DDL）

| 键 | 作用 | 为什么不在表上 |
|---|---|---|
| `im:report:dedup:{reporterId}:{targetType}:{targetId}` | 去重闸门（默认 24 小时，`dedup-hours`） | 见 §14.1 唯一键那条；类型串直接拼进键里不做数字编码，因为这张表的键本来就要靠人肉 `redis-cli` 排查。代价：Redis 丢了去重就失效，后果只是后台多几张重复工单 |
| `im:report:quota:{reporterId}:{yyyyMMdd}` | 每人每日条数（默认 20，`daily-quota`） | 键里带日期而不是靠 TTL「一天后过期」：后者要么算「到明天零点的秒数」，要么写成固定 24 小时滑到半夜重置。日期取服务器本地时区 |
| `im:admin:dashboard` | 看板聚合缓存（默认 60 秒，`dashboard-cache-seconds`） | 缓存的是各模块 SPI 现算的 COUNT，不落数字行——**刻意不建汇总表**，避免缓存失效与真值不一致 |

### 14.5 种子数据与权限

后台能力只有一个权限点：`im_permission` 的 **`107 / system:manage`**（`system` 分组）。种子只给 `admin` 角色（`role_id=1`）授予它，`user` 角色（`role_id=2`）的授权清单里**不包含 107**。

> 这个权限点是两个前端的唯一闸门：后台 `/api/admin/**` 全部带 `@SaCheckPermission("system:manage")`，`im-admin-ui` 登录后拉 `/auth/me`，拿不到这个权限就在**登录环节**直接拒（不写 token），而不是进去看一堆 403。用户侧 `/api/report/**` 三个端点**没有任何权限注解**（登录即可），聊天端也绝不会去调 `/api/admin/**`。

### 14.6 不跑 SQL 会怎样、怎么回滚

- **只影响举报与后台**：`POST /api/report` 与 `GET /api/report/mine` 会抛 Table doesn't exist 并转成 `5000` 系统异常，后台举报队列与看板举报分区取不到数；**用户 / 消息 / 会话 / 直播 / 钱包等既有接口一概不碰这张表**（它只有 im-admin 读），所以不会像收藏那次一样把消息列表整片打挂。
- 即便如此仍建议正序：**先跑脚本、再启动新版后端**。
- **回滚就是 `DROP TABLE IF EXISTS im_report;`**（纯新增表，删表不影响任何既有数据）。但注意 `migration_report.sql` 自带 `DROP TABLE IF EXISTS` 以保幂等重跑——**已产生工单后再跑一次会把工单连历史一起删掉**，线上环境先 `SELECT COUNT(*) FROM im_report` 确认。

## 十五、群通话的实时态（im-websocket，零 DDL）

群通话（多方 mesh，2026-10-19）**一张表都没建、一行 SQL 都不需要跑**。它落库的只有通话记录本身（复用第十四节 `MsgType.CALL(6)`，`extra` 多一个 `callParticipantCount`，见 §12），其余全部是 Redis 里带 TTL 的瞬时态：

| 键 | 值 | 作用 | 为什么不在表上 |
|---|---|---|---|
| `im:gcall:state:{callId}` | 花名册 JSON（成员 / 角色 / muted / cameraOff / joinedAt） | **唯一权威**。整存整取而不是 Hash：两人同时进房必须在 SETNX 锁内排队，分字段写会让后写的抹掉前一个 | 通话挂了就是历史，没寿命的用户数据才该进 MySQL；而这份态丢了只会「这通电话断线」，不会错账 |
| `im:gcall:user:{userId}` | callId | 忙线指针：一人同时只允许一路群通话 | 与 `im:call:user:`（1:1）、`im:link:user:`（直播连麦）是**三套独立的键**，服务端互不相认；跨类型不并发靠前端拦（代价与理由见指南 §13） |
| `im:gcall:group:{groupId}` | callId | 一群一路的闸门，同时是 `GET /api/call/group/active` 的索引 | 不做全群广播只查 REST：`im-websocket` 不持群成员名单，要广播就得让业务模块反向喂名单（破星型约束） |
| `im:gcall:lock:{callId}` | 占位 | 读改写互斥短锁 | 纯并发控制，不承载业务数据 |

TTL = `im.call.max-duration-seconds + 120s`，每次协商续期。所以：**即使进程崩了、没人发 `leave`，Redis 也会自己回收**（这正是这类键不该建表的理由——它们的正确性靠过期兜底，不靠删除链路）。

> 三个旋钮：`im.call.group-enabled`（默认 true）、`im.call.group-max-slots`（默认 4，服务端硬夹 `[2,6]`，因为 mesh 下每人要上行 `N-1` 路编码）、`im.rate-limit.ws-group-call-count / -seconds`（默认 600/60s，比 `ws-chat` 宽两个量级：N-1 路的 ICE candidate 是逐条帧）。四个前缀按既有惯例**定义在 `GroupCallSignalingService` 里而不是 `RedisKeys`**（`im:call:*` 与 `im:link:*` 也是这么放的：这类键只有信令层读写、不需跨模块共享，提到公共常量类反而误导其他模块去拼它）。机理见《[语音视频通话接入指南](语音视频通话接入指南.md)》§13。
