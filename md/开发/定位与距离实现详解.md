# 定位与距离实现详解（坐标采集 → 落库 → 距离计算 → 模糊展示）

> 本文说明 IM 系统「定位」与「距离」这两件事是怎么实现的：坐标从哪来、存到哪、谁算距离、
> 为什么用户看到的永远是一句「3 km」而不是一个数字。写侧在 `im-user`，读侧在 `im-friend`，
> 算法与编码收在 `im-common`，前端采集与地区换算在 `im-ui`。
>
> 分工说明：**省市县三级联动与坐标反查地区**属于「定位」的下游，本文第四节讲它的口径与降级策略；
> 字典生成、级联框交互细节见 [`README详细开发指南.md`](../../README详细开发指南.md) §十九.14 / §十九.15。
> 逐项手验步骤见 [`交友功能手动验证清单.md`](../交友功能手动验证清单.md) §7（附近的人）、§18.2、§19。
>
> 定位本身怎么来的（信号源、API 形态、参数与字段）见第二节 2.5 / 2.6；
> 经纬度怎么变成地图卡片与第三方导航链接（瓦片算法、高德/百度/谷歌逐参数）见第十一节。

## 一、全景：一条写链路，三条读链路

「距离」这件事**不落库**：库里只存坐标与坐标的 geohash，距离是每次请求时现算的。
算完立刻模糊化成一句文案再出门，精确米数只活在服务端内存里。

| 链路 | 方向 | 位置 | 产出 |
|---|---|---|---|
| 采集并落库 | 写 | `im-ui` → `im-user` | `im_user_profile` 的 `lng / lat / geohash / location_time` |
| 资料卡距离 | 读 | `im-user` | `DatingProfileVO.distanceText`（一句模糊文案或 null） |
| 卡池距离 | 读 | `im-user` → `im-friend` | `DatingCardDTO.distanceText`（同上，走同一个方法） |
| 附近的人 | 读 | `im-friend` → `im-user` | 按精确距离排序的 ID 列表，对外仍只给 `distanceText` |

```
写：浏览器定位 API
     └─ utils/location.js  requestLocation()          三个入口共用
          ├─ Profile.vue    locateMe()        → 交友资料定位（落库 + 触发第四节地区反查）
          ├─ Discover.vue   locateForNearby() → 附近的人报 2042 时的原地引导
          └─ ChatWindow.vue useMyLocation()   → 发一条位置消息（★ 与交友距离无关，见下）
                     │
                     ▼  PUT /api/dating/profile  { lng, lat }
          DatingProfileServiceImpl#applyLocation
                     │  服务端重算 geohash（6 位）+ 写 location_time = now()
                     ▼
          im_user_profile  (lng, lat, geohash, location_time)

读：谁看谁的距离
     ├─ 资料卡 / 卡池 → UserProfile#distanceTextFrom(viewer)
     │                    ├─ 门 1：本行 show_distance = 1
     │                    ├─ 门 2：双方 location_time 都在 7 天内
     │                    └─ GeoUtil.fuzzyDistanceBetween() → 「500 m 内 / 1 km 内 / N km / 100 km 以上」
     └─ 附近的人 → DatingQuerySpiImpl#nearbyIds()
                      ├─ 半径决定 geohash 前缀位数（5 位或 4 位）
                      ├─ SQL 粗筛：likeRight(geohash, prefix) + 采信期 + 筛选条件，LIMIT 500
                      ├─ 内存精排：逐行 haversine，留下 ≤ 半径的，按米数升序
                      └─ 多取 3 倍去校账号状态 → NearbyPeerVO（无距离字段）
```

★ **三个定位入口里有一个是「假同类」**：`ChatWindow.vue` 的位置消息走的是
`utils/geo.js`（拼外部地图链接：高德 / 百度 / 谷歌三家可选，点卡片时弹窗选或设置里钉一家）
与消息表的 `extra`，**不写 `im_user_profile`**，
既不参与附近的人也不参与资料卡距离。它只是共用同一个采集函数，
以便复用「授权等待不计入超时」那一套口径。查「为什么定位了却没有距离」时别把它算进去。

★ 位置消息这一侧自己有个坐标系坎值得记一笔（与交友距离无关，但同样是坐标）：
浏览器给的是 WGS-84，高德用 GCJ-02、百度用 BD-09，直接当对方坐标用会偏几十到几百米。
**前端不自己算转换**，而是声明原始坐标系交对方服务端转（高德 `coordinate=wgs84`、
百度 `coord_type=wgs84`）。改这里要当心两家的经纬度顺序是**反的**：
高德 `position=经度,纬度`、百度 `location=纬度,经度`，弄反了不报错、只把人标到另一个地方。

## 二、采集坐标：把「没授权」和「取不到」分开

实现在 `im-ui/src/utils/location.js`，只有一个对外函数 `requestLocation(options)`。

### 2.1 权限态决定超时档位

`navigator.geolocation` 的 `timeout` 是**从调用那一刻**开始计时的，它把「用户在授权弹窗上
思考的那几十秒」也算进去。原先固定 8 秒，于是首次定位几乎必然先超时：界面报失败，
而用户随后点了允许、位置其实到手了；再点一次因为权限已授出且 `maximumAge` 命中缓存立刻成功
——表现就是「失败了但其实成功，必须再点一次」。

修法是先查 Permissions API，按权限态分档：

| 权限态 | 超时 | 理由 |
|---|---|---|
| `granted` | 15 s | 只剩「设备取不到固定解」这一段，室内 GPS 弱也够 |
| `prompt` | 75 s | 要留出用户读提示、点允许的时间；超时只说明他没点，不代表定位坏了 |
| `unknown` | 75 s | 部分浏览器不允许查 `geolocation` 这一项，一律按「还在问」处理，宁可多等不要误报 |

另外自己兜一个 `timeout + 2000` 的计时器：部分 WebView 在页面隐藏时把回调整个挂起，
一次都不回来，没有这个兜底按钮会永远停在 loading。

### 2.2 三种「取不到」各说各的话

`requestLocation` **永远 resolve，不抛异常**——调用点是「顺手带出坐标」这种增强，
失败要在原地出一句能看懂的话，而不是把一次保存资料整个打断。

| 情况 | 判据 | 给用户的文案 |
|---|---|---|
| 浏览器没这个 API | `!navigator.geolocation` | 当前浏览器不支持定位，可先只填城市 |
| 非安全上下文 | `window.isSecureContext === false` | 当前页面不是 HTTPS（localhost 除外），浏览器已禁用定位 |
| 拒授权 | `err.code === 1` | 定位权限被拒，请在地址栏站点设置里允许后重试 |
| 取不到固定解 | `err.code === 2` | 设备暂时取不到位置（室内 GPS 弱或未开定位服务） |
| 超时 | `err.code === 3` | 按权限态分两句：还在等点允许 / 多半是室内信号弱 |

★ 非安全上下文这一条**重试没有意义**：`http://` 且非 localhost 时浏览器直接回
`PERMISSION_DENIED`，与用户有没有点允许无关。所以它在进 `getCurrentPosition` 之前就短路返回，
文案直接告诉用户换 https 或用本机 localhost 打开。

### 2.3 精度与后端同口径

采集到的坐标先 `toFixed(6)` 再传：库里是 `DECIMAL(10,6)`（约 0.1 m），
多出来的小数位在存库时会被截掉，不如一开始就别传。`accuracy`（系统给的精度圈，米）
一并回传但**不落库**——它只用于日志与调试判断。

### 2.4 定位本身不发网络请求

这是最常被当成 bug 报上来的一条：`navigator.geolocation` 走的是操作系统/浏览器的位置服务，
网页只接一个回调，Network 面板里干干净净是**预期**。真要有请求，是第四节
「坐标 → 省市县」那一步去拉行政区划边界。至于这个点究竟是怎么算出来的，见下面 2.5、2.6 两节。

### 2.5 三信号源：浏览器凭什么知道你在哪

一句话——**不是浏览器算出来的，是操作系统给的，浏览器只是转交**。网页调 `getCurrentPosition`
时拿到的是 OS 位置服务**融合完的结果**，一个点加一个精度圈，中间过程对网页不可见。
OS 手上通常有四类料，谁快用谁、谁准信谁：

| 信号源 | 典型精度 | 首次耗时 | 谁能用 | 说明 |
|---|---|---|---|---|
| GNSS（GPS/北斗/GLONASS） | 5 ~ 20 m | 冷启动可上 30 s | 手机、带 GPS 模块的笔电 | 室内基本失效；桌面浏览器多数根本没这硬件 |
| Wi-Fi 指纹 | 20 ~ 200 m | 亚秒 | 几乎所有联网设备 | **室内主力**。靠「路由器 BSSID ↔ 坐标」的云端数据库反查，Chrome 用 Google 那张库、Firefox 用 Mozilla 的 Ichnaea、国内浏览器与系统多走厂商自建库 |
| 蜂窝基站 | 几百 m ~ 公里级 | 亚秒 | 手机/有基带的设备 | 只知小区扇区，城市里能到几百米，郊县就是公里级 |
| IP 地理库 | 城市级 | 亚秒 | 任何设备 | 本系统**刻意不用**（理由见 §十.10：城市级都常错，错坐标会同时污染附近的人与资料卡距离） |

★ 关键认知：网页无法指定「用 GPS 不要用 WiFi」，也拿不到原始信号。所以「精度」这件事
在浏览器侧只能**采信系统报的 `accuracy`**，我们不做「精度圈太大就拒绝」的策略（§十.9）。

### 2.6 API 形态：只调一次采集，三个入口传参不同

本模块只用 `getCurrentPosition`，**全仓没有 `watchPosition`**（0 命中）：三个入口的语义都是
「点一下要一个点」，持续跟踪要额外处理权限吊销、后台节流、页面卸载清理，而换来的收益
只有「实时移动」——可我们的采信期是 7 天，压根不关心这一秒在动。

`getCurrentPosition` 的第三个参数只有三项，逐项都有坑：

| 选项 | 本系统的值 | 坑在哪 |
|---|---|---|
| `enableHighAccuracy` | 交友两个入口默认 `false`，发位置消息传 `true` | 名字叫「高精度」，实际语义是**要求用 GNSS 这类精确源、别拿 WiFi 快解糊弄**。室内开了反而更容易超时，所以只在「用户明确要发当前位置」时才要 |
| `timeout` | 按权限态分 15 s / 75 s（§2.1） | 从**调用那一刻**起算，包含用户盯着授权弹窗的时间 |
| `maximumAge` | 默认 60 s，发位置传 0 | 允许复用系统缓存的位置。60 s 让「重开页面不必再催一次 GPS」；发位置要的是此刻，所以置 0 强要新解 |

三个采集入口的传参对照（同一个函数，两种诉求）：

| 入口 | 传参 | 为什么 |
|---|---|---|
| `Profile.vue#locateMe` | 无参（非高精度 + 60 s 缓存） | 只为落一个「大概在哪儿」的点，快、少打扰优先 |
| `Discover.vue#locateForNearby` | 无参 | 同上，半径最小也还有 500 m |
| `ChatWindow.vue#useMyLocation` | `{ highAccuracy: true, maxAgeMs: 0 }` | 这是要发给别人的具体地址，差一条街就是错的 |

成功回调拿到的 `coords` 其实有七个字段，本系统只取三个：

```
longitude / latitude  → 取，toFixed(6) 后传后端（§2.3）
accuracy              → 取，Math.round 后只用于日志与调试，不落库
altitude / altitudeAccuracy → 不取：WiFi 与基站定位下多半是 null
heading / speed       → 不取：单次快照语义下无意义，且同样常为 null
```

失败回调的 `err.code` 只有三个值，映射见 §2.2 那张表（1 拒授权 / 2 取不到固定解 / 3 超时）。
★ 注意 1 号码**不只有「用户点了拒绝」会命中**：站点策略、无痕模式、内网浏览器组策略
直接拦掉时也回 1，所以那句文案写的是「请在地址栏的站点设置里允许后重试」而不是「你拒绝了」。

Permissions API 那一查（`navigator.permissions.query({ name: 'geolocation' })`）
**只读状态、不弹窗、不会触发授权**，`state` 取 `granted / prompt / denied`，查不到时按
`unknown` 处理。授权是站点级且持久的，用户点过一次允许后浏览器就不再问——这也是
「第二次点立刻就成」的另一个原因（权限已授 + `maximumAge` 命中缓存）。

★ 桌面 EXE 同样走 OS 位置服务，不因为套了 Electron 就自己有定位能力。Windows 上
「设置 → 隐私 → 定位 → 定位服务」这个总开关被关掉时，`getCurrentPosition` 会恒定回 `code=2`，
代码怎么改都没用——报障「桌面端定位一直失败」先查这个开关，再查代码。

## 三、落库：四列与一个只在服务端算的 geohash

写入收口在 `DatingProfileServiceImpl#applyLocation`，只认 `PUT /api/dating/profile` 这一个入口。

### 3.1 四列一起写

```sql
lng            DECIMAL(10,6)   -- 经度 WGS84，-180~180
lat            DECIMAL(10,6)   -- 纬度 WGS84，-90~90
geohash        VARCHAR(12)     -- 实际只存 6 位，约 ±0.6 km
location_time  DATETIME        -- 采信期的唯一判据
KEY idx_geohash (geohash)      -- 附近的人靠前缀检索，没这个索引就是全表扫
```

★ **geohash 只由服务端算，不接受前端传值**：它必须与坐标同源。两边各算一次迟早会对不上
（前端库版本差一位、精度截断方式不同都够），而对不上的表现是「本人永远刷不到自己附近的人」
——不报错、不掉日志，是最费劲的一类问题。前端传 geohash 一律忽略。

经纬度**必须成对**出现：只给一个直接 400。清零走 `clears: ['location']`，四列一起置 null
（留一半坐标会让采信期判定与 geohash 各自为政）。

### 3.2 定位成功即落库，不等「保存交友资料」

坐标以前只活在前端表单里，不点保存就从不入库；而后端算距离读的是库里那一行，
于是「明明定位了，附近的人还是不行」。现在 `Profile.vue#locateMe` 拿到坐标就单独发一次
`saveDatingProfile({ lng, lat })`，成功后清掉待上报值。

★ 落库回来**只刷定位相关的几个字段**（`applyLocationFields`：`hasLocation` /
`locationFresh` / `locationText` / `profileScore` / `missingTips`），不走整表回填
`fillDating(vo)`——那会把用户正在改、还没保存的生日与城市按库里旧值覆盖回去，
界面凭空吞掉几次输入。

三个名字（`province / city / district`）刻意**不跟着自动落库**：坐标是定位成功即存
（那是附近的人的前提），但出差在外点一下定位不该静默改掉家里城市，那会直接改变同城匹配结果。
所以第四节只填 UI 并提示「确认无误后点保存写库」。

### 3.3 后端不回坐标，只回三个展示字段

`DatingProfileVO` 里与定位有关的对外字段是 `hasLocation`（采集过没有）、
`locationFresh`（还在 7 天内吗）、`locationText`（城市级展示文本），**没有 lng/lat**。
前端只拿它们决定「已定位 / 定位已超过 7 天，建议重新采集 / 还没采集过定位」这三句提示。
本人视角尚且如此，陌生人视角连这三个字段都没有。

## 四、坐标换算省市县三级

实现在 `im-ui/src/utils/regionLookup.js`，由 `Profile.vue#fillRegionByCoords` 在定位成功后调用。
它与距离计算无关，但同一次定位触发，故一并记在这里。

### 4.1 三步走 + 一档兜底

| 步 | 数据源 | 请求 | 判定方式 |
|---|---|---|---|
| 省 | 随包 `data/provinceCenters.js` | 零 | 外包框命中，同步返回 |
| 市 | 阿里云 DataV `{省码}0000_full.json` | 1 次 | 射线法判点在多边形内（只取每个面的外环） |
| 区县 | DataV `{市码}0000_full.json` | 1 次 | 同上；直辖市那份给的就是区，一次到底 |
| 兜底 | 随包 `data/regionCenters.js`（3181 条） | 零（动态 import） | 外包框筛候选 → 中心点最近 |

不把全国边界打进包：几 MB 的东西为「给一个输入框预填」撑大首屏不值得。
省级那份小表随包，所以**点完定位框里立刻能出现「广东省」**，市与区县等公网回来再补
（`locateMe` 里因此是「先起反查、再落库坐标、最后 await 反查」的顺序）。

base 可用 `VITE_REGION_BOUNDARY_BASE` 换成自建镜像。

### 4.2 三档分开降级，每次失败只少填一档

★ 三条铁律：

1. **每次失败只降级成「少填一档」，绝不丢掉已拿到的坐标**；
2. 判不准时退到最近中心点并打 `approximate`，界面说明「这是推断的」——宁可标注也不假装精确；
3. **境外坐标直说「不在国内行政区划范围内」而不硬猜一个国内地址**（给境外用户回填一个
   国内地址比让他手选更坑）。

「只填到省」曾有三条并存真因，各修各的：

| 真因 | 修法 |
|---|---|
| DataV 单次 6 s 无重试，手机上 DNS + TLS + 200 KB 容易吃满 | 超时提到 10 s，且**只对超时/断网/5xx 重试一次**；404 不重试（省直辖县级市、兵团各市本来就没有下级文件） |
| 内网 / EXE / APK 出不去外网 | 随包中心点表兜底，按「外包框筛候选 → 中心点最近」推断市与区县 |
| DataV 的行政区划比随包字典旧（撤县设区换了码，它发 320602 崇川区而字典里已是 320613） | 编码对不上时**按名字在同一父下找**（`codeByName`）——名字比编码稳 |

中心点表是**动态 `import()`** 的，只有真走兜底那条路才加载，Rollup 因此切出独立 chunk，
首屏包不受影响。代价是：DevTools 切 Offline 且该 chunk 从未被浏览器缓存过时，
动态 import 也会失败，此时退回「只填到省」并如实说明——拉不到兜底表时宁可少填一档，
也不弄崩整个反查。

### 4.3 结果缓存：精确的存，推断的不存

命中结果按约 1 km 网格缓存 30 天（`utils/localCache.js`），所以第二次定位同一个位置
**看不到任何请求**，这是预期。★ 但走中心点表**推断**出来的结果一律不写缓存：
缓存了的话，网络恢复后再定位也拿不到精确结果，一次断网能把错档位钉住一个月。

### 4.4 回填时的两条不覆盖原则

`Profile.vue#applyRegionCodes(codes, note)` 把编码与名字**一起写**
（级联框显示的是编码数组 `regionValue`，而 `onRegionChange` 只写三个名字；
只写一边就是「定位后框里空的、点保存才出现三级」那个 bug）。写之前守两条：

1. **空数组不动**：定位没判出来 ≠ 用户原来填的是错的；
2. **同一个省里档数变少也不动**：只判到省，不能把用户已经填好的市/区抹掉，
   改为提示「定位只判断到「广东省」，已保留原来更细的地区」。

## 五、算距离：球面公式与四档模糊文案

全部收在 `im-common` 的 `GeoUtil` 一个工具类里。

### 5.1 为什么放在 im-common 而不是 im-user

写侧（保存资料、上报定位）在 `im-user`，读侧（附近的人）在 `im-friend`，
两边必须用**同一套**编码与算法。拆成两份的后果是「自己存的 geohash 自己圈不进去」，
这种问题不报错、只在数据上表现为「附近永远没人」。

### 5.2 haversine 球面距离

`GeoUtil#distanceMeters(lng1, lat1, lng2, lat2)` 返回米，地球平均半径取 6371000 m：

```
a = sin²(Δlat/2) + cos(lat1)·cos(lat2)·sin²(Δlng/2)
d = 2R · atan2(√a, √(1−a))
```

★ **不用 MySQL 空间函数**：候选池已由 geohash 前缀在索引里圈到几百行，
精确距离在内存里对这几百行现算即可；把计算下推给数据库只是多一次函数调用与更难排查的 SQL。

`GeoUtil#isValid` 刻意不把 `(0,0)` 当合法值：它是数据库默认值最常见的落点，位于大西洋，
放进候选池会让所有沿海用户都看到一个在非洲湾里的人。

### 5.3 geohash 编码

`GeoUtil#geohash(lng, lat, precision)` 是标准实现：base32 字母表（去掉 `i/l/o/u`
以免与 `1/0` 混淆），每字符 5 位，经度位与纬度位从经度开始逐位交错。默认精度 6 位（约 ±0.6 km）
——正好是「附近」的粒度；更长的前缀会把人圈到某栋楼，那是跟踪不是找对象。

★ 这段位运算改过之后必须重新对一遍三个公开参照点：`(116.4074, 39.9042) → wx4g0b`、
`(121.4737, 31.2304) → wtw3sj`、`(120.1551, 30.2741) → wtmknp`。
编错的 geohash 不会报错，只会让人永远刷不到附近的人。

### 5.4 四档模糊文案

`GeoUtil#fuzzyDistance(meters)` 是同城社交展示用的**唯一出口**：

| 实际距离 | 对外文案 | 为什么 |
|---|---|---|
| < 500 m | `500 m 内` | 近到这一档，精确数字等于报出「我们在同一间咖啡店」 |
| < 1 km | `1 km 内` | 同上，步行可达的距离没有区分意义 |
| < 100 km | `N km`（取整公里） | 这一档要能看出远近，但不必精确到百米 |
| ≥ 100 km | `100 km 以上` | 再远就只是「不在同城」，数字已无意义 |

传入负数或 null 返回 `null`，由调用方决定这一行是否展示。
`GeoUtil#fuzzyDistanceBetween` 把「先算再模糊」两步包在一起，调用方不必自己拼——
这一步走错（把精确米数丢给前端）是本模块最贵的错误。

★ **距离模糊化是展示口径而不是存储口径**：`lng/lat` 全精度存，服务端算完真实距离再收口。
直接把坐标给前端，等于把「某人每天几点在哪」交给每一个刷到他的人，
这不是一个隐私开关能补救的。

## 六、能不能给你看：两道门与一个收口方法

### 6.1 收口在实体方法上

规则本体是 `UserProfile#distanceTextFrom(viewer)`，**四个条件全满足**才给文案，
任一不满足返回 `null`：

```java
if (viewer == null || !distanceVisible() || !viewer.hasFreshLocation() || !hasFreshLocation()) {
    return null;
}
return GeoUtil.fuzzyDistanceBetween(viewer.lng, viewer.lat, this.lng, this.lat);
```

（上面省了 getter 与 `BigDecimal` → `double` 的 `toDouble` 转换，只为把四个条件的顺序看清楚；
坐标列在库里是 `DECIMAL`，实体上是 `BigDecimal`，算距离前必须转一次。）

放在实体上而不是服务层：资料卡（`DatingProfileServiceImpl`）与交友卡池
（`DatingQuerySpiImpl`）两处都要这一句，写两份就会出现「同一个人在自己资料页与
别人的卡池里距离口径不一致」。

### 6.2 门 1：对方的 `show_distance`

`distanceVisible()` 读的是**被查看者**那一行的开关，判定是 `flag != null && flag == 1`
——列为 NULL 按**不显示**（隐私位宁可少给，不可多给）。DDL 上是 `NOT NULL DEFAULT 1`，
所以真从库里读出的行不会是 NULL；这个保守口径针对的是 `getOrCreate` 返回的、
还没落库的内存对象。

★ 关掉距离**只影响展示，不影响排序**：这个人仍会出现在「附近的人」列表里，
只是不给公里数（DDL 注释即此意）。

### 6.3 门 2：双方都在 7 天采信期内

`hasFreshLocation()` = `location_time` 非空且晚于 `now - 7 天`，且 `lng/lat` 都非空。
常量是 `UserProfile.LOCATION_VALID_DAYS = 7`。

为什么双方都要查：距离是**相对量**，我三个月前在北京、对方今天在上海，
算出来的公里数是一句谎话。旧坐标会把人说成在别处，比不给距离更糟。

前端把 `LOCATION_VALID_DAYS` 抄了一份常量只为写清提示文案，★ 改后端这个值时必须同步改前端。

### 6.4 前端把「为什么没有」说出来

以前条件不满足时界面什么也不说，用户只能反复重定位。现在 `Profile.vue` 的定位行下方
按优先级出四句提示之一：

| 界面状态 | 提示 |
|---|---|
| 正在取位置 | 正在取位置；浏览器弹窗里点「允许」后会自动继续 |
| 从没采集过 | 定位一次即可：坐标当场入库，附近的人与资料卡距离立刻生效 |
| 开关关着（黄色） | 「显示距离」这个开关是关的，别人的资料卡上看不到公里数；打开后仍需双方在 7 天内都定位过 |
| 采集失败（黄色） | 按 §2.2 那张表给具体原因 |

★ **要用户自己猜的原因等于没有原因**。别人侧仍只给模糊档位，响应 JSON 与页面源码里
不得出现经纬度（这是手验清单 §18.4.3 的硬检查项）。

## 七、附近的人：粗筛与精排

读侧在 `im-friend` 的 `NearbyServiceImpl#nearby`，坐标与排序在 `im-user` 的
`DatingQuerySpiImpl#nearbyIds`——★ **im-friend 只传半径，不传坐标**（星型架构不互读表）。

### 7.1 半径的三级取值

`NearbyServiceImpl#radiusOf`：请求参数 > 偏好里的 `distance_km` > 出厂默认 3000 m，
最后夹进 `[500, 20000]`。

单位换算与兜底放在这里而不是 `applyTo` 里：偏好存的是公里且「不限」为 0，
而半径的默认值属于「附近的人」这一个入口，不是全局筛选条件。
`applyTo` 只填没显式给过的字段，所以显式传的半径不会被偏好抢掉，
而调用方没提的那些条件（年龄/城市/性别…）才是从偏好来的。

前端下拉六档与后端区间一致：500 米 / 1 公里 / 3 公里 / 5 公里 / 10 公里 / 20 公里。
再远就不是「附近」而是同城筛选，那一档属于按 `city` 包含匹配的推荐流。
★ 前端**永远把下拉框的值传过去**（下拉框就在眼前，让它说了算才是所见即所得），
偏好兜底改在「把下拉框预选成偏好的值」这一步做；两个例外：对不上可选档的偏好值
（比如存了 7 km）就不动，宁可按默认 3 km 展也不往一个空下拉框里塞选项外的值；
而用户**手动改过下拉框**（`nearbyRadiusTouched`）之后就不再拿偏好去抢他的选择。

### 7.2 geohash 前缀档位

| 半径 | 前缀位数 | 格子大小 |
|---|---|---|
| ≤ 1000 m | 5 位 | 约 4.9 × 4.9 km |
| > 1000 m | 4 位 | 约 39 × 19.6 km |

★ **格子必须比半径宽一档**，否则跨在格子边界上的人会被漏掉。
不扩展 8 邻居是因为：邻居需要 geohash 解码能力，而误差已被「取粗一档」吸收到大半，
用户看到的又只是一句「3 km 内」。粗筛多圈进来的行会在下一步按精确距离滤掉。

### 7.3 SQL 粗筛

`UserProfileMapper#nearbyPool(geohashPrefix, query)`：

```
likeRight(geohash, prefix)                                  -- 走 idx_geohash
  AND location_time >= now() - 7 天                          -- 采信期
  AND baseWrapper(query)：discoverable = 1（排除隐身）
                        AND user_id <> viewerId（排除自己）
                        AND user_id NOT IN excludeIds（附近的人只放拉黑名单）
  AND applyFilters(query) 的筛选条件（年龄/城市/学历/身高…）
ORDER BY location_time DESC
LIMIT 500
```

★ 账号状态（封禁/注销）**不在这一层 SQL 里**，而是排完序取前几倍之后由
`aliveInOrder` 批量校（见 §7.4）。`discoverable` 是「隐身」，与 `show_distance`
不是一回事：前者是整个人不被陌生人刷到，后者只是不给公里数。

两个刻意的选择（第三个「不看 `sortBy`」见 §7.5）：

- **不在 SQL 里按距离排序**：精确距离要把坐标取回内存逐行算，MySQL 这一侧只负责
  把「可能是附近的」缩小到几百行。
- **预排 `location_time DESC` 而不是分数倒序**：一个 90 分但三个月前定位的人实际上不会在附近，
  让这种行占满 500 行扫描窗口，会让真正在附近的人一个都进不来。
  不封顶就会在热门城市里捞回几千行再全部丢掉。

### 7.4 内存精排与状态探针

```
逐行 haversine → 只留 meters <= radius → 按 (米数, userId) 升序
   → 取前 limit × 3 个 → 校账号状态 → aliveInOrder 保序返回
```

- 排序键带上 `userId` 是为了**稳定**：同距的人不能每次刷新换序。
- 多取 3 倍（`NEARBY_STATUS_PROBE`）再校状态，是为了不让「查了 20 个有 3 个被封」
  直接把列表砍成 17 个。
- ★ **先算距离再查账号状态**：候选窗口有 500 行，而一发的 `IN` 查五百个 ID 是白花销；
  排完序只取前几倍去校状态，既不漏近处的人也不把批量查拖大。

### 7.5 刻意忽略 sortBy 与 onlineFirst

这一栏的顺序**永远是离我最近**。偏好里的排序口径是给推荐流用的，
把一个每秒变化的在线态排进这一栏，用户得到的就是一个刷一次换一次序的列表。
筛选条件照旧生效，只有顺序不让步。

与卡池的另两处不同：

- 附近的人**只排拉黑，不排已划过与已配对**（卡池排三类）——「附近」是一个地理事实，
  不该因为我划走过谁就把他从地图上抹掉。
- **不排低质号**：`excludeLowQuality` 只有推荐流（`MatchServiceImpl`）传 true，
  附近的人不传，所以 `quality_flag = 低质` 的人在这一栏照旧可见——降权是不主动推给你，
  不是把人从地图上抹掉。

### 7.6 两种空态是两句话

| 情况 | 判据 | 前端表现 |
|---|---|---|
| 你自己没法按距离找人 | `locationReady()` 为假 → **2042** `DATING_LOCATION_REQUIRED` | 空态「你还不能按距离找人」+「立即定位」「去资料页」两个按钮 |
| 真的附近没人 | 池子空 → 200 + 空数组 | 空态「这个范围里暂时没人」+「放大范围」（直接跳下一档，不让人去下拉框里找） |

★ 2042 在这一栏**不是一次失败而是一个要原地出引导的正常状态**，所以请求带 `silent`：
弹全局红条会对同一个问题再说第二遍。其它错误因为没被静默，照旧补上弹条。

★ 空态里那个「立即定位」有**自己一个 loading 位**（`nearbyLocating`），与拉列表的
`nearbyLoading` 分开：两者同时转会把文案遮掉。

★ 顺序是**先查自己的定位，再查池子**：反过来的话，一个没定位的用户每翻一次附近的人
都要白扫一遍 `im_user_profile` 才收到 2042。

`locationReady` 与 `hasFreshLocation` 是同一口径，所以「定位超 7 天」也会落到 2042 这一档，
空态文案因此写的是「定位一次就能用（超过 7 天会自动失效）」而不是「去开启定位」。

## 十、边界与已知局限

诚实清单，都是已知且刻意接受的：

1. **geohash 格子边界漏人**：粗筛只取同一个前缀格子，不扩 8 邻居。
   贴着格子边界的人（例如我在格子西南角、对方在东北角外 200 m）会被漏掉。
   接受理由：邻居需要 geohash 解码能力，而「前缀取粗一档」已吸收大半误差，
   用户看到的又只是一句模糊文案。
2. **附近的人一次最多扫 500 行**：热门城市中心区可能扫满了还漏掉更近的人。
   预排 `location_time DESC` 缓解（近期定位的优先进窗口），但没有根治。
3. **距离是两点直线距离**：不是通勤距离，跨江跨山时「3 km」可能意味着 40 分钟。
4. **`show_distance` 关了仍参与排序**：这个人会出现在附近的人列表里，只是不给公里数。
   这是刻意的（隐身用 `discoverable`，不用距离开关），但用户可能误以为关掉就找不到了。
5. **同城筛选是单向兼容**：`wrapper.like(city, ...)` 包含匹配，
   存「深圳市」能被筛词「深圳」命中，存「深圳」却被筛词「深圳市」漏掉。
   所以老的手填数据重存一次对齐字典是有意义的。
6. **坐标反查依赖公网 DataV**：内网/断网时退到随包中心点表（3181 条），
   精度是「哪个区县中心点最近」而不是「点落在哪个多边形里」。
   字典缺位的区县（主要是台湾、两江新区这类新设单位、兵团新设市）兜不出来。
7. **DataV 的行政区划比随包字典旧**：撤县设区换了码的区县靠名字兜回来；
   名字也变了的（极少数）会只填到市。换字典后要重跑 `node scripts/gen-region-centers.mjs`。
8. **`(0,0)` 被当成非法坐标**：真有用户位于几内亚湾的浮标上会被判为未定位。
   接受理由：它是数据库默认值最常见的落点，放行的代价远大。
9. **定位精度圈 `accuracy` 不参与判定**：系统报「精度 3000 m」时我们照样采信这个点。
   目前只用于调试，没有做「精度太差就拒绝」的策略。
10. **没有 IP 定位兜底**：拒绝授权就是没有坐标，不会用 IP 猜一个城市写进 `lng/lat`。
    IP 定位在城市级都常错，而错坐标会同时污染附近的人与资料卡距离。

## 十一、位置消息：站内瓦片渲染与第三方导航拼接

本章只讲 `ChatWindow.vue` 那一支（§一 里点名的「假同类」）：一个经纬度到手后，
怎么变成聊天里那张地图卡片，又怎么拼成高德/百度/谷歌的跳转链接。**全程零 SDK、零密钥、零后端参与**。

### 11.1 一条链，两个出口

```
采集  requestLocation({ highAccuracy: true, maxAgeMs: 0 })   或 用户手填经纬度
         │  （两个入口都在位置对话框里，填回输入框而不是直接发，可手改）
         ▼
存储  chat.send({ msgType: 8, content: 地点名,
         extra: { locationName, latitude, longitude } })
         │  ★ 坐标只存在消息表的 extra JSON 里，服务端不生成任何地图图片
         ▼
出口 A（站内看图） MessageBubble.vue → tileUrl(lat, lng) → <img> 一张瓦片
出口 B（导航去）  emit('open-location') → ChatWindow → externalMapUrl() → 新标签页
```

位置消息的类型号是 **8**（7 是名片，易记错），会话列表里的预览文本是 `[位置] 地点名`。
卡片上三样东西：地图缩略图 + `📍` 标注 + 两行文字（`locationName` 与 `formatCoord` 的六位小数坐标）。

### 11.2 站内缩略图：经纬度 → 瓦片地址

地图是一堆 256×256 的 PNG 方格按行列切的，编号规则是 `(z, x, y)`：`z` 是缩放级，
该级下全网共 `2^z × 2^z` 张。`tileUrl()` 就是算出「这个点落在哪一张上」：

```javascript
const n = 2 ** zoom
// 经度是线性的：-180 → 0，+180 → n
const x = Math.floor(((lng + 180) / 360) * n)
// 纬度不是线性的（Web Mercator 投影在高纬度拉伸），要过一道墨卡托公式
const latRad = lat * Math.PI / 180
const y = Math.floor(((1 - Math.log(Math.tan(latRad) + 1 / Math.cos(latRad)) / Math.PI) / 2) * n)
// 越界钳制，避免 NaN 或负号把 URL 拼坏
return TEMPLATE.replace('{z}', zoom).replace('{x}', cx).replace('{y}', cy)
```

拿几个真值对一遍（可直接拿去跟 DevTools 里 `<img>` 的 src 对）：

| 坐标（WGS-84） | zoom=15 的瓦片号 | 完整地址 |
|---|---|---|
| 杭州西溪 `30.2741, 120.1551` | `15/27320/13490` | `https://tile.openstreetmap.org/15/27320/13490.png` |
| 北京 `39.9042, 116.4074` | `15/26979/12416` | 同上模板 |
| 上海 `31.2304, 121.4737` | `15/27440/13389` | 同上模板 |

几个要点：

- **默认模板是 OSM 公共瓦片**（`tile.openstreetmap.org`），免密钥免申请；可用
  `VITE_TILE_TEMPLATE` 整段替换成高德/Google 等带密钥源，形如
  `https://.../{z}/{x}/{y}.png?key=xxx`——所以「三个占位符的模板」是本函数唯一的约定。
- **只用一张瓦片**（没拼 3×3 九宫格），z=15 下单张 256px 在地面尺度上约覆盖 1 km 见方，
  对「一眼看出在哪个片区」够用；再细一级就要拼图，不值得。
- ★ **卡片上的 `📍` 是示意不是精确位置**，两处误差叠在一起：取整拿到的是「包含该点的
  那一格」，点未必在格中心；而 CSS 把 pin 钉在容器几何中心（`left/top: 50%`），
  容器又只有 220×110 且 `object-fit: cover` 把方瓦片裁成了横条。要把位置看准就点开 11.3 的外部地图。
- ★ 兜底只兜「没坐标」：`hasCoord` 用 `Number.isFinite` 判，不成立才渲染「地图不可用」占位。
  **坐标有但瓦片拉不到（内网、OSM 不可达）时不报错，就是一张破图/灰底**——因为坐标在手，
  点开外部地图仍然能看到真实位置，卡片里那张图只是个预告。

### 11.3 第三方导航拼接（三家逐参数）

这是免密钥的：`uri.amap.com` 与 `api.map.baidu.com` 走的是各家 **URI API**（开放跳转协议），
只负责「把你的参数变成一个带标注的页面」，不返回数据——需要申请 key、算配额、做签名的是
另一类（Web 服务 API 与 JS API），这里一概用不到。三家均收 WGS-84 原始坐标 + 声明源坐标系，转换在对方服务端做。

**高德**（经度在前）

```
https://uri.amap.com/marker
  ?position=120.1551,30.2741      ← 经度,纬度（★ 与百度相反）
  &name=%E8%A5%BF%E6%BA%AA%E6%B9%BF%E5%9C%B0   ← 标注标题，encodeURIComponent
  &src=im                          ← 来源标识，高德这边选填
  &coordinate=wgs84                ← ★ 声明我给的坐标是 WGS-84，由高德服务端转 GCJ-02
  &callnative=0                    ← 0 = 留在浏览器；1 = 拉起高德 App
```

**百度**（纬度在前）

```
https://api.map.baidu.com/marker
  ?location=30.2741,120.1551      ← 纬度,经度（★ 与高德相反）
  &title=%E8%A5%BF%E6%BA%AA%E6%B9%BF%E5%9C%B0  ← ★ 必选
  &content=30.274100%2C%20120.155100          ← ★ 必选，这里放坐标原文供对方页面核对
  &output=html                      ← ★ 必选，给 H5 页而不是 App  scheme
  &coord_type=wgs84                 ← ★ 声明源坐标系，由百度服务端转 BD-09
  &src=webapp.im.location           ← ★ 必选，格式限定 webapp.公司.应用，不传不保证服务
```

**谷歌**（本来就吃 WGS-84，无需声明）

```
https://www.google.com/maps?q=30.2741,120.1551
```

三条容易踩的坑，都是**不报错只出错**型的：

1. **经纬度顺序两家是反的**（高德 `position` 经度在前、百度 `location` 纬度在前）。
   弄反了链接照样打开，只是把人标到另一个地方——国内常见的是丢到非洲或海里。
2. **忘了声明坐标系**（漏 `coordinate` / `coord_type`）：对方默认你给的已经是它自己的坐标，
   于是 GCJ-02 被当 WGS-84 用，偏移几十到几百米，**越往西偏越多**。
3. **名字没 `encodeURIComponent`**：地点名带空格、`&`、`#` 就把 query 拼断了，
   而中文在部分浏览器里看起来正常，测试很容易漏。

★ 谷歌那条刻意**不带 `name`**：`q=` 里塞标签是另一种未文档化的写法，而 `?q=纬度,经度`
是本功能一直在用、已验证可用的链接形态，不为「更规范」去换它。所以
`MAP_PROVIDERS` 里 google 的 `build` 只接两个参数——文档里写明了「谷歌那家忽略 name」。

改这三条模板后的验证办法：固定一组坐标（比如上面的 `30.2741, 120.1551`）把三条 URL
打印出来逐字符对官方文档，再各自打开一次看针尖落点——只测「能打开」测不出偏移。

### 11.4 选哪家：三态与两处顺序细节

`MAP_PROVIDERS` 数组就是弹窗里的展示顺序（国内两家在前）。`key` 会存进设置项
`mapProvider`，★ **改 key 等于让所有人已记住的选择失效**，别随手改。

| `mapProvider` | 行为 |
|---|---|
| `''`（出厂默认） | 每次点卡片都弹选择框 |
| `amap` / `baidu` / `google` | 直接开那家，不再问 |
| 非法值（手工改坏了、旧版本残留） | 不报错，`resolveMapProvider` 退回清单第一项（高德） |

两处顺序细节：

1. `chooseMap()` 是**先开页再写设置**。写在前面的话，万一 `window.open` 被拦，
   用户就被钉在一个根本没打开的选择上，下次连弹窗都没了。
2. 三处调用（弹窗选、记住后直开、设置里改完再试）都走同一个 `openInMap()`，
   保证「记住」与「每次问」两条路开出来的是**同一个 URL**。

偏好只存在本机（`stores/settings.js`），**不建后端表也不同步**：这是设备相关的环境
（手机上装了高德却未必打得开谷歌），丢到云上反而错。设置页「位置消息默认地图」那个下拉的
「每次询问」对应 `''`，与聊天窗里勾「记住我的选择」写的是同一个字段。

### 11.5 这一支不参与任何距离计算

重申一遍（§一 已标）：位置消息写的是消息表 `extra`，**不碰 `im_user_profile`**，
既不参与「附近的人」也不参与资料卡距离。它与交友定位共用的只有
`requestLocation()` 这一个采集函数（为了复用 §2.1 那套授权等待口径），传参并不共用
（见 §2.6 对照表）。查「为什么定位了却没有距离」时别把它算进去。
