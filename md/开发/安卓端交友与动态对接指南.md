## 一、开工前先认清的三件事

### 1.1 `im-android` 不是空工程，缺的只是交友域

工程里已经有一套**跑通了的**原生客户端（`versionCode 6` / `versionName "0.1.5"`，包名
`com.im.nativeapp`，Kotlin + Jetpack Compose + Hilt + Retrofit + kotlinx-serialization + OkHttp）。
`core/network/` 下已有 `ApiClient` / `AuthApi` / `Dtos`(395 行) / `ImApis`(265 行) / `Models` / `TlsCompat`，
`data/` 下已有 5 个 Repository 和 `WsDispatcher`，`ui/` 下已有 13 个包（其中
`theme` / `components` / `debug` 不是页面）。

所以这份文档的定位不是「从零对接」，而是**在既有工程上补最后一块**：
写 `DatingApi` / `MomentApi` + 交友域 DTO + `DatingRepository` + `ui/dating/`，并在 `WsDispatcher` 里加一个分支。

| 板块 | im-android 现状 |
| --- | --- |
| 登录 / 续期 / 扫码确认 | 已有 `AuthApi`（6 个端点 + 二维码 2 个） |
| 会话 / 消息 / 已读撤回 | 已有 `ConversationApi` `MessageApi` + Room 缓存 |
| 好友 / 群 / 文件上传 / 通话信令 / 直播 / AI | 已有 |
| WebSocket 长连 + 心跳 + 重连 | 已有 `ImWebSocket`，协议与 `im-ui/src/ws/socket.js` 对齐 |
| **资料卡 / 照片墙 / 标签 / 破冰** | **完全没有** |
| **滑动匹配 / 偏好 / 附近的人 / 访客 / 亲密度** | **完全没有** |
| **动态 Feed（发布、点赞、评论、转发、可见范围）** | **完全没有** |
| **权限位判断** | **完全没有**（`im-android` 内搜 `permissions` 零命中，见第十四节） |

### 1.2 后端不会为安卓改任何东西

后端接口是 Web 端、小程序端、管理台、安卓共用的一套。安卓侧遇到的所有奇怪行为（同一字段时而数字
时而字符串、失败也是 HTTP 200、`total` 是纯数字、`clears` 拼错字段名报错而不是忽略）
都是**已定的设计**，改不了，只能按本文适配。

### 1.3 整个交友域只有一条 WebSocket 推送

后端 `WsMessageType` 有 31 个事件，其中和交友相关的**只有一种**：`notify` 帧里
`bizType = "match-success"`（配对成功，推给双方）。

**点赞、评论、访客、喜欢我的、新动态、亲密度升级，全都没有推送**——不是我没找到，是后端确实没写。
安卓端这些一律靠下拉刷新或进入页面时拉取，**不要去找一个不存在的事件名**。

## 三、网络层：照抄现有约定，别发明新写法

### 3.1 服务接口怎么声明

完全照 `ImApis.kt` 的现有写法：**路径不带前导斜杠，也不带 `/api`**（`baseUrl` 已经是
`{服务器}/api/`，由 `SessionStore.apiBase()` 提供，用户在「高级设置」里换环境时会自动跟过去）。

```kotlin
interface DatingApi {
    @GET("dating/profile")
    suspend fun mine(): ApiEnvelope

    @PUT("dating/profile")
    suspend fun saveProfile(@Body body: DatingProfileRequest): ApiEnvelope

    @GET("dating/photos")
    suspend fun photos(@Query("userId") userId: String?): ApiEnvelope

    @DELETE("dating/photos/{id}")
    suspend fun deletePhoto(@Path("id") id: String): ApiEnvelope
}
```

一律返回 `ApiEnvelope`（不是 `Result<T>`、不是泛型），取数据靠 `unwrap`：

```kotlin
val vo: DatingProfileVO = api.mine().unwrap(apiClient.json)
api.deletePhoto(id).unwrapUnit()          // Result<Void> 用这个
val list = api.photos(userId).unwrap<List<UserPhotoVO>>(apiClient.json)
```

`unwrap(json)` 是 `Models.kt` 里已有的内联函数：`code == 200` 就解 `data`，否则抛
`ApiError(code, message, traceId)`；`data` 缺失时抛 `code = -1`。**不要自己判 `resp.success`**。

通过 `ApiClient` 现有的服务缓存拿实例（`apiClient.api()` 拿 `AuthApi`，其余按同样的方式取），
不要 new Retrofit。

### 3.2 数组参数：不要带方括号

Retrofit 对 `@Query("ids") ids: List<Long>` 默认就生成 `ids=1&ids=2`，这是对的。
**千万别写成 `ids[]`**：Spring 的 `@RequestParam List` 认不了带方括号的名字。
Web 端为此专门配了 `paramsSerializer: { indexes: null }`，安卓不需要额外配置，保持默认即可。

### 3.3 鉴权头

`ApiClient` 的 `authInterceptor` 已经做了两件事：加 `X-Trace-Id`（前缀 `android-`）和用
`session.currentTokenName()` 动态取头名。**tokenName 不能写死 `satoken`**——它由后端
`sa-token.token-name` 决定并在登录时下发，`SessionStore.DEFAULT_TOKEN_NAME` 只是本地没记录时的兜底。
交友域沿用同一拦截器，不用做任何事。

### 3.4 自签证书与图片加载

`TlsCompat.install()` 已在 `ApiClient` 构建时调用（生产环境是 IP 直连 + 自签证书）。
照片墙和动态的图要用 `ApiClient.mediaHttpClient` 那个 OkHttpClient 交给 Coil，
这样才带上同一个鉴权拦截器；自己 new 一个 OkHttpClient 会在自签证书上直接失败。

## 四、ID 一律按字符串收（第一大坑）

### 4.1 后端的行为

`im-common/config/JacksonConfig` 里注册的 `SafeLongSerializer` 是**条件序列化**：

- 雪花 ID（19 位，超过 JS 安全整数 `9007199254740991`）→ 输出成**字符串** `"194823748239849472"`；
- `seq`、`fileSize`、`size` 这类小 Long → 仍然是**数字** `123`。

也就是说：**同为 Java `Long` 字段，JSON 里可能是字符串也可能是数字**，取决于数值大小。
kotlinx-serialization 是严格解析，`val userId: Long` 遇到 `"19482..."` 会直接抛异常，
整个列表一屏都出不来。

### 4.2 现成的解法（工程里已经有，直接用）

`core/network/Dtos.kt` 顶部已定义好两个序列化器，注释就写着「对齐后端 JacksonConfig$SafeLongSerializer」：

```kotlin
object IdAsString : KSerializer<String>          // 非空 ID
object IdAsStringNullable : KSerializer<String?> // 可空 ID
```

**交友域所有 ID 字段一律声明成 `String` 并挂这两个序列化器**，跟现有 DTO 一模一样：

```kotlin
@Serializable
data class MatchPairVO(
    @Serializable(IdAsString::class)      val pairId: String = "",
    @Serializable(IdAsString::class)      val peerUserId: String = "",
    @Serializable(IdAsStringNullable::class) val conversationId: String? = null,
    val card: DatingCardDTO? = null
)
```

哪些算 ID：`userId` `peerUserId` `targetUserId` `visitorId` `momentId` `mediaId` `commentId`
`pairId` `likeId` `conversationId` `fileId` `photoId(id)` `tagId` `messageId` `replyUserId`。

### 4.3 唯一的例外：分页对象的四个数字字段

`PageResult<T>` 的 `total` / `current` / `size` / `pages` 在 Java 里是**原始类型 `long`**。
`SafeLongSerializer` 只注册了包装类 `Long.class`，没注册 `Long.TYPE`，所以这四个字段
**永远是数字，永远不会是字符串**。安卓就按 `Long` 收，不要给它们挂 `IdAsString`：

```kotlin
@Serializable
data class PageResult<T>(
    val records: List<T> = emptyList(),
    val total: Long = 0L,      // 数字，不是 ID
    val current: Long = 1L,
    val size: Long = 10L,
    val pages: Long = 0L
)
```

同理 `UserPhotoVO.size`（字节数）也是原始 `long`，按数字收。
拿不准的字段就看它「是不是某个实体的主键或外键」——是 ID 就字符串，是数量/大小就数字。

### 4.4 请求方向：字符串和数字后端都认，一律发字符串

后端 DTO 里的 ID 都是包装类 `Long`，Jackson 对 `Long` 同时接受 `"123"` 和 `123`。
Web 端曾经用 `Number()` 把 19 位 ID 转数字，结果精度掉成 `...400`，导致请求打到一个不存在的 ID 上
并且**后端没有任何日志**。安卓对应的禁令是：**任何 ID 都不要 `toLong()`**，
路径参数、查询参数、请求体、Map 的 value 全部原样传字符串。

## 六、Kotlin DTO 全集

字段名与后端 VO 逐字对齐（`ignoreUnknownKeys = true`，多出来的字段可以不解，但少写一个可空字段
就会在解引用时崩，所以一律给可空 + 默认值）。时间字段是字符串：`LocalDate` 形态 `2000-01-15`，
`LocalDateTime` 形态 `2026-11-27T10:23:45`，展示时自己格式化，**不要用 `Instant.parse` 去解**
（没有时区偏移，会直接抛异常）。

### 6.1 出参 VO

```kotlin
// ====== 资料卡（DatingProfileVO.java 事实源）======
// ★ 不含 nickname / avatar：自己的去 AuthRepository.currentUser 取，别人的去 DatingCardDTO 取
@Serializable
data class DatingProfileVO(
    @Serializable(IdAsString::class) val userId: String = "",
    val self: Boolean? = null,                  // true 表示这是本人视角
    val birthday: String? = null,               // yyyy-MM-dd
    val age: Int? = null,                       // 对方关了「显示年龄」时为 null
    val heightCm: Int? = null,
    val education: Int? = null, val educationDesc: String? = null,
    val occupation: String? = null,
```

## 八、错误码与三种呈现策略

### 8.1 失败也是 HTTP 200

后端全局异常处理器不带 `@ResponseStatus`，**所有业务失败（含未登录）都是 HTTP 200 + Result 体**。
非 2xx 只可能来自传输层（断网、超时、证书、404 路径写错）。

所以安卓的判断链是：`OkHttp 异常` → 网络层提示；`HTTP 非 2xx` → 路径或服务问题；
`HTTP 200 且 code != 200` → 业务错误，**走 `ApiError`，看 `code`**。`unwrap` 已经做了后两步的拆分。
如果按惯例去写 `if (httpCode == 401) 跳登录页`，这段代码永远不会触发。

`ApiError.isAuthError(code)`（`1002` / `2010`）已有，命中就清登录态回登录页，交友域不要吞掉它。

### 8.2 通用码

| code | 后端文案 | 安卓怎么做 |
| --- | --- | --- |
| 1001 | 请求参数有误：{} | 弹后端 message（大括号里是具体原因，如「未知的清空字段：xxx」） |
| 1002 | 登录状态已失效，请重新登录 | 清态跳登录，**不要弹 toast** |
| 1003 | 没有操作权限 | 弹一句「当前账号无此权限」，并把入口按权限隐掉（见第十四节） |
| 1004 | 请求的资源不存在 | 弹 + 刷新列表 |
| 1005 | 请求方法不被支持 | 是我方写错了（GET 写成 POST），进调试日志 |
| 1006 | 业务处理失败：{} | 弹后端 message |
| 1007 | 系统繁忙，请稍后重试 | 弹固定文案 + 重试按钮；**表结构没应用时（新库）就是这一码** |
| 1008 | 参数校验失败：{} | 弹后端 message（Bean Validation 拦的，如「身高需在 100~250 cm 之间」） |
| 1009 | 上传内容超过大小限制 | 上传前自己先按 bizType 限一遍，别等后端 |
| 1010 | 操作过于频繁，请稍后再试 | **限流**，要静默降级（不刷新旧数据、不弹错），第 8.4 条 |

### 8.4 限流要静默

`1010` 意味着用户手速超了上限（如 `deck` 60 次/分、`match/action` 120 次/分）。
**不要把卡片飞回的动画回退，也不要弹一屏红**：丢掉这一次请求，保留已有数据，
30 秒后允许重试。滑动匹配很容易碰限流，这是唯一需要预先想好降级的一处。

## 九、图片与视频：先上传拿 fileId，再提交业务接口

交友域三处要传文件，**bizType 是硬校验的**，错了就报 2027 / 2054。

| 场景 | 上传时的 bizType | 允许的扩展名 | 后续提交到 |
| --- | --- | --- | --- |
| 照片墙 | `dating_photo` | jpg jpeg png gif webp bmp avif jfif | `POST /api/dating/photos` |
| 动态图 | `moment_image` | 同上 | `POST /api/dating/moments` 的 `media[].type=1` |
| 动态视频 | `moment_video` | mp4 avi mov mkv webm flv wmv | 同上，`media[].type=2` |

安卓现有的上传方法就是 `FileApi.upload(file: MultipartBody.Part, bizType: String)`，
只是它的注释里没列这三个新值，补上注释即可：

```kotlin
val part = MultipartBody.Part.createFormData("file", name, requestBody)
val vo: FileVO = api.upload(part, "moment_image").unwrap(apiClient.json)
// 只把 vo.fileId 交给业务接口，不要拿 url 去拼请求体
```

三个要点：

1. **地址一律服务端现拼**。请求体里传 URL 没有任何意义（服务端不采信），反查 `fileId` 才算。
   这是为了防往别人信息流里挂外链（既躲过审核，也躲过「文件已删」）。
2. **`type` 不由服务端从扩展名猜**，但会校验「`type` 与那一行的 `bizType` 对得上」。
   所以图一定要用 `moment_image` 上传，拿 `chat_image` 的 fileId 过来会被拒。
3. **删动态不会删 `im_file` 行**（秒传的字节可能被别处引用）。安卓不需要做任何补偿。

## 十、定位与距离

### 10.1 坐标是安卓取的，后端不做 IP 定位

后端只存不算。取坐标自己负责（建议 `FusedLocationProviderClient`，需要
`ACCESS_FINE_LOCATION`，Android 12+ 还要 `ACCESS_COARSE_LOCATION` 一起申请）。
拿不到就什么也别提交——「没定位」是完全正常的状态，不报错。

**不要开长期后台定位**。交友只需要一个点 + 7 天内有效，用户点「定位」按钮时取一次就够了，
对应用户在资料页看到的「更新我的位置」。

### 10.2 上传方式：只有一个入口

```kotlin
api.saveProfile(DatingProfileRequest(lng = lng, lat = lat, city = city, ...))
```

- **`lng` 与 `lat` 必须成对提供**，只传一个报 `1001 经纬度必须成对提供且在有效范围内`。
  范围：经度 -180~180，纬度 -90~90。
- 服务端会自己算 `geohash`、写 `locationTime = now`。**安卓不传 geohash，也不传「定位时间」**。
- 想清定位：`clears = ["location"]`（会同时清 lat/lng/geohash/locationTime）。
- ★ **没有单独的「上报定位」接口**，不要再开一条写路径：附近的人和卡池是同一个候选池的两种读法。

### 10.3 七天有效期与 2042

`locationTime` 超过 7 天就算失效：`DatingProfileVO.locationFresh = false`，
`GET /nearby` 直接报 **2042**。Web 端的做法是：**拉取失败不弹 toast，而是在列表区域原地
换一段引导文案 + 「去定位」按钮**。安卓照做：

```kotlin
runCatching { nearby(radius, size) }
    .onFailure { if (it is ApiError && it.code == 2042) state = NeedLocation else toast(it) }
```

### 10.4 距离只能展示，不能参与逻辑

**接口不返回任何坐标**（防拿它当坐标探测仪高频刷，所以还加了 60 次/分限流）。
只有 `card.distanceText`，三档模糊文案：`500 m 内` / `1 km 内` / 取整公里。
安卓**不要试图自己算距离或排序**，排序已在服务端按查看者当前存储的位置重算过了。

### 10.5 位置消息与第三方导航（与交友无关，但顺手补齐）

聊天里的位置消息是 `msgType=8`，`extra` 存 `{locationName, latitude, longitude}`，
**与 `im_user_profile` 的交友定位完全无关，也不会写进去**。点「导航」时拼 URI 即可，
三家都是**免密钥**的 URI API：

```kotlin
// 注意：高德经度在前，百度纬度在前，顺序相反；坐标系一律声明 WGS-84 交对方服务端转
val amap  = "https://uri.amap.com/marker?position=$lng,$lat&name=$enc&src=im&coordinate=wgs84&callnative=1"
val baidu = "https://api.map.baidu.com/marker?location=$lat,$lng&title=$enc&output=html&coord_type=wgs84&src=webapp.im.location"
val goog  = "https://www.google.com/maps?q=$lat,$lng"
// 安卓更推荐直接拉原生：Intent(ACTION_VIEW, "geo:$lat,$lng?q=$lat,$lng($name)")
```

详细原理见同目录 `定位与距离实现详解.md` 第十一节（含瓦片图 URL 的算法与三家逐参数解释）。

## 十一、WebSocket：只有一帧，其余全靠拉

### 11.1 唯一的交友推送

后端 `WsMessageType` 有 31 个事件，交友域只复用 `notify` 的一种 `bizType`：

```json
{"type":"notify","timestamp":1764200000000,"data":{
  "bizType":"match-success",
  "userId":"194823748239849472",
  "nickname":"小明",
  "avatar":"https://...",
  "pairId":"194823748239849473",
  "conversationId":"194823748239849474"
}}
```

- **字段里的 ID 都是雪花，按第四节口径收成字符串**。
- **双向都推**：先喜欢的那个人也可能正开着应用，所以两边各收一帧。
- 推送挂在事务 `afterCommit` 上，所以收到时会话一定已建好。
- 推送失败只记日志，**不是可靠信道**：没收到不代表没成对，进「我的配对」页仍然能看到。

现有 `WsDispatcher.handleNotify()` 只认 `friend-request` / `friend-accepted` / `biz==group`，
**必须补一个分支**（会话是刚建的，不刷列表点进去会看到一个找不到归属的会话 id）：

```kotlin
when (data["bizType"]?.jsonPrimitive?.content) {
    "friend-request" -> friends.onFriendRequestNotify()
    "friend-accepted" -> { friends.refreshPendingCount(); conversations.fetchList() }
    "match-success" -> {
        conversations.fetchList()                  // 新会话要先补进本地列表
        dating.onMatched(                          // 弹「配对成功」，给「去聊天」入口
            peerUserId = data["userId"]?.jsonPrimitive?.content.orEmpty(),
            nickname   = data["nickname"]?.jsonPrimitive?.content.orEmpty(),
            avatar     = data["avatar"]?.jsonPrimitive?.content,
            conversationId = data["conversationId"]?.jsonPrimitive?.content
        )
    }
}
```

★ **发起方只弹一层**：滑完卡片的那次 HTTP 响应里已经带了 `MatchActionVO`（`matched=true`），
Web 端就是靠它弹「去聊天 / 继续刷」。同一对 pairId 会收到两路信号（HTTP 与 WS），
**不要自己再叠一层通知**，否则点一次喜欢出三个东西。去重靠「各只发一种形态」，
不是靠共享一个已弹过的 pairId 集合。

### 11.2 剩下的都靠拉

点赞数、新评论、谁看过我、喜欢我的、新动态、亲密度升级、资料审核结果，
**全都没有推送**。安卓用这三招覆盖：

1. 进页面就拉（首次 `LaunchedEffect`）。
2. 下拉刷新（交友页、动态流、访客页必须提供）。
3. 写操作后用返回体就地更新（第 12 节里标了「返回全量列表」的那些接口）。

握手、心跳、重连、顶号都已在 `ImWebSocket.kt` 里实现，交友域不需要动它。
顺便记住三个已有结论：上行帧**必须带 `timestamp`**（否则被 1001 拒），
心跳间隔由服务端 `notify(action=connected)` 帧下发覆盖默认 30s，
死亡判定是两个心跳周期没等到 pong 就主动 close 触发重连。

## 十二、容易写错的行为口径（逐条）

这一节是从 `im-ui/src/api/dating.js` 的注释里抽出来的，都是 Web 端已经踩过、
后端故意这么设计的点。安卓重写一遍很容易写反。

**资料与隐私**

1. `PUT /profile` 是 **null 字段不修改**，不是整组替换。传 `heightCm=null` 不会清空身高，
   只是「不提这件事」。**要清空必须把字段名放进 `clears`**，白名单只认 11 个：
   `birthday` `heightCm` `education` `occupation` `income` `marriage` `datingGoal`
   `province` `city` `district` `location`。拼错一个名字报 **1001「未知的清空字段：xxx」**
   （故意报错而不是忽略：静默不清空是最难查的「改了没生效」）。
   一个字段都没改也没清 → **1001「没有需要修改的字段」**。
2. 改资料会顺带刷 `lastActiveTime`，「活跃优先」排序靠它。所以安卓不要为了「只改一个字段」
   就连环发多个 `PUT`，那会把活跃时间刷很多次。
3. `PUT /profile/privacy` 同样是 null 不修改；`momentVisibleDays` 只认 0/3/7/30，
   其他值报 1001；一个开关都没传报 1001「没有需要修改的开关」。
4. 成功后都返回**全量 `DatingProfileVO`**（含重算后的 `profileScore` / `missingTips`），
   直接用返回值覆盖本地，不要为了「保险」再 GET 一次。

**字典**

5. `GET /dict` 一个请求拿全部（学历/收入/婚恋/交友目的/排序），进交友页拉一次
   缓存在内存即可。选项集几乎不变，**不要每个表单都拉一次**。注意 `sorts[].code` 是字符串。

**照片墙**

6. `machineChecked` 的真假很重：`true` 就直接算「已通过」（对外可见），`false/null` 进人工复审。
   Web 端的取值是「客户端图像审核真跑了且没降级」才为 true。
   **安卓如果没接机审，一律传 `false`**（或不传），照片会显示「审核中」，这是事实而不是 bug；
   谎报 true 等于把没人看过的图直接公开。
7. `GET /photos` 不传 `userId` 为本人。本人视角多返 `fileId/auditStatus/auditStatusDesc/rejectReason`；
   **他人视角拿不到待审与被驳回的行**（不是字段为空，是整行不返）。所以照片墙的「审核中」角标
   只能在用户自己的页面上画。
8. `POST /photos` 上限 9 张（2025），同一 `fileId` 重复提交报 2026。
9. `PUT /photos/sort` 的 `ids` 必须与当前照片 ID 集合**完全一致**（包集合相等，不只是长度），
   否则 2029。正确做法：拖完就发，2029 就静默重拉再让用户重拖。
10. `isMain` 是 `Int`（0/1）不是 `Boolean`；`DELETE` / `main` / `sort` 都返回重排后的全量列表。

**标签**

11. `PUT /tags` 的 `ids` **不能不传**（`@NotNull`），清空要显式传 `[]`；上限 10（2030），
    超了报 2030，有下架 ID 报 2031。`/tags/library` 按分类分组返回，已下架标签不会出现在库里，
    但会出现在 `/tags?userId=` 里（`disabled=true`）——**用户已选的下架标签要显示出来且可取消**。

**破冰**

12. `GET /icebreakers?userId=` 返回的 `content` 是**成品**：`{nickname}` `{city}` `{tag}` 这类
    占位符已由服务端替换完，**安卓绝不能再替一次**。
    对方没填的项会让整条不下发，所以下面只有 5 条是正常结果，不是接口坏了。
    `POST /icebreakers/{id}/use` 是埋点，`Result<Void>`，**失败完全静默**（不阻塞发送）。

**匹配**

13. `GET /deck` 返回**数组而不是分页**（无限流）。到底的判据是「长度 < size」；
    到底了还可以接着刷（服务端会重新洗牌补充），Web 端的做法是剩余 ≤ 3 张自动补一批。
    `sort` **只对本次生效，不会写回偏好**；不传或认不出的值都按偏好里存的那个。
14. `POST /match/action` **一个方向只记一行**（`uk_from_to` 幂等），重复滑同一个人是 UPDATE
    不是 INSERT（改动作）。动作与来源都没变时后端**不发 UPDATE**（因为 `update_time` 是
    「谁喜欢我」的排序列，刷新页面重刷同一张卡会把三天前的喜欢顶到最前）。
15. `matched=true` 时返回体直接带 `conversationId`，**不要再去查一次会话**；跳聊天前先
    `conversations.fetchList()`。已知并发窗口：两人同一毫秒互点喜欢会双双读不到对方的行而都不成对，
    这是明知代价后的设计（加 `FOR UPDATE` 会死锁回滚，用户看到「点了喜欢报错」），
    后果可自愈（双方「喜欢我的」里都有对方，再点一次立即成对）。**不要把这当 bug 报给后端**。
16. ★ `GET /likes` 与 `GET /pairs` 的 `total` **会偏大**：卡片解不出来的人（注销/封号）后端直接
    `continue` 跳过，所以分页条显示 12 条而列表只有 10 行是正常现象。
    **不要拿 total 去断言「还有多少页」或做本地计数对账**。
17. 解除配对后对方**不会自动回到卡池**（「划过」是不可撤销的事实），要再成对得从
    「喜欢我的」那一页点回去。
18. 配对 ≠ 加好友：成对后对方不会出现在好友列表里。

**偏好**

19. `PUT /preference` 是**整组替换**（与资料保存相反），必须全字段一起 PUT，
    先 GET 填表单再整体 PUT 是唯一正确的做法。
20. 越界与自相矛盾（如 `ageMin > ageMax`）**报错而不是夹紧**，要把后端 `message` 原样弹给用户。
    取值范围（Bean Validation 硬拦）：`targetGender` 0-2、`ageMin/ageMax` 18-80、
    `distanceKm` 0-20（0 为不限，再远用城市筛）、`targetCity` ≤32、
    `heightMin/Max` 0 或 100-250、`targetEducation` 0-6、`targetMarriage` 0-4、
    `onlineFirst` 0/1、`excludePassed` 0/1、`sortBy` ≤16。
21. ★ `saved=false` 时后端**根本没拿默认值去筛人**。安卓要提示「尚未保存」，
    不能把一组默认值当用户设过的偏好画出来。

**附近的人 / 访客 / 亲密度**

22. `GET /nearby`：`radius` 500-20000（越界直接被参数校验拦下，服务端还会再夹一次），
    `size` 1-50；返回是数组。2042 的静默处理见 10.3 节。
23. `GET /visits`：**无分页无 total**，固定上限 50 位的短列表，所以不需要做无限滚动。
    访客记录不是接口写的——**你 GET 了对方的资料卡（第 5.1 表里的 4 号接口）就自动记一条**。
    两种情况不会留痕，都不是 bug：① 访问者自己把 `discoverable` 关了（隐身），
    隐身与「不留足迹」用的是同一个判定；② 访问者从未打开过交友页（库里没有
    `im_user_profile` 行）。同一天反复点开只算「来过一天」但 `visitTimes` 累加。
24. `GET /intimacy?userId=` **从不返回 null**：没来往就是一组 0，可以直接画。
    `progress` 是**当前档位内**的百分比（不是总分百分比）；`nextLevelScore==null` 表示顶档，
    别画「还差 N 分」；`sparkAlive` 只代表今天或昨天聊过，**天数一律用 `streakDays`**。

**动态**

25. `POST /moments`：`content` ≤500 字，与附件至少有一样（都空报 2051）；附件最多 9（2052），
    有视频就不允许再有图（九宫格画不下一格视频）；`visibility=3` 时 `visibleUserIds` 至少 1 人（2053）。
    ★ `visibleUserIds` 一律传字符串数组（雪花 ID 转数字会掉精度）。
26. ★ `GET /feed` 是**游标翻页**，把返回的**最后一条 `momentId`** 当下一页的 `cursorId`（首页不传）。
    **条数不足一页不代表到底**——可见范围是在内存里逐条过滤的，被滤掉的也算扫过了；
    **只有空数组才是真的没了**。拿 `size` 判底是错的。（`/user/{userId}` 同理。）
27. `GET /mine/page` 是**页码翻页**且返回标准 `PageResult`；它**不过可见范围**，
    包含 `status=2` 已下架的，每条带 `viewCount`。与 26 是两套分页，不要抽成同一个函数。
28. `like` / `unlike` 都返回**操作后的点赞总数**，幂等（重复点不会加两次），
    可以乐观更新。需要 `friend:apply` 权限，**没权限应该藏按钮而不是吃 1003**。
29. `POST /{id}/comments`：回复一条二级评论时 `parentId` **仍传一级评论的 ID**（两层封顶），
    要标谁被回复就另带 `replyUserId`。返回新评论对象直接插入列表，**不要重拉详情**。
30. `DELETE /comments/{id}` 删一级评论会**连子树一起删**，重画时按子树长度算减量，
    不要自己只减 1。
31. `POST /{id}/share`：`conversationId` 优先于 `toUserId`；转发的卡片三行（作者/正文摘要/图数）
    由服务端反查覆写，**不要自己拼消息 content**；**转发不改变原动态的可见范围**（服务端会在
    渲染时再校一次）。
32. `DELETE /moments/{id}` 连带附件、评论、点赞、可见名单一起删，但 **`im_file` 一行不动**。

**他人资料卡**

33. `GET /profile/{userId}` 对**从未回填过交友资料的账号返回一张空卡而不报错**（不是 2001）：
    `birthday` / `age` 等为 null，而 `locationText` 与 `educationDesc` / `incomeDesc` /
    `marriageDesc` / `datingGoalDesc` 是**空字符串而不是 null**。安卓要能渲染
    「这个人还没填交友资料」，不能因为字段为空而崩，也不要拿它当「对方不存在」处理。

## 十三、建议开发顺序

按「先能看见人，再能筛人，最后才做社交」排，每一步都能独立验收：

1. **DTO + API 声明 + unwrap 跑通一个只读接口**（`GET /dict`）。
   这一步先把 ID 序列化与时间格式两个坑验完，后面就不会反复返工。
2. **资料页**：`GET /profile` → 编辑 → `PUT /profile` + `PUT /profile/privacy`，
   把 `clears` 与「null 不修改」这两条跑对。
3. **字典驱动的表单**：学历/收入/婚恋/交友目的用 `DictOption` 渲染 SingleChoice；
   排序口径用 `SortOption`。
4. **照片墙**：上传（`dating_photo`）→ 提交 → 排序 → 设主封面，重点验 2026 / 2029。
5. **标签**：`/tags/library` 分组选择器 + `/tags` 回显（含 `disabled`）。
6. **匹配三 tab**：`deck` 无限拖 + `likes` 分页 + `pairs` 分页 + `unmatch`。
   先把 `match-success` 的 WS 分支接上，否则双向测试时看不到对面。
7. **偏好页**：先 GET 填表、整体 PUT，把越界报错原样弹出来。
8. **附近的人 + 定位 + 访客**（定位拿不到时要能降级成只用城市）。
9. **动态**：feed 游标 → 发布 → 点赞评论 → 我的分页 → 转发到会话（复用现有 `MessageRepository`）。
10. **破冰与亲密度**：挂在他人资料卡与会话顶部，最后做（它们不影响主链路）。

## 十四、安卓侧已知缺口（后端不会补）

### 14.1 拿不到权限位

后端 `UserVO` 有 `permissions` 字段，但 `im-android` 的 `UserInfoVO` 只声明了
`id/username/nickname/avatar` 四个字段，而 `ApiClient` 的 `Json` 配了 `ignoreUnknownKeys = true`，
所以权限数组被**静默丢弃**（`im-android` 内搜 `permissions` 零命中）。

要做的事：给 `UserInfoVO` 补 `val permissions: List<String>? = null`，在 `AuthRepository`
里存一份，提供一个 `hasPerm(code)`。交友域需要判的三个码：`user:profile:update`（编辑资料、
照片墙、标签、偏好）、`friend:apply`（滑动喜欢、解除配对、点赞、评论）、`message:send`（转发动态）。
没权限时要**藏掉按钮**，而不是让用户反复点了吃 1003。

### 14.2 无交友推送

只有 `match-success` 一条，其余全靠拉。交友、动态、访客三个页面必须提供下拉刷新，
否则用户会以为数据不更新。

### 14.3 照片审核结果没有推送也没有回调

后台人工改 `audit_status` 之后不会通知任何人。用户进自己的照片墙页时重拉一次 `GET /photos`，
靠 `auditStatusDesc` 画角标即可。

### 14.4 定位能力差异

Web 端室内可用 Wi-Fi 指纹兜底，安卓 GNSS 室内不可用，而 `FusedLocationProvider` 在没 Google
服务的机型上会直接不可用。没服务时退到 `LocationManager.getLastKnownLocation`；再拿不到就
只让用户手填城市（`city` 字段不依赖定位），距离筛选自动置灰。

### 14.5 图片大图内存

接口不分页也不提供缩略图字段，`url` 就是原图。Coil 统一限解码尺寸（如 1080），
九宫格不要直接解原图。

## 十五、自测清单

只需两个账号（下文 A/B）与一个已应用交友表的库。**相关表未应用时接口会报 1007**
（例如 `im_match_like` / `im_match_pair` 缺失时，匹配那几个端点全报），先确认版本已应用再报缺陷。

- [ ] 1 A 滑 B 的卡 → B 的「喜欢我的」出现 A；B 回喜欢 → **两边同时**收到 `match-success`，
      会话列表各多出一条，里面有一条系统通知（入口不同文案不同）。

      「未知的清空字段」，而不是静默成功。
- [ ] 5 照片上传到第 10 张报 2025；重复提交同一 fileId 报 2026；改顺序时中途删一张再提交报 2029
      且能自动重拉。
- [ ] 6 自己的照片墙能看到「审核中」角标；**用另一账号看时看不到这张**。
- [ ] 7 选 11 个标签报 2030；不传 `ids`（而不是传 `[]`）报 1001/1008。
- [ ] 8 偏好先 GET 后 PUT；只 PUT 一个字段能观察到其他字段被重置为默认（整组替换的证据）；
      `ageMin=30 ageMax=20` 能把后端 message 原样弹出来。

      （转发不改变可见范围）。
