## 一、实现方案概述

### 1. XSS 防护（渲染转义 + 纵深防御）

| 防线 | 位置 | 说明 |
|---|---|---|
| 第一道：渲染层转义 | `im-ui` 全部消息渲染 | 消息气泡用 Vue 插值（`{{ }}`）渲染，框架自动 HTML 转义，天然免疫 XSS；全项目仅两处 `v-html`（会话内搜索高亮 `ChatWindow.vue#highlightSearch`、全局搜索高亮 `ChatHome.vue#highlightGlobal`），均先把 `& < > " '` 五类字符转义再做关键字替换 |
| 第二道：存储侧内容治理 | `TextContentHandler` / `AttachmentContentHandler` | 敏感词过滤（可热开关）；文本长度上限 `im.message.max-text-length=5000` |
| 第三道：安全响应头（本次新增） | `im-common/config/SecurityHeaderConfig.java` | 所有响应统一加 `X-Content-Type-Options: nosniff`（禁止 MIME 嗅探）、`X-Frame-Options: DENY`（防点击劫持/iframe 套壳）、`Referrer-Policy: no-referrer`（票据 URL 不随 Referer 外泄）；JSON 接口另加 `Cache-Control: no-store`（消息/token 不落中间缓存），文件下载端点刻意排除以保留 ETag/304 协商缓存 |

### 2. CSRF 防护（机制性消除，无需 Token）

CSRF 攻击成立的前提是「浏览器自动携带凭证（Cookie）」。本项目从机制上消除了这个前提：

- `sa-token.is-read-cookie: false`、`is-read-header: true`、`is-read-body: false`（`application.yml`）——token 只从 `satoken` 请求头读取，**不存在任何浏览器会自动附带的凭证**；
- 前端 token 存 localStorage，由 axios 拦截器显式放进请求头，跨站表单/图片请求伪造不出这个头；
- `<img src>` 等无法带请求头的场景走 URL 短时票据（`file-ticket-ttl-seconds: 1800`），票据与文件 ID 绑定、过期即失效，且 `Referrer-Policy: no-referrer` 防止票据经 Referer 泄露；
- CORS 白名单（`im.cors.allowed-origins`）限制可信来源，WebSocket 握手同样依赖票据而非 Cookie。

结论：不引入双提交 Cookie / Synchronizer Token 这类 CSRF Token 方案——在 header-only 凭证模型下它们是多余的复杂度。

### 3. 接口鉴权与越权防护（既有能力，本次核验）

| 层级 | 机制 |
|---|---|
| 统一登录鉴权 | `SaTokenConfigure`：拦截器覆盖 `/api/**`，白名单仅注册/登录/验证码/文件下载（下载在 Controller 内用票据自行鉴权）；写操作叠加 `@SaCheckPermission` RBAC 权限码 |
| 消息越权 | `MessageServiceImpl`：history/search/markRead/deleteForUser/clearConversation 逐项校验 `conversationSpi.isMember`；转发校验原会话成员身份（防猜 messageId 广播他人文件） |
| 文件/视频越权 | `FileServiceImpl.requireAccessible`：仅「本人上传 / 公开头像 / 与文件所在消息同会话的成员」可访问（`existsVisibleFileMessage` 联查消息可见性，含单端删除过滤）；下载端点票据校验绑定 viewerId+fileId |
| WS 通道越权 | 发送者 ID 只认握手票据解出的连接身份（`connection.userId()`），客户端无法冒充；系统消息类型禁止客户端自选 |

### 4. 限流防刷（本次新增，核心工作）

架构：`@RateLimit` 注解（声明配额）→ `RateLimitInterceptor`（HTTP 入口检查，order=-100 先于 Sa-Token）→ `RateLimiter`（Redis 固定窗口计数，Lua 原子 INCR+EXPIRE；Redis 故障时 fail-open 退化为进程内计数）；WS 发消息通道在 `WsInboundDispatcher.handleChat` 内走同一个 `RateLimiter`。超限抛 `TOO_MANY_REQUESTS(1010)`，HTTP 返回标准 JSON 错误体，WS 回 error 帧，**均不断连接、不弹全局告警**（前端按业务错误提示「操作过于频繁」）。

配额一览（维度：IP=按来源地址，USER=按登录用户，未登录退化为 IP）：

| 端点 | 配额 | 维度 | 说明 |
|---|---|---|---|
| `POST /api/auth/register` | 5 次/分钟 | IP | 防批量注册 |
| `POST /api/auth/login` | 10 次/分钟 | IP | 防密码爆破（另有图形验证码闸门） |
| `POST /api/auth/login/sms` `/email` | 10 次/分钟 | IP | 防验证码撞库 |
| `GET /api/captcha/image` | 30 次/分钟 | IP | |
| `POST /api/captcha/sms` `/email` | 5 次/分钟 | IP | 与服务层「同号 60 秒一次」互补：后者防单目标轰炸，此处防换号滥刷（短信费/邮件信誉） |
| `POST /api/file/upload` | 30 次/分钟 | USER | 防刷爆存储 |
| `POST /api/file/avatar` | 10 次/分钟 | USER | |
| `POST /api/file/upload/init` `/merge` | 30 次/分钟 | USER | |
| `POST /api/file/upload/chunk` | 1200 次/分钟 | USER | 单独放宽：2GB 文件按 5MB 切片即 400 分片 |
| `POST /api/message/send` | 120 次/分钟 | USER | REST 通道发消息 |
| WS `chat` 帧 | 60 次/分钟 | USER | `im.rate-limit.ws-chat-count/seconds`，防绕开 REST 从长连接刷 |
| **全部 /api/**** 兜底 | 300 次/10 秒 | IP | `im.rate-limit.global-count/seconds`，覆盖所有未标注解接口 |
| 远程控制接口 | —— | —— | 该功能尚未开发；开发时在端点上标 `@RateLimit` 即自动纳入 |

配置项（`application.yml` → `im.rate-limit`）：`enabled`（总开关，排障可临时关）、`global-count/global-seconds`、`ws-chat-count/ws-chat-seconds`。内网多人共用出口 IP 部署时需按人数上调全局兜底。

### 已知边界与注意事项

1. **IP 维度依赖代理头**：`SecurityUtil.getClientIp` 信任 `X-Forwarded-For`。仅应在可信反向代理之后部署；若后端直接暴露公网，攻击者可伪造该头绕过 IP 限流（USER 维度不受影响）。
2. **固定窗口**：窗口交界处理论上可放行 2 倍配额（如登录 10 次/分钟，跨窗口瞬间最多 20 次）。对防爆破场景无实质影响，且登录另有图形验证码闸门。
3. **fail-open 取舍**：Redis 故障时限流退化到单机内存计数而非拒绝服务——限流是护栏不是闸门，可用性优先；多实例部署且 Redis 故障期间，总配额会放大为「节点数 × 配额」。
4. **内网共享出口 IP**：全公司一个出口 IP 时，300 次/10 秒的全局兜底是所有人共享的，部署前按人数上调 `im.rate-limit.global-count`。
5. **远程控制接口**（需求第 30 行提及）：功能本身尚未开发（待开发功能.txt 第 2 节），开发时在对应端点标注 `@RateLimit` 即自动纳入本限流体系。
