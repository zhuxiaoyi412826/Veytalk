# 可复用教训

1. **乱码不看日志看 HEX**：字符集问题的决定性证据是 `HEX(col)` 的字节前缀（`C3/C2` = 双重编码，`E5/E6/E7` = 正常），以及「前端写死的中文正常、只库读字段乱」这条对照——logback 日志里根本没有这条信息。
2. **反解必须逐列带 `WHERE col REGEXP` 只碰乱码行**：表里往往有上次已治好的正常行，整表/整 id 段 `CONVERT` 会把好行二次解坏，制造出更难查的第三种乱码。
3. **SQL 要交给 mysql，别交给 bash**：带括号/注释的 SQL 裸贴 shell 会报 `syntax error near unexpected token '('`、`command not found` 且**静默不执行**；一律包进 `mysql … -e "…"`，跑完用只读普查复核「结果变了」，别信「回车没报错就是成功了」。
4. **治数据 ≠ 治复发**：只反解存量、不修导入路径，下次换服务器/重建容器会原样再乱——本次「两次导入乱码」正是只治标留下的账。根治在容器层把客户端连接字符集钉死。
5. **`:ro` 单文件挂载是目录陷阱**：源文件不在，Docker 会建成同名目录，进程读到目录直接起不来（与记录 2 教训 8 同族）。加这类挂载务必配套「缺则补文件」的 bootstrap 步骤。
6. **非空坏值比空值危险**（承接记录 1 教训 4、记录 2 教训 4）：`--character-set-server=utf8mb4` 看着配了、非空、还全绿，却只管服务端只管不到客户端连接——「配了 ≠ 配到了真正起作用的那一层」。
7. **修改配置重启容器**，不仅要重启后端容器也要重启nginx容器，不然内网分发不到IP

## 记录 1：语音视频通话全挂——STUN/TURN 地址把冒号写成了等号（2026-11-13）

### 症状

- 公网浏览器拨打/接听，弹「**无法获取麦克风/摄像头：SyntaxError**」；
- **第一次访问会先弹摄像头/麦克风权限提示**，用户点了允许，**几秒后**才报上面这句；第二次开始不弹权限、直接报错；
- F12 网络面板看不到任何外发的 STUN/TURN 请求、也没有新的 HTTP 请求；
- 「局域网里测是好的，公网才炸」——当时被当成网络路径问题排查了很久。

### 排查过程（三步分诊，命令可在服务器直接复用）

```bash
cd /opt/im-docker
# ① 源头文件长什么样
grep -nE 'IM_CALL|IM_TURN' conf/im.env
# ② 运行中容器里的真实环境变量（决定性一步：证明改动生没生效）
docker compose exec im-server sh -c "env | grep -E 'IM_CALL|IM_TURN'"
# ③ 最终答案在浏览器：登录 → F12 网络面板 → 过滤 config → /api/call/config 的 Response
#    iceServers 里每条 urls 必须以 stun: / turn: 开头（该请求在页面加载时就发完了，要 Ctrl+F5 后看列表最前面）
```

实测输出（①② 完全一致）：

```
IM_CALL_STUN_URLS=stun=120.78.126.132:3478     ← 等号！应为 stun:120.78.126.132:3478
IM_CALL_TURN_URLS=turn=120.78.126.132:3478?transport=udp   ← 同款等号
IM_CALL_TURN_ENABLED=true                       ← coturn 还没部署就先开着 true
```

### 根因链

1. **病灶在文档/模板里**：`conf/im.env.example` 与三份部署文档把示例写成了 `stun=<公网IP>:3478`（等号），照抄的人忠实地保留了等号、只替换了 IP。仓库内 7 处已全部勘误为 `stun:<公网IP>:3478`（2026-11-13）。
2. **浏览器对非法 ICE 地址零宽容**：`/api/call/config` 原样下发坏地址，Chromium 在 `new RTCPeerConnection({iceServers})` **构造即抛 SyntaxError**——不是逐条跳过的软错误。
3. **报错文案张冠李戴**：旧前端把 buildEngine 的异常统一报「无法获取麦克风/摄像头」，真凶（ICE 配置）被冤枉成了设备问题。
4. 症状逐条对上：权限弹窗在 getUserMedia 阶段就出现并成功；随后建 PC 才抛错；teardown 把轨停掉。网络面板安静是因为 pc 根本没建出来、一个探测包都发不出去；信令走已有 WS 长连接，不产生新 HTTP 请求。

### 修复

```bash
cd /opt/im-docker
sed -i -E 's/^(IM_CALL_STUN_URLS)=stun=/\1=stun:/; s/^(IM_CALL_TURN_URLS)=turn=/\1=turn:/' conf/im.env
grep -nE 'IM_CALL|IM_TURN' conf/im.env                        # 肉眼确认两行已是冒号
docker compose up -d --force-recreate im-server              # ★ 必须 recreate，见教训 3
docker compose exec im-server sh -c "env | grep -E 'IM_CALL|IM_TURN'"   # 复核容器内真值
```

### 为什么「局域网正常、公网报错」是假象

SyntaxError 是**配置字符串解析失败**，与请求从哪张网发来无关：同一台服务器、同一个生产页面，局域网机器和公网手机读到的 `/api/call/config` 是同一份。**局域网测通 ≠ 生产配置没问题**——那次「通」几乎必然是没打到这份 `conf/im.env`（本机 dev 环境 iceServers 本来就是空、或改配置前的旧标签页）。跨网对比只能用来区分「P2P 打洞/中继不通」这类真网络问题，对「构造即抛」的解析错误没有区分度。

### 代码层加固（同批入库，随下次构建生效）

- 后端 `CallSignalingService.buildIceServers`：下发前校验 URL 格式（`^(stun|stuns|turn|turns):[^\s<>]+$`），非法条目跳过并 log.warn 指到具体配置键——保护所有旧客户端；
- 前端 `utils/webrtc.js`：`sanitizeIceServers` 丢弃非法条目降级 console 警告（配置笔误最多丢打洞能力，不再打挂整通电话）；`mediaErrorHint` 把 SyntaxError 的文案分流为「ICE 地址非法，查 IM_CALL_*」；
- `im.env.example`：`IM_CALL_TURN_ENABLED` 默认改回 `false` 并加警示注释。

### 可复用教训

1. **浏览器报错名带 Error 后缀的「构造/解析」类异常（SyntaxError/TypeError）先怀疑下发配置字符串本身**，而不是网络路径；getUserMedia 成功后的权限弹窗出现 ≠ 麦照有问题。
2. **配置排障双验范式**：源头文件 `grep` + 运行进程 `exec env | grep`，两者一致才谈「改了没生效」；只看文件会漏掉 recreate 没做的情况，只看接口响应会分不清是缓存还是现值。
3. **env_file 的改动一律 `up -d --force-recreate`**：环境变量在容器创建时注入，`restart` 和裸 `up -d`（compose 判定配置未变时）都不重读 `conf/im.env`——restart 了等于没改。与「挂载文件用 restart、up -d 反而没用」（app/extra/*.yml、证书）恰好相反，两类文件别搞混。
4. **非空的占位符比空值更毒**：`IM_TURN_SECRET=<与coturn逐字一致>` 不是空串，后端判「secret 非空才下发 TURN」于是照样签发了一条坏中继条目；模板里凡是「配了才生效」的开关（如 TURN_ENABLED）默认值就该 false。
5. **照抄文档前先怀疑文档**：本次病灶源头是模板与三份手册共 7 处笔误，用户一字不差照抄反而必炸——文档示例值改动后要在真实环境验一次语法类字段（URL/正则/cron）。
6. **coturn 部署的独立检查点**（与 SyntaxError 无关但决定公网能否接通）：compose 的 coturn 段放开后，`--external-ip=<公网IP>/<内网IP>` 必须替换（阿里云公网 IP 是 NAT 映射不在网卡上），安全组放行 `3478 TCP+UDP` 与 `49160-49200 UDP`，`.env` 的 `TURN_SECRET` 与 `conf/im.env` 的 `IM_TURN_SECRET` 逐字相同，否则客户端一律 401。

## 记录 2：直播上线——六条 curl 验收里挖出五处独立故障（2026-11-15）

### 背景

直播代码早写完了，生产差的是「开闸」：媒体面三层闸门（compose 发布 8088 / nginx 配置 / 云安全组）+ 一条密钥链（`.env` → `conf/im.env` → nginx `secure_link_md5`）+ 一个盘（`data/live` 写权限）。
验收口径是手册 §12.6 那六条 curl，首轮只有 ②③ 对：

| # | 意图 | 期望 | 首轮实测 |
|---|---|---|---|
| ① | PUT 分片到 8088 | 201/204 | **500** |
| ② | GET 8088（只写不读） | 403 | 403 ✅ |
| ③ | GET 443 不带签名 | 403 | 403 ✅ |
| ④ | GET 443 带签名 | 200 | **403** |
| ⑤ | PUT 连麦 `webm/manifest.json` 到 443 | 201 | **403** |

**状态码是分层证据，推进一位就排除一层**（本轮靠它收敛，比读代码快得多）：

- `403 → 404`：签名校验已经过了，只是文件不存在 → ④ 就是靠这个确认密钥链通了；
- `404 → 200`：文件真落盘了；
- `403 → 500`：location 命中了但写盘失败，**与鉴权无关**，此时去查 streamKey 是弯路；
- `405`：镜像缺 `http_dav_module`（`nginx -V` 确认）；
- 超时 / `connection refused`：分别是云安全组没放行 / compose 没发布端口。

### 故障 A：compose 的 `live-retention` 被 YAML 认成了 nginx 的属性

```
validating /opt/im-docker/docker-compose.yml: services.nginx.live-retention false schema
```

**根因**：把整块注释转成生效时保留了模板里更深的缩进。`services:` 下的同级键必须与 `nginx:` **同列（2 空格）**，子项 4 空格；差一列就是「挂到邻居家里去了」。报错路径 `services.nginx.<名字>` 直接读作「它被当成了 nginx 的属性」，是缩进问题而不是内容问题。

**修复与验证**：整块顶格重写（别逐行删 `# `），然后
```bash
docker compose config -q && docker compose config --services   # 应列出全部服务名
```

### 故障 B：nginx location 正则里的 `{24}` 未加引号（本轮最大时间黑洞）

同一个字符的两个错法，症状完全不同：

| 写法 | `nginx -t` | 实际行为 |
|---|---|---|
| `location ~ ^/live/...[0-9A-Za-z]{24}/webm/...$ {` | **拒**：`unknown directive "24}/webm/manifest\.json$"` | 词法解析在未加引号的参数里遇到 `{` 就结束当前指令 |
| `location ~ ...[0-9A-Za-z]\{24\}/webm/...$ {` | **通过**，站点全绿 | PCRE 把花括号当字面量，location 永远匹配不上 → 连麦 PUT 一律 403 |

**唯一正解**：整条正则用双引号包起来。
```nginx
location ~ "^/live/[0-9]+/[0-9A-Za-z]{24}/webm/manifest\.json$" {
location ~ "^/live/[0-9]+/[0-9A-Za-z]{24}/webm/[A-Za-z0-9._-]+\.webm$" {
```
不想用引号可以把 `{24}` 换成 `+` 兜底，安全性不变（nginx 本来就不校验 streamKey 真伪，写权限靠的是路径不可猜）。

**定位关键**：报错里的 `/etc/nginx/conf.d/im.conf:77` 与我手上文件的第 77 行**完全对上** —— 行号能对上就说明传输没问题、病灶在文件内容本身。此前我两轮把它误判成「上传过程被改坏」「手工编辑改坏」，都是在没有这个对照的情况下猜的。

★ 仓库模板 `Docker/nginx/conf.d/im.conf.example` 已同批修正（否则下次 `bootstrap.sh --force` 会重新生成一份坏配置）。

### 故障 C：密钥链三处不一致（两种「占位符当真值」+ 一种「校验码当密钥」）

链条：`.env` 的 `LIVE_SIGN_SECRET` → `conf/im.env` 的 `IM_LIVE_SIGN_SECRET` → `im.conf` 的 `secure_link_md5`，三处必须逐字相同。本轮实际出现的坏值：

1. `secure_link_md5 "${uri}${arg_expire}<开直播才需要，≥16位随机>";` —— 部署文档 `.env` 示例段里的**尖括号占位说明**被整行照抄进 `.env`，因为非空，一路畅通无阻地被脚本灌进了 nginx（与记录 1 教训 4 同族）；
2. `REPLACE_ME_LIVE_SECRET` —— 仓库里公开的占位串，两边「一致」所以直播看着能用，但任何读到仓库的人都能自造签名 URL 白看回放；
3. 更险的一种：把**文件校验码（md5sum）**当密钥填，并且整行替换时把 `${uri}${arg_expire}` 弄丢了 —— 那样 nginx 对**所有** URL 算出同一个哈希，防盗链形同不存在，而 `nginx -t` 与健康检查全绿。

**正确做法与自检**：
```bash
cd /opt/im-docker
grep -n '<' .env                       # ★ 一条命令扫出所有照抄进来的尖括号占位符
sed -i "s|^LIVE_SIGN_SECRET=.*|LIVE_SIGN_SECRET=$(openssl rand -hex 24)|" .env
SECRET=$(grep '^LIVE_SIGN_SECRET=' .env | cut -d= -f2-)
sed -i "s|^IM_LIVE_SIGN_SECRET=.*|IM_LIVE_SIGN_SECRET=$SECRET|" conf/im.env
# nginx 那行必须保留 ${uri}${arg_expire} 前缀：用「整行重写」的脚本改，别手粘、别拿 sed 拼正则
docker compose exec -T nginx nginx -T 2>/dev/null | grep -o 'secure_link_md5.*'   # 看生效值而非文件值
docker compose up -d --force-recreate im-server       # 后端读的是 env_file，必须重建
```
签名编码是 **base64url（无 `=` 填充）**不是十六进制；手造验收 URL：`printf '%s' "${URI}${EXP}${SECRET}" | openssl dgst -md5 -binary | base64 | tr '+/' '-_' | tr -d '='`。

### 故障 D：`data/live` 属主 1000、nginx worker uid 101 → PUT 500

决定性日志（`docker compose logs --tail=20 nginx`，不用猜）：
```
[crit] mkdir() "/data/live/999999/1f55254b5ed25bb522a4b304" failed (2: No such file or directory)
```

★ **反直觉点：errno 是 ENOENT（2）而不是 EACCES（13）**。因为父目录 `/data/live/999999` 本身就没建出来（101 对 1000 的 755 目录只有 `r-x`），对更深一级的 mkdir 只能报「父路径不存在」。按字面去查「路径拼错 / root 指令写错」会彻底走偏。

```bash
docker compose exec -T nginx id nginx          # → uid=101(nginx)
docker compose exec -T nginx ls -ld /data /data/live
chown 101:101 data/live
docker compose exec -T nginx sh -c 'touch /data/live/.w && rm /data/live/.w && echo WRITABLE'
```
**遗留**：`scripts/bootstrap.sh` 每次跑都把 `data/*` 统一 `chown 1000:1000`（那是给 im-server 的），会把 `data/live` 打回 1000 —— 症状是「哪天跑了 bootstrap 之后直播突然 500」。根治要在脚本里把 `data/live` 排除或单独 chown 成 nginx 的 uid。

### 故障 E：命令「看着执行了其实没执行」

- 整块粘贴时多行糊成一行（终端回显成 `...--force-recreate im-servernginx: the configuration ...`），**后两条根本没跑** → 表现是「配置改了没生效」，真凶是没 `reload`；
- `curl -s -w "%-14s %{http_code}"` 里 `%-14s` 是 printf 语法，curl 只认 `%{...}`，标签会原样打印出来（本轮输出满屏 `%-14s`）。

两条规矩：改 nginx 配置后 **`nginx -t` → `nginx -s reload` 逐条单行回车看回执**；带标签的探测用 `printf '%-22s %s\n' "$1" "$(curl -s -o /dev/null -w '%{http_code}' "${@:2}")"`。

### 服务器上改 nginx 配置的正确姿势（本轮流程沉淀）

1. 生效的是**生成物** `nginx/conf.d/im.conf`：只改仓库 `im.conf.example` 不生效；反过来手改 `im.conf` 会在下次 `bootstrap.sh --force` 时被 example 冲回 —— 两处必须一起改，或干脆让 example 保持最新后统一 `--force`。
2. 上传先落 `im.conf.new`：**不是 `.conf` 结尾就不会被 `conf.d/*.conf` include**，落盘当天不伤线上；校验通过后 `mv` 同目录改名替换（原子操作，且 `:ro` bind mount 能立刻看见。目录级挂载下改名/覆盖都穿透，只有「新建一个目录项」才需要 restart nginx）。
3. 传文件三步定死：本地 `Get-FileHash` 算 md5 → scp → 服务器 `md5sum` 对帐。**校验码只用于验传输，绝不能被当成密钥**（本轮就踩过）。
4. `nginx -T` dump 的是**正在加载的配置**，比 grep 文件更接近真相：文件对而 `nginx -T` 不对 = 没 reload。
5. `conf/im.env` 改了必须 `up -d --force-recreate im-server`，`restart` 不重读 `env_file`（同记录 1 教训 3）。

| # | 结果 |
|---|---|
| ② ③ | ✅ 一直正常 |
| ④ | ✅ 已从 403 推进到 404，**密钥链与 reload 都验通**，只差 ① 落盘后变 200 |
| ① | 待 `chown 101:101 data/live` 后复测（故障 D） |

### 可复用教训

1. **状态码推进一位就排除一层**：多故障叠加时，先用「期望/实测」表定位到最早断掉的那一层，别按最后一条症状改配置。
2. **报错行号是「内容问题 vs 传输问题」的指纹**：能和本地文件行号对上，就说明文件本身错了，后续所有「谁改坏了」的猜测都可以跳过。
3. **元字符 `{}` 有两个方向的错法**：nginx 词法要引号，PCRE 要原样；反斜杠转义能骗过语法检查却骗不过匹配，属于「全绿但功能死」的最难查一类。
4. **文档里的 `<中文说明>` 是不可抄的占位符**：`grep -n '<' .env` 应成为每次上线前的固定一条；非空占位符比空值危险（空值至少会 fail-fast）。
5. **密钥 / 校验码 / 令牌不能共用同一串十六进制**：本轮把文件 md5 当密钥填，还把 `${uri}${arg_expire}` 一起覆盖掉了 —— 改这种「前缀有语义」的行必须整行按模板重写，不能只替换尾部。
6. **权限故障的 errno 会降级**：写不进父目录时，深层 mkdir 报的是 ENOENT 而不是 EACCES；容器内排权限一律 `id <进程用户>` + `ls -ld` + 直接 `touch` 三连，比读日志猜快。
7. **整块粘贴命令不可信**：多行会在终端里糊接，长流程要逐条回车并核对回执；`nginx -t` 通过 ≠ 已加载，reload 才是分水岭。
8. **挂载目录里的占位文件会被 Docker 好心补成目录**：bind mount 的源文件不存在时 Docker 建同名目录，容器内报 `EISDIR`。放开任何带文件挂载的 service 前先 `ls -l` 那个文件。

## 记录 3：种子数据中文双重编码——同一批乱码反复导入两次，烧掉几个小时（2026-11-16）

### 症状

- 生产后台「用户协议 / 隐私政策 / 服务条款」的**标题、摘要、正文**显示为 `ç”¨æˆ·åè®®` 式乱码；「系统管理员」「爱丽丝」等账号昵称、角色名、权限名同样乱；
- **决定性对照**：前端写死的中文（页面标题、按钮文案）一直正常，**只有从数据库读出来的字段乱** → 一眼锁定是库里的数据坏了，不是前端编码、不是传输、不是字体；
- 「之前修过一次又犯了」：这是同一个坑的**第二次**发作，第一次只治了 `im_user` 两条，没查清导入路径，于是容器重建后又从源头再乱一遍。

### 排查过程（不看 logback 日志——乱码的证据全在库里）

```bash
cd /opt/im-docker
# ① HEX 定性：看每个字符的字节前缀（区分正常 UTF-8 与双重编码）
docker compose exec -T mysql mysql --default-character-set=utf8mb4 -uroot -p"$MYSQL_ROOT_PASSWORD" im_db -e \
"SELECT id, nickname, HEX(nickname) FROM im_user WHERE id IN (1,2,1000);"
# ② REGEXP 普查：一次捞出四张表所有乱码行，同时验证过滤条件命中准确
for c in "im_user:nickname" "im_role:role_name" "im_permission:perm_name" "im_agreement:title"; do
  t=${c%%:*}; col=${c##*:}
  docker compose exec -T mysql mysql --default-character-set=utf8mb4 -uroot -p"$MYSQL_ROOT_PASSWORD" im_db -e \
    "SELECT id, $col FROM $t WHERE $col REGEXP '[ÃÂåæçèé]'";
done
```

判读指纹：

| HEX 开头 | 含义 | 例 |
|---|---|---|
| `E5/E6/E7 …` | ✅ 正常 UTF-8 中文（三字节） | `客服`=`E5AEA2E69C8D` |
| `C3A6/C3A5/C3A7/C2B3 …` | ❌ **双重编码**：真正的 UTF-8 字节被当成 latin1 又各编了一遍 | admin「系统管理员」=`C3A7C2B3…` |

普查把爆炸半径钉死：`im_user` 只有 1000/1001 乱（1/2/1002 是上次修好的、正常）；`im_role` 1~4、`im_permission` 101~125 一大片、`im_agreement` 1301~1303 全乱。

### 根因链

1. **病灶是导入时的连接字符集，不是 SQL 文件本身**：仓库 `sql/*.sql` 顶部早有 `SET NAMES utf8mb4;`，但**空卷首次启动**时镜像 entrypoint 用 `mysql < 文件` 原生重定向跑 `sql-init/*.sql`，这条**客户端连接**的 `character_set_client` 由客户端默认决定；compose 里的 `--character-set-server=utf8mb4` 只钉服务端默认，**管不到客户端连接**。连接落在 latin1，文件里的 UTF-8 中文被逐字节当 latin1 存进去 → 落库即 `C3…` 双重编码。
2. **换服务器 / 容器重建必复发**：只要 `sql-init/` 落的是旧版或外部没写 `SET NAMES` 的脚本，首启 initdb 就再乱一次——这就是「两次导入乱码」的由来。`import-sql.sh` 手工导反而没事（它显式带了 `--default-character-set=utf8mb4`）。
3. **上次只治标**：第一次只反解了 `im_user` 两条，`im_role`/`im_permission`/`im_agreement`/admin 这批种子行一直没动，导入路径也没堵，所以既「没治好」又「会复发」。

### 修复

**A. 治已坏的数据（按列反解，只碰乱码行）**——⚠️ MySQL 写操作由运维本人执行；且**绝不能**整表反解，否则会把已正常的 id 1/2/1002 二次解坏：

```sql
-- 每一列单独 UPDATE，靠 WHERE col REGEXP '[ÃÂåæçèé]' 只命中乱码行
UPDATE im_user    SET nickname  = CONVERT(CAST(CONVERT(nickname  USING latin1) AS BINARY) USING utf8mb4) WHERE nickname  REGEXP '[ÃÂåæçèé]';
UPDATE im_role    SET role_name = CONVERT(CAST(CONVERT(role_name USING latin1) AS BINARY) USING utf8mb4) WHERE role_name REGEXP '[ÃÂåæçèé]';
-- im_permission(perm_name/description)、im_agreement(title/summary/content) 同款逐列
```

> ★ **这几个 UPDATE 必须整段包进 `docker compose exec -T mysql mysql … im_db -e "…"` 里跑，不能裸贴到 bash 提示符。** 本次就栽在这：bash 把 `CONVERT(` 当子 shell → `syntax error near unexpected token '('`，把 `-- im_role` 当命令 → `command not found`，结果**一条都没执行**、库纹丝未动（现象：跑完再普查结果和之前一模一样）。只读查询之前能跑通，正是因为外面包了那层 `mysql -e` 壳。

改完：`bash scripts/clear-perm-cache.sh` + `docker compose restart im-server`，页面硬刷 Ctrl+F5；再跑一次上面的 ② 普查，**四段全零行**才算清干净。

**B. 堵复发（容器级根治，已随 `scp -r Docker/*` 落到任何服务器）**：

| 改动 | 作用 |
|---|---|
| 新增 `mysql/conf.d/zz-client-utf8mb4.cnf`（`[client]/[mysql] default-character-set=utf8mb4`）+ compose `:ro` 挂进 `/etc/mysql/conf.d/` | entrypoint 那条 `mysql < 文件` 的连接字符集被**无条件钉成 utf8mb4**，与 sql 里有没有 `SET NAMES` 彻底脱钩 |
| `bootstrap.sh` ②：缺则补该 cnf 文件 | 防 `:ro` **单文件**挂载时宿主缺文件被 Docker 建成目录 → mysql 起不来 |
| `bootstrap.sh` ⑥：扫 `sql-init/*.sql` 缺 `SET NAMES` 只 warn | 容器护栏不当唯一遮羞布，提醒换仓库版脚本 |
| `guard-sql-init.sh --comment-compose` | 挪走建库脚本 + 注释 sql-init 挂载，断掉「容器重建=静默重导 43 条 DROP/CREATE」这条路 |

## 记录 4：后台「法定文本」整屏崩溃并卡死路由——`v-loading` 多触发的一次重渲染（2026-11-20）

### 症状

- 后台点左侧「法定文本」`/agreements`，整屏渲染中断，Console 满屏 `TypeError: Cannot read properties of undefined (reading 'value')`，组件栈停在 `<ElTable> <ElTabPane> <AgreementView>`；
- 崩溃后**点其它菜单只变 URL、页面内容不替换**（`router-view` 被卡死），连带报 `Cannot read properties of null (reading 'parentNode' / 'emitsOptions')`；
- 「SQL 早执行过了、数据却不显示」——其实数据接口正常返回，是渲染树在挂载阶段就断了，列表根本没机会画出来；
- 只有法定文本崩，群组 / 钱包 / 视频（同样是 `el-tabs` + `el-table` + `v-loading`）全部正常。

### 排查过程（决定性证据是真实 Error.stack，不是猜）

1. 用浏览器实测拿到完整调用栈，崩溃点是 Vue 运行时 `invokeDirectiveHook` 里的 `binding.oldValue = oldBindings[i].value`——`oldBindings[i]` 为 `undefined`，即**同一元素 patch 时 `vnode.dirs` 新旧数组长度对不齐**（新 vnode 比旧 vnode 多了一条指令绑定）；
2. 对比法定文本与群组/钱包：结构几乎一样却不崩，差异在法定文本凑齐了「**初始激活页 + 挂载即异步拉数 + 同屏两个 `el-select`**」；
3. **bisect 定位触发器**：把表格上的 `v-loading` 摘掉 → 立刻全绿（数据出 3 条、tab 与菜单切换正常、Console 零报错）；
4. ★ **一次走弯路**：以为根因是「指令挂在组件根节点」，把 `v-loading` 从 `el-table` 挪到外层 `div` → **仍然崩**。证明触发点是 `v-loading` 状态翻转多出的那次重渲染，而**不是指令挂在哪**。

### 根因链

1. `onMounted(loadVersions)` 里 `vLoading` 由 `true→false`，与「组件首次挂载」同一帧发生；`v-loading` 的这次翻转额外触发一轮 patch；
2. 这轮额外 patch 撞上同屏 `el-select` 的内部指令数组，令 `vnode.dirs` 新旧长度不齐，`invokeDirectiveHook` 读 `oldBindings[i].value` 抛 `reading 'value'`，整棵渲染树被打断；
3. 卸载这棵坏树时又级联抛 `parentNode` / `emitsOptions` of null；`AdminLayout` 用的是**裸 `<router-view/>`（无 keep-alive、无边界隔离）**，于是路由切得动 URL、换不掉内容——表现为「点别的菜单只变地址栏」。

### 修复

- `AgreementView.vue`：去掉表格区的 `v-loading`，加载反馈改由「查询」按钮的 `:loading` 转圈承担；未激活的「同意留痕」页签加 `lazy`，免提前渲染带 `type="expand"` 列的表。
- 纯前端，无后端改动。

### 部署教训（这一条才是「真实服务器」的坑）

1. **纯前端修复必须重新 `npm run build` 并把 `im-admin-ui/dist` 重新部署到服务器才生效**：dev server（`127.0.0.1:5273`）的 HMR 只影响本地开发端口，线上（80 端口）跑的是构建产物；「代码改了线上没变」九成是**忘了重建 dist**，不是改动没落盘。验证顺序：本地 `npm run build` 通过 → 覆盖 `dist` → 浏览器 Ctrl+F5。
2. **bisect 比读源码快**：面对「同结构别人不崩就它崩」，直接摘掉可疑指令复现，比逐行比对组件内部实现高效得多；但**摘掉有效 ≠ 找到真因**——挪个位置仍崩才暴露「触发点是重渲染本身而非挂载位置」。
3. **裸 `router-view` 会把单页崩溃放大成全站卡死**：一个页面渲染异常会连带让后续所有路由跳不动。给布局加错误边界（或至少意识到「切菜单不换页」的根因往往在**上一个崩掉的页面**，不在当前想跳去的页面）。
4. **Vue 3.5.x + Element Plus 2.14.x 的 `v-loading` 挂载时机敏感**：初始激活 tab 里的表格若「挂载即异步拉数」，`v-loading` 的 true→false 有概率触发指令数组不齐崩溃；规避法是别给这类表格区挂 `v-loading`，用按钮 `:loading` 或独立遮罩层承担加载反馈。
