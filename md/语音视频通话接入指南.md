## 一、这次到底落地了什么

`md/待开发功能.txt` 第 10 条要求「语音视频通话」。本期取向四条：**仅一对一**、**内网直连优先 + 公网可用（需 TURN）**、
**媒体用 WebRTC**、**录屏/录音产物本地落盘 + 上传服务端留存**。

一句话定性：**服务端只做信令中介与关系校验，从不碰媒体字节。** 音视频流由两端浏览器的
`RTCPeerConnection` 点对点直连，内网下根本不经过服务器；服务器只在通话结束后收到一条
`MsgType.CALL` 的文字记录和（桌面端）一个上传上来的录音文件。

| 能力 | 状态 | 承载 |
|---|---|---|
| 1:1 语音 / 视频通话 | **已完成** | 信令复用用户 WS 长连接；媒体走原生 WebRTC |
| 振铃 / 接听 / 拒绝 / 取消 / 挂断 / 忙线 / 离线 / 超时 | **已完成** | 服务端 Redis 会话态裁决 |
| 多端振铃、首接胜出 | **已完成** | invite 推被叫全部设备，首个 accept 胜出，其余收 `canceled(answered-elsewhere)` |
| 静音 / 关摄像头 / 屏幕共享 | **已完成** | `replaceTrack`，均在本机生效，无额外信令 |
| 通话记录（气泡显示类型 + 时长） | **已完成** | 复用 `im_message`，新增 `MsgType.CALL(6)`，**零新表** |
| 桌面端录制 + 上传留存 + 气泡回放 | **已完成（仅桌面端）** | 复用 `electron/recorder.js` 流式落盘 + `im_file`（`bizType=call_record`） |
| 群通话 / 多路 SFU 混流 | **不在本期** | 与「仅一对一」取向一致 |

## 二、链路一眼看完

```
主叫点「语音/视频通话」按钮（ChatWindow，仅单聊且 call.enabled=true 才显示）
        │
        ├─ 1. GET /api/call/config   ← 开关 + RTCConfiguration.iceServers（TURN 时按 userId 现签临时凭据）
        │        enabled=false → 前端按钮 disabled，整条 WebRTC 代码不加载
        │
        ├─ 2. 主叫生成 callId(uuid)，getUserMedia 取本地流，经 WS 发 call/invite{calleeUserId, mediaType}
        │        服务端校验：好友关系 / 非拉黑 / 主叫未自忙 / 被叫未在他途通话 → 否则回 failed(busy|not-friend|self-busy)
        │        invite 转发给被叫全部设备；被叫无活跃连接 → 回 failed(offline)
        │
        ├─ 3. 被叫某设备点接听：accept → 服务端通知主叫 accept、通知被叫其余设备 canceled(answered-elsewhere)
        │        主叫收到 accept 才 createOffer → offer 经服务端原样转给被叫设备
        │        被叫 setRemote + createAnswer → answer 回转 → 双方交换 ICE candidate（trickle）
        │        媒体 RTCPeerConnection 直连建立；connectionState=connected → 开始计时（桌面端可自动录制）
        │
        ├─ 4. 通话中：静音 / 关摄像头 / 屏幕共享 全在本机 replaceTrack，不额外发信令
        │        任一方挂断 hangup{reason}；振铃超 ring-timeout-seconds 服务端下发 timeout；超 max-duration 下发 hangup(max-duration)
        │
        └─ 5. 通话结束：仅【主叫】落一条 MsgType.CALL 记录消息（content=录音 fileId 可空，extra{duration, callMediaType, callScreenRecorded}）
                 桌面端若录了音：im:record-read 读回本地 .webm 字节 → uploadFileSmart(file,'call_record') → fileId 回填消息
                 该消息随会话推送给被叫，两端气泡各看到一条，不重复
```

## 三、信令协议（WebSocket）

信令复用**已认证的用户 WebSocket 长连接**（握手鉴权、在线判定都现成），不新建连接。
上行帧 `type=call`，下行帧 `type=call-signal`，都用 `data.action` 区分子事件。

| 方向 | action | 关键字段 | 说明 |
|---|---|---|---|
| 上行 | `invite` | `calleeUserId, mediaType` | 主叫发起；服务端校验关系 + 在线后转发给被叫全部设备 |
| 上行 | `accept` | — | 被叫接听；首台胜出，其余设备收 `canceled(answered-elsewhere)` |
| 上行 | `reject` | `reason` | 被叫拒绝 |
| 上行 | `offer` / `answer` | `sdpType, sdp` | SDP 原样在两端间转发，服务端不解内容 |
| 上行 | `ice` | `candidate` | ICE candidate trickle 转发 |
| 上行 | `cancel` | `reason` | 主叫在对方接听前取消 |
| 上行 | `hangup` | `reason` | 任一方挂断 |
| 下行 | `invite` | `callId, mediaType, fromUserId` | 被叫振铃 |
| 下行 | `accept` | — | 主叫收到 → 触发 createOffer |
| 下行 | `offer` / `answer` / `ice` | 同上 | 转发对端 SDP / candidate |
| 下行 | `reject` / `cancel` / `hangup` | `reason` | 转发终止意图 |
| 下行 | `canceled` | `reason: answered-elsewhere \| timeout` | 被叫其余设备收起来电界面 |
| 下行 | `failed` | `reason: not-friend \| self-busy \| busy \| offline \| timeout \| gone \| forbidden` | 服务端主动下发的失败回执 |

**callId**：主叫用 `crypto.randomUUID()`（非安全上下文有降级实现）生成，同一次通话所有信令共享。
服务端 Redis 记 `call:{callId} -> {caller, callee, state, mediaType, startedAt}`，另用
`call:user:{userId}` 占位作「忙线指针」。振铃超时与最大时长由「帧驱动兜底 + TTL」双保险处理。

> `fromUserId` 一律取连接身份，忽略客户端自报的 from，杜绝冒充主叫。

## 五、配置项与生效方式

`im-bootstrap/src/main/resources/application.yml` 的 `im.call`：

| key | 默认 | 环境变量 | 说明 |
|---|---|---|---|
| `enabled` | `true` | `IM_CALL_ENABLED` | 总开关。关掉后 `/api/call/config` 回 `enabled=false`，前端按钮禁用、整链路不加载 |
| `stun-urls` | 空 | `IM_CALL_STUN_URLS` | 逗号分隔（`stun:ip:3478`）。留空 = 只做局域网直连 |
| `turn.enabled` | `false` | `IM_CALL_TURN_ENABLED` | 跨公网且对称 NAT 打不通时才打开 |
| `turn.urls` | 空 | `IM_CALL_TURN_URLS` | 逗号分隔（`turn:host:3478?transport=udp`） |
| `turn.secret` | 空 | `IM_TURN_SECRET` | coturn `use-auth-secret`，须逐字一致；为空则不下发 TURN |
| `turn.ttl-seconds` | `86400` | — | 临时凭据有效期 |
| `ring-timeout-seconds` | `45` | — | 振铃超时，到点服务端下发 `timeout` |
| `max-duration-seconds` | `3600` | — | 单通话最大时长，到点下发 `hangup(max-duration)` |
| `record-max-size` | `200MB` | — | 录制产物上传上限；读回本地文件超限即 `CALL_RECORD_TOO_LARGE` |

生效：改配置后**后端需重启**；前端无需改代码，`/api/call/config` 是运行期拉取。
关掉 `enabled` 是整套能力唯一的「总闸」，无需改任何一处代码。

## 六、内网直连原理（为什么不耗服务器流量）

WebRTC 建连时 ICE 会收集多档候选地址：`host`（本机 / 局域网网卡地址）、`srflx`（STUN 探测出的公网映射）、`relay`（TURN 中继）。
两端都在同一局域网时，**host 候选直接命中彼此的 192.168.x.x 地址**，`RTCPeerConnection` 选一条局域网可达的候选对直连，媒体流从一台机器的网卡走到另一台机器的网卡：

- 不经过 Java 服务器，也不经过任何中继进程；
- 不消耗服务器出口带宽——服务器的负载只有几十个几百字节的信令 JSON 帧；
- 不配 STUN / TURN 也能用：`stun-urls` 留空即可，这正是默认值。

因此**纯内网部署（本项目的典型场景）开箱即用**，不需要任何额外服务。

## 七、公网互通：自建 STUN 与 coturn TURN

只有当两端跨 NAT / 走公网时才需要额外配置：

1. **自建 STUN**（解决一对一 NAT 的 srflx 探测）：
   `stun-urls: stun:你的公网IP:3478`，放行 UDP 3478 入站。STUN 只帮两端「看到自己对外映射的 ip:port」，
   媒体仍是点对点，一旦打洞成功就不经过 STUN 服务器。

2. **coturn TURN**（对称 NAT / 打洞失败的兜底中继）：
   对称 NAT 下 srflx 探测出的映射对每个对端都不同，打洞必失败，只能靠 TURN 中继媒体（此时**才**消耗中继带宽）。
   TURN 走 **REST 长效凭据**：

   ```ini
   # coturn /etc/turnserver.conf 关键项
   listening-port=3478
   use-auth-secret                 # 开启 REST API 临时凭据
   static-auth-secret=与 IM_TURN_SECRET 逐字一致
   realm=你的域名或公网IP           # 与凭据校验配套
   ```

   服务端 `buildIceServers(userId)` 按当前用户现签一组临时凭据下发给前端：
   - `username = 过期时间戳:userId`
   - `credential = Base64(HMAC-SHA1(static-auth-secret, username))`
   - 有效期由 `turn.ttl-seconds` 控制。

   **前端拿不到那个 HMAC 密钥**，凭据必须以服务端身份签发——这也是 `/api/call/config` 要 `@SaCheckLogin` 的原因。
   TURN 未配（`turn.enabled=false` 或 `secret` 为空）时，`/api/call/config` 只回 STUN，公网对称 NAT 可能不通，**内网不受影响**。

## 八、桌面端录制与通话留存

录制是「本端对本端可见画面的抓取」，只在 Electron 桌面端落地（Web 端无 `__IM_NATIVE__.record`，录制整体禁用，仅通话可通）。

- **合流**：`utils/callRecorder.js` 把远端 `<video>` 与本地画面绘制到一张 1280×720 canvas（远端铺满、本端右下 PIP），
  用 `AudioContext` 把上下行两路音频混进 `MediaStreamDestination`，音视频合并交给 `MediaRecorder`。
- **容器固定 WebM**：MP4 不按 timeslice 吐分片会堆内存；WebM 每秒（timeslice=1000ms）吐一片，逐片串行 append 落盘。
- **落盘**：复用 `electron/recorder.js` 的 `im:record-start/chunk/stop`（编解码无关，只 append 字节），音频轨天然进容器。产物旁有 sidecar `.json`，`type=im-call-recording`。
- **读回 + 上传**：通话结束后经新增 `im:record-read(filePath, maxBytes)` 读回字节 → `uploadFileSmart(file,'call_record',...)` → 得到 fileId 回填 `MsgType.CALL` 消息的 `content`，`extra.fileUrl` 供回放。
- **大小护栏**：读回时超过 `record-max-size` 抛 `CALL_RECORD_TOO_LARGE`；上传走分片通道。
- **目录 / 自动录制**：`stores/settings.js` 的 `callRecordDir`（缺省回退 `remoteRecordDir`）与 `callAutoRecord`（媒体连通后自动开始录）。
- **访问控制**：`FileBizType.CALL_RECORD.isPublic()=false`，沿用会话成员 `canAccess` 校验，仅同会话成员可下载回放。

气泡回放：`MessageBubble.vue` 对 `MsgType.CALL` 显示「类型图标 + 时长」；`extra.fileUrl` 存在且为视频容器时内联 `<video>` 播放，否则给一个音频播放按钮（复用 `utils/media.js` 的 `mediaUrl` 缓存）。

> **只有主叫落一条记录**：被叫不发，避免一次通话产生两条气泡；记录消息随会话推送给被叫，两端各见一条。时长以「接通后」计时为准，未接通记 0。

## 九、`file://` / HTTPS 下的媒体权限

浏览器把 `getUserMedia` / `getDisplayMedia` 视为敏感能力，只在**安全上下文**放行：

- `https://` 与 `http://localhost` / `127.0.0.1`：正常放行；
- **`file://` 打开的页面**：多数 Chromium 版本视为非安全上下文，`getUserMedia` 会被直接拒绝——
  Electron 桌面端可用自定义协议或 `app.allowRunningInsecureContent` / `--unsafetlb-treat-http-ports=true` 等策略处理，
  本项目桌面端以打包后的 Electron 环境运行，媒体能力由 Electron 主进程的权限授予；
- `getDisplayMedia`（屏幕共享）在部分环境下额外要求用户手势触发（点击「共享」按钮即满足）。

内网用 IP 直连前端页面时，若非 localhost 又没上 HTTPS，浏览器会拒绝取流——这与远程控制录屏、内容审核遇到的
约束同源，联调时优先用 `http://localhost` 或部署 HTTPS。

## 十、自测与验证

- 后端 `mvn -o -q compile` 通过；前端 `npm run build` 通过。
- **Web ↔ Web 本机 1:1 视频**：走 host candidate，验证媒体不经服务器（关抓包看无服务器中转的 RTP）。
- **桌面 ↔ Web、桌面 ↔ 桌面**：振铃 / 接听 / 拒绝 / 取消 / 挂断 / 忙线 / 离线 / 振铃超时 逐一验证。
- **多端**：被叫多设备时首接胜出，其余收到 `canceled(answered-elsewhere)`。
- **录制**：通话结束本地目录生成 `.webm` + sidecar `.json`，读回上传后气泡可回放；关闭 TURN 时内网仍能接通。
- **总开关**：`im.call.enabled=false` 时 `/api/call/config` 回 `enabled=false`，前端通话按钮禁用，整链路不加载。

## 十一、已知局限与排查

| 现象 | 原因 / 边界 |
|---|---|
| 公网对称 NAT 下打不通 | 未配 TURN；补 coturn + `turn.enabled=true` 即中继兜底 |
| Web 端没有录制按钮 | 设计如此：Web 无 `__IM_NATIVE__.record`，仅桌面端落盘 |
| `file://` 打不开摄像头 | 非安全上下文，改 `http://localhost` 或 HTTPS |
| 来电界面在另一台设备没收起 | 确认被叫该设备仍在线且收到 `canceled`；掉线设备靠状态 TTL 兜底 |
| 通话记录只有一条 / 出现两条 | 设计上只主叫落一条；若两条说明两端都发了记录消息，需检查 `role==='caller'` 判定 |
| 上传录音被拒 `CALL_RECORD_TOO_LARGE` | 超过 `record-max-size`，上调该值或缩短通话 |
| 伪造信令 | v1 已校好友 / 在线 / 忙线；SDP 内容由两端浏览器负责，服务端不解媒体，属正常路径闸门 |
| **手机点接听后浮层立刻自动关闭**（「接通后就关闭」） | 手机用 `http://局域网IP` 访问：非安全上下文下浏览器根本不给麦照，接听方取流失败只能拒接收场。改用 `https://<电脑IP>:5173`（见第十二节）；新版前端已预检并在拨号/接听时报明确提示，不再无声关闭 |
| 两端都显示已接通但无画面无声音，约 5s 后自动挂断 | ICE `failed`：两端不在同一网段 / 路由器开了 AP 隔离 / 电脑防火墙拦了浏览器 UDP。确认同 Wi-Fi 同网段、防火墙放行专用网络；新版已自动收口并提示原因（之前是卡在无声浮层里） |

> 群通话、多路 SFU 混流不在本期。伪造信令的对抗性校验（服务端深度介入 SDP）留待后续，
> 与内容审核「判定在客户端」的定性一致：这是正常路径上的闸门，不是对抗性防御。

## 十二、手机 ⇄ 电脑同一局域网互通步骤（通话实战）

目标：电脑和手机各登录一个账号，在单聊里互相拨语音/视频，媒体同局域网 P2P 直连、不经服务器。

**第 1 步：两台设备接入同一个局域网**

- 手机连家里/公司路由器的 Wi-Fi，电脑接同一台路由器的局域网口（有线或同 SSID 的 Wi-Fi 都行）。
- **不要用访客 Wi-Fi**，并确认路由器没开「AP 隔离 / 客户端隔离」——开了它两台设备互相 ping 不通，WebRTC 也必不通。
- 验证同网段：电脑 `ipconfig` 看「默认网关」，手机 Wi-Fi 详情里看网关，两边一致（如都是 `192.168.1.1`）即同一局域网；再看两台自己的 IPv4 是否同前缀（如 `192.168.1.x`）。

**第 2 步：电脑起后端 + 前端（必须 https，别用 dev:lan）**

```powershell
# 后端：IDE 里跑 ImApplication，或 mvn -pl im-bootstrap spring-boot:run（监听 8080）
# 前端（im-ui 目录）：
npm run gen:cert   # 首次/换网段后：自签证书，SAN 覆盖本机全部 IPv4
npm run dev        # 有 certs/server.pem 就自动 https，控制台 Network 行就是手机地址
```

> ⚠️ **通话场景禁用 `npm run dev:lan`**：该模式强制回落 http（为远程控制联调设计），
> 手机浏览器在非安全上下文（http + 非 localhost）不暴露 `navigator.mediaDevices`，
> 取麦/摄像头直接被拒——表现就是「点接听后通话立刻自动关闭」。
> 想恢复 https 用默认 `npm run dev` 即可；换网段后证书 SAN 对不上时控制台会直接喊出来（`npm run gen:cert` 重新生成，根 CA 复用、手机无需重装）。

**第 3 步：手机访问并信任证书**

- 手机浏览器打开 `https://<电脑IP>:5173`（以后端所在电脑 `ipconfig` 的 IPv4 为准）。
- 首次会有未受信警告：把 `im-ui/certs/ca.pem` 发到手机安装为 CA 证书（Android：设置 → 安全 → 加密与凭据 → 安装 CA 证书；iOS：描述文件安装后还要在「通用 → 关于本机 → 证书信任设置」里打开完全信任），装完地址栏不再报警，页面/fetch/wss 全部干净通过。
- 不装根证书也能点「继续访问」打开页面，但部分浏览器会对同源 wss 静默拒绝（振铃/信令收不到），**通话请优先装证书**。

**第 4 步：两个不同账号登录并互为好友**

- 通话强制好友关系（与发消息同级）：非好友/已拉黑会被服务端回 `failed(not-friend)`；同账号自己拨自己不允许（多设备在线互拨也不行，呼叫对象取自单聊会话的对端）。
- 一台设备一个账号：电脑登 A、手机登 B，先互加好友再拨。

**第 5 步：拨打与验收**

- 任一方开单聊点顶部「语音/视频」按钮 → 对端全设备振铃 → 点接听 → 计时开始即打通（内网 host candidate 直连，`stun-urls` 留空就够）。
- 打不通先看两端浮层提示：新版会对「非 HTTPS 取流被拒」和「ICE 连接失败」分别报明确原因（见第十一节排查表后两行）。
- 防火墙：Windows 首次运行 Chrome/Node 的弹窗要点「允许」并勾选专用网络；不确定时临时关闭防火墙隔离测试一轮即可定位。

### 十二点一、“一台手机 USB 共享网络给电脑，另一台手机怎么进来”

这是典型误用。`192.168.136.75` 这类地址是 **USB 网络共享（RNDIS）在“手机#1 ⇄ 电脑”之间临时新建的点对点链路地址**，
这个网段只存在于这条 USB 链上：第二台手机无论怎么连（连自己的热点、连另一个 Wi-Fi），在物理上都无法到达这个 136.x 地址。
所以「热点连不上」不是配置问题，而是两台设备根本不在同一个子网。

**正确做法：让电脑、手机#1、手机#2 三者处于同一个子网**，三选一：

- **方案 A（最推荐）——路由器**：电脑用网线或 Wi-Fi 接路由器，两台手机都连同一个路由器 Wi-Fi。
  此时电脑在路由器网段的 IP（`ipconfig` 里「无线局域网适配器 WLAN」或「以太网」那一栏，如 `192.168.1.x`）才是手机该访问的地址，
  不是 136.75。手机#1 的 USB 共享网络可以关掉，路由器自己能上网。
- **方案 B——手机#1 开 Wi-Fi 热点**（不用 USB）：电脑和手机#2 都去连手机#1 的热点。三者在热点网段（常见 `192.168.x.x`）。
  电脑 `ipconfig` 里对应那个 Wi-Fi 适配器的 IPv4 就是手机#2 要访问的地址。此方案下电脑上网也走手机#1 热点，一举两得。
- **方案 C——电脑开 Windows 移动热点**：电脑作 AP（设置 → 网络→移动热点），两台手机都连电脑热点。
  电脑在热点适配器上的 IP（常见 `192.168.137.1`）就是手机要访问的地址；上联网络可以还是手机#1 的 USB 共享。

**不管选哪个方案，网段一变必做这三件事**（否则会退回上一节 “点接听就秒关 / 远程控制一闪即断”）：

1. 重新 `cd im-ui; npm run gen:cert` 后重启 dev：新 IP 不在旧证书 SAN 里，页面能开但同源 wss 会被静默拒。
2. 手机重新拉取并安装新的 `im-ui/certs/ca.pem`（根 CA 一般会被复用，手机无需重装，只有服务器证书换了）。
3. 新网络常被 Windows 归为「公用网络」默认拦入站：控制面板 → Windows Defender 防火墙 → 启用或关闭→ 对公用网络允许；或把该网络改为专用。

> 怎么确认选对了 IP：手机和电脑先互 ping（同网段才能 ping 通），能 ping 通再用手机浏览器开 `https://<那个 IP>:5173`。
> 开发服务监听的是 `0.0.0.0`（见 `vite.config.js` 的 `server.host`），所以它本来就同时 listen 在所有网卡上，
> 用错 IP 只是“地址不属于手机所在网段”，不是“服务没开”。

### 十二点二、“没有路由器，只有手机热点能上网”——照这个做

思路：拿一台手机当“路由器”，让电脑和另一台手机都接入它的热点，三台设备同一个网段。具体（假设手机#1 有流量卡，用它开热点）：

1. **手机#1 开 Wi-Fi 热点**（设置 → 个人热点/移动热点），**不要再用 USB 共享网络**（USB 那个 136.x 地址是点对点链路，手机#2 进不来）。若热点设置里有“AP 隔离/客户端隔离”**务必关闭**——开着它两台手机间 ping 不通、WebRTC 也连不上。
2. **电脑连手机#1 的热点**（电脑右上/右下网络图标 → 选手机#1 的 WiFi 名）——电脑上网就此走热点，不再需要 USB。
3. **手机#2 也连手机#1 的同一个热点**。至此三台都在热点网段（常见 `192.168.43.x` 或 `192.168.x.x`）。
4. **电脑上 `ipconfig`**，找“无线局域网适配器 WLAN”那一栏的 IPv4（就是电脑在热点网段的地址，**不是** 136.75），两台手机都用 `https://<这个IP>:5173` 访问。
5. **重新生成证书 + 重启 dev**：`cd im-ui; npm run gen:cert; npm run dev`（新 IP 必须进证书 SAN，否则 wss 静默拒。控制台若刷“[证书过期于网段]”就是忘了这步）。
6. **防火墙放行 5173**（手机连不上最常见就是这个）：管理员 PowerShell 跑
   `New-NetFirewallRule -DisplayName "IM Vite dev server 5173" -Direction Inbound -Protocol TCP -LocalPort 5173 -Action Allow -Profile Any`
7. **两台手机都装 `im-ui/certs/ca.pem` 根证书并开完信任**，各自登录不同账号、互加好友，再拨打。

> 为什么不用 `dev:lan` 的 http 省事？因为 http 下手机浏览器拒绝授权麦/摄像头，**只能看页面、不能通话**。只想快速验证“手机能否连上”可临时用 http；一旦要通话必须按上面走 https。
> 如果电脑本身没 Wi-Fi（纯台式机无无线网卡）做不了方案 B，就把手机#2 也换成“连手机#1 热点”同段即可；仍不行只能找路由器或让电脑开热点（方案 C）。

> 跨公网（手机 4G/5G ↔ 家庭宽带电脑）不算同一局域网，host 直连必败，需按第七节配 TURN 中继兜底。
