## 一、远程控制软件（向日葵 / ToDesk / TeamViewer）的实现原理

### 1.1 前提：被控端必须"反向连接"

被控电脑几乎都在 NAT 和防火墙后面，没有公网地址，外部**无法主动连入**。
所以所有远控软件的第一块基石都一样：

- 被控端客户端开机自启，**主动向外**建立一条 TLS 长连接到厂商的中继集群；
- 靠心跳把这条连接保活，中继因此知道"这台设备在线、在哪条连接上"；
- 控制端也连中继，双方在中继上"相遇"，先由中继转发信令。

"设备始终在线"的真相不是它能被找到，而是它一直握着一条出去的线。
这也是为什么被控端断网、休眠、客户端被杀，控制端立刻显示离线——那条 outbound 连接没了。

### 1.2 连接建立三阶段

| 阶段 | 做什么 | 失败时 |
|---|---|---|
| 信令与身份 | 设备 ID + 动态验证码 / 账号绑定；中继校验双方后交换会话参数 | 拒绝会话 |
| NAT 穿透 | UDP hole punching：双方**同时**向对方的公网映射端口发包，在各自 NAT 表上打出孔；辅以 UPnP / NAT-PMP 请求路由器开端口；中继兼作 STUN 告知双方公网地址端口 | 进入下一阶段 |
| 端到端通道 | 打洞成功 → 媒体流 P2P 直连；失败 → 中继转发（TURN 角色） | 中继兜底，永远有路 |

两个值得注意的商业事实：

- **免费用户的限速限流主要发生在中继这一档**。中继带宽是厂商的真金白银，直连成功时流量不经过厂商服务器，成本几乎为零。所以"打洞成功率"直接等于厂商的带宽账单。
- **密钥协商**通常走 ECDH 交换会话密钥、设备证书或账号体系验证对方身份，媒体流端到端加密——中继原则上只看得到密文。

### 1.3 画面怎么传：抓屏 → 变化检测 → 编码 → 传输

这是远控的技术主战场，四步缺一不可：

1. **抓屏**
   Windows 用 Desktop Duplication API（DXGI，比 GDI `BitBlt` 快一个量级，能拿到 GPU 合成后的画面）；
   macOS 用 `CGDisplay` 系列；Linux 走 X11 + shm 或 PipeWire。
2. **变化检测**
   把屏幕划成网格（常见 32×32 / 64×64），逐块比对，只把**变化的块**送编码器；
   拖窗口、切屏、放视频这类全屏级变化时退化为发整帧。
   这一步决定了"静止桌面几乎不耗流量"。
3. **编码**
   H.264 / H.265 硬件编码优先（Intel QSV / NVIDIA NVENC / AMD AMF）；
   没有硬编就回落软件编码或 JPEG / 差分编码。
   码率与帧率由拥塞控制（GCC 一类）按实测带宽动态调整。
4. **传输**
   自研可靠 UDP（FEC 前向纠错 + 选择性重传）或 QUIC / WebRTC DataChannel。
   关键设计是**两类流量分开排队**：画面走"不可靠 + 关键帧自愈"（丢了就丢，等下一帧），
   键鼠指令走可靠通道——否则一个鼠标点击会被前面没发完的画面堵在队列里，手感全毁。

### 1.4 键鼠与系统级操作：两层注入

- **API 层**：`SendInput`（Windows）/ `CGEvent`（macOS）/ `XTest`（Linux）。
  简单可靠，但受会话隔离与权限限制：服务进程与用户桌面会话不同时注入失败，UAC 弹窗、锁屏界面也够不着。
- **驱动层**：安装虚拟键鼠驱动，在内核层派发输入事件。
  TeamViewer、向日葵都带自己的驱动，正是为了进 UAC  consent 界面、锁屏、以及模拟 Ctrl+Alt+Del 这类 API 层做不到的事。

同层还有剪贴板同步、文件分块传输（带校验与断点）、多显示器切换等周边能力。

### 1.5 安全与审计

- 动态验证码每会话变化、被控端弹窗二次确认、设备白名单 / 黑名单；
- 无人值守模式 = 固定密码或绑定账号，风险面更大，通常叠加 IP 白名单与允许时段；
- 会话水印、操作日志上报、企业版的录屏审计——"谁在什么时候动了我的电脑"必须可追溯。

### 1.6 共性清单

反向长连接、信令中继、打洞直连优先中继兜底、硬件编码 H.264、网格脏块差分、
画面/指令双通道分级、驱动级输入注入、端到端加密、全程审计。
**第三段会逐条对照本仓库做到了哪几条。**

### 1.7 NAT 打洞（P2P 穿透）详解

#### 为什么需要打洞

NAT 设备只放行「从里面先出去」的包回来，外部主动进来的包一律丢弃。
两台都在 NAT 后面的电脑互相看不见对方的内网地址，直接连是连不上的。
打洞的目的就是让双方的 NAT **各自以为这条连接是自己先发起的**，从而把孔留在表里。

#### 前置知识：NAT 的四种类型（决定打洞能不能成）

| 类型 | 行为 | 打洞难度 |
|---|---|---|
| 完全锥形 Full Cone | 内网 (ip:port) 映射到公网 (P:p) 后，**任何**外部主机发往 (P:p) 都能进来 | 最易 |
| 受限锥形 Address Restricted | 只有内网先发包去过的那个 **IP** 能进来 | 易 |
| 端口受限锥形 Port Restricted | 那个 IP 的**那个端口**也必须先发过包 | 中（要向精确映射端口发包） |
| 对称 NAT Symmetric | 内网→**不同目标**分配**不同**公网端口 | 极难（问 STUN 得到的端口 ≠ 对端看到的端口） |

家庭路由器默认多是端口受限或对称；企业网、运营商级 NAT（CGN）更严。
**打洞成功率不是 100%**，这就是中继永远不能省掉的原因。

#### UDP 打洞五步

1. **问地址**：A、B 各自连中继（中继此时兼作 STUN 服务器），中继告知 A「你的公网映射是 Pa:pa」、告知 B「Pb:pb」。
2. **换信令**：中继把 Pa:pa 告诉 B、把 Pb:pb 告诉 A。到此双方都知道对方的公网门牌。
3. **同时敲门**：A、B **几乎同一时刻**向对方的公网映射发包。
   - A 发往 Pb:pb 的包在 B 的 NAT 处被丢（B 还没向 A 发过包）——但这一发在 **A 自己的 NAT 表上打出了「A→Pb:pb」的孔**；
   - 同一时刻 B 发往 Pa:pa 的包，恰好穿过 A 刚打出的孔进入 A；B 的发包也在 B 的 NAT 上打了孔，让 A 的下一个包能进 B；
   - 所以第一个包的作用是「敲门 + 打孔」，从第二个包开始才真正双向通。
   「同时」是关键：谁先谁后都会变成单方被丢，要靠中继协调计时或双方各连发多包覆盖时间差。
4. **确认选路**：几轮 ping/pong 确认这条路径可用，顺带测 RTT 与丢包，然后媒体流切上来；打洞期间的试探包全部带鉴权摘要，防伪造。
5. **保活**：NAT 表项有超时（UDP 映射常见 30s～2min），双方每 10～25s 互发保活包维持孔不关；一旦连续丢保活就触发重新打洞或回落中继。

#### TCP 打洞为什么难

TCP 有连接状态机，NAT 对 SYN 的审查比 UDP 严；双方同时互连还要撞上「两个 SYN 交叉」的同时打开（simultaneous open）技巧，
任何一端的重传时序差一点就失败。所以业界媒体面普遍走 UDP，TCP 只用于信令或兜底中继。
本项目的直连阶梯里 TCP 只出现在**局域网档**（不经过 NAT，不存在打洞问题），跨网打洞档同样是 UDP。

#### 打洞失败的补救阶梯

1. **UPnP / NAT-PMP**：请求路由器主动开一条端口映射（路由器支持且开启才有效，很多环境是关的）；
2. **端口预测**：对称 NAT 的端口分配有时呈递增规律，拿多个候选端口并发试探碰运气；
3. **中继转发（TURN 角色）**：最后的兜底，代价是流量回到服务器带宽上（见 1.8）；
4. 本项目对应实现：LAN-TCP → UDP 打洞 → 中继 WS 三档，**中继常开做兜底、直连失败永不算错误**。

#### 安全注意

打洞等于把自己的公网映射端口暴露给对方，任何知道地址端口的人都能来敲门。
所以通道建立后必须立即鉴权：一次性 token + 会话密钥的 HMAC proof（本项目 DXP 的做法），
或 DTLS 证书指纹比对（WebRTC 的做法）——敲门可以，进门必须验票。

### 1.8 三种传输方式的服务器带宽成本对照（控制 1 小时）

先立模型：1080p、H.264，均值码率按场景分三档——
静止/文档 ≈ 1 Mbps、常规办公（浏览、打字、拖窗口）≈ 4 Mbps、视频/游戏画面 ≈ 10 Mbps。
1 小时 = 3600 秒，故下行媒体流量分别为 ≈ 0.45 GB / 1.8 GB / 4.5 GB。
计价取大陆云厂商公开价目的量级：**出方向流量 ≈ ¥0.8/GB**（入方向一般不计费）；
固定带宽 5 Mbps 内约 ¥23/Mbps/月、超出部分约 ¥80/Mbps/月。价格随厂商与活动浮动，看量级即可。

| 传输方式 | 服务器承担什么 | 1h 出方向流量（常规办公档） | 单会话·小时成本 | 100 并发所需服务器带宽 |
|---|---|---|---|---|
| 局域网直连 | 什么都不承担（发现与媒体全在内网） | 0 | ¥0 | 0 |
| P2P 打洞直连 | 仅信令、打洞协调、会话状态上报；媒体流不经过服务器 | 几十 KB | ≈ ¥0（< 0.001 元） | ≈ 0 |
| 中继转发 | 全部媒体流进出（TLS 终结 + 转发） | ≈ 1.8 GB | ≈ ¥1.4 | 400 Mbps 持续 |

换成另外两档码率看中继成本：静止档 ≈ 0.45 GB → ≈ ¥0.36/会话·小时；视频档 ≈ 4.5 GB → ≈ ¥3.6/会话·小时。
**同一个功能，打洞成功与否成本差三个数量级。**

再把并发算进去就能看到商业模式的来源：100 路并发中继 = 400 Mbps 持续出带宽，
按固定带宽包月量级是 5×23 + 395×80 ≈ **¥3.2 万/月**，按流量则是 100×1.8×0.8 ≈ ¥144/小时。
而打洞直连时这 100 路对服务器来说只是 100 条几乎空闲的信令长连接。
所以：

- 厂商拼命优化打洞成功率，因为每成功一路就省一路带宽钱；
- 免费用户被限速限流几乎都发生在中继档——那是唯一花厂商钱的地方；
- 「直连成功时画质更好、延迟更低」不只是体验话术，也是成本结构的直接结果。

本项目的选择与之一致：直连档承载画面 + 输入 + 文件**全部**流量，中继退居兜底；
内网场景甚至完全绕开服务器（LAN 档），服务器成本恒为信令那一档。

## 二、多人实时在线（腾讯会议 / Zoom / WebRTC 系）的实现原理

### 2.1 三种组网拓扑

| 拓扑 | 做法 | 代价 | 适用 |
|---|---|---|---|
| 全网状 P2P | N 人两两互连，N(N-1)/2 条连接 | 每人上行带宽随人数线性爆炸 | 2~4 人 |
| MCU | 服务端**解码**所有流，混音混画面后只下发一路 | 服务端算力极贵、延迟高、丢失 individual 流 | 录制、直播、超低带宽端 |
| SFU | 服务端**不解码**，只把每个人的流选择性转发给订阅者 | 客户端要收多路、要自己做订阅管理 | 主流会议（Zoom / 腾讯会议 / Meet） |

实际产品是混合体：视频走 SFU，音频混音可能在服务端，录制与直播旁路转 MCU。
SFU 能成为主流，是因为它把"算力"留在了端上、把"带宽"变成了可选择的订阅关系。

### 2.2 WebRTC 建链四步（信令本身不在标准里）

1. **信令**：SDP offer/answer 经自有信道交换（WS / HTTP / 私有协议）。腾讯会议用自己的信令服务器，标准不管这一段。
2. **ICE 候选收集**：host（本机地址）/ srflx（问 STUN 服务器得到的公网映射）/ relay（TURN 兜底地址）。
3. **连通性检查与打洞**：候选按优先级配对试探，选出可用路径；全失败走 TURN 中继。
4. **加密媒体**：DTLS 握手导出密钥 → SRTP 承载音视频；DataChannel 走 SCTP over DTLS。

### 2.3 多人场景的三个核心难题与解法

**带宽不对称**：同一路采集编出高/中/低多层（Simulcast），或分层可截断的 SVC；
SFU 按**每个订阅者**的带宽估计转发合适的层——弱网的人看小流，好网的人看大流，互不拖累。

**订阅规模**：百人会议不可能订 99 路视频。
只订"当前说话人 + 可见宫格里的几路"（active speaker + viewport 订阅），其余只收音频；
超大规模再上级联 SFU 与区域边缘节点分摊转发压力。

**弱网对抗**：GCC / BBR 做带宽估计驱动自适应码率；FEC 前向纠错 + NACK 重传双管齐下；
花屏时发 PLI / FIR 请求关键帧自愈；jitter buffer 抗抖动；音频丢包用 PLC 隐藏补偿。

### 2.4 音频是一条独立且更成熟的线

Opus 编码（20ms 一帧）、AEC 回声消除、NS 降噪、AGC 自动增益；
VAD 说话人检测驱动画面切换与"谁在说话"的高亮框。
音频的延迟预算比视频紧得多：人耳对超过 150ms 的对话间隔极度敏感，
视频卡一下能忍，音频卡一下整场会议就乱了——所以音频永远优先于视频保带宽。

### 2.5 与远程控制的本质差异

| 维度 | 多人会议 | 远程控制 |
|---|---|---|
| 流量形态 | 多对多，以下行为主（人人都在收） | 一对一，双向但不对称（画面下行大、指令上行极小） |
| 延迟预算 | 200~400ms 可接受，jitter buffer 兜着 | 超过 100~150ms 操作手感就崩 |
| 丢包态度 | FEC + 隐藏补偿，容忍丢包 | 指令必须可靠（ARQ），画面宁可丢也不堆缓冲 |
| 会话状态 | 近乎无状态的媒体流 | 强状态：谁在控制、权限档、审计留痕 |
| 安全重心 | 入室鉴权、会议号、等候室 | 被控方**明确授权** + 全程可审计 |

一句话：会议是"把很多人的流 efficiently 分发出去"，远控是"把一台电脑的现在时准确地搬到另一块屏幕上并让它听话"。

## 三、本仓库自己的实现（im-remote + im-remote-agent + im-ui）

### 3.0 定位

单机 / 局域网 / 内网穿透场景下的远程桌面，对齐向日葵的核心能力但全部自建：
识别码接入（ToDesk 式）、三档链路自动选路、H.264 硬件编码、AES-256-GCM 数据面、会话审计与录屏。

### 3.1 三个角色、两条 WebSocket

| 角色 | 模块 | 职责 |
|---|---|---|
| 中继服务端 | `im-remote` | REST `/api/remote/session/**`；WS `/ws/remote/agent`、`/ws/remote/control`；`AgentRegistry` 维护在线 Agent；`RemoteSessionService` 管状态机；`RemoteRelayService` 做中继转发 |
| 被控端 Agent | `im-remote-agent` | 纯 JDK 零依赖 fat jar，Swing UI，任意 JRE 21+ 可跑；可随 Electron 安装包捆绑 jlink 裁剪 JRE 做到免安装 |
| 控制端 | `im-ui` `Remote.vue` | 浏览器 / Electron 双形态；设备列表、识别码输入、画面渲染与输入采集 |

与业界同样的前提：被控端 Agent **主动 outbound** 连 `/ws/remote/agent` 并心跳保活，
服务端从不试图反向连入；控制端凭一次性 ticket 连 `/ws/remote/control`。

### 3.2 接入与授权链路

两种接入方式：

- **账号模式**：设备列表里选在线设备发起邀请；
- **识别码模式**：6~12 位访问码（ToDesk 式），Agent 自动生成或自定义，服务端校验唯一性后存 Redis 带 TTL。

授权链路（状态机 `inviting → active → ended`）：

```
invite → Agent 弹窗（可再次降档为 readonly）→ accept
       → 服务端生成 ticket（一次性，约 60s）+ 会话 aesKey
       → 控制端轮询 detail 拿到 ticket + aesKey
       → 连 /ws/remote/control?ticket=..&satoken=..
       → ControlHandshakeInterceptor 一次性消费 ticket
       → 双端收到 session-start（带 aesKey）→ 数据面开跑
```

一个踩过的坑值得记在这里：ticket / aesKey **不落数据库**。
早期把它们当 `@TableField(exist=false)` 挂在实体上，结果 `detail()` 一 `selectById`
重新加载出的对象这两个字段全是 null，前端误判"会话已结束"。
现在改为 `RemoteSessionService` 内的 `ConcurrentHashMap<Long, SessionSecrets>` 内存容器：
`doInvite` 放 aesKey、`handleAccept` 补 ticket、`finishSession` 移除。
代价是后端重启会使进行中的会话失效——会话本身是用户发起的短生命周期行为，这个代价被设计接受。
空闲与超时会话由 `RemoteIdleCheckTask` 回收。

### 3.3 画面：双编码 + 脏块网格 + 原子贴屏

- **抓屏与差分**：Agent 侧 `ScreenCapturer` 用 `Robot` 抓屏 + 64×64 网格脏块检测；
  推流三档 `auto / tile / full`（自适应 = 脏块为主、全屏级变化才发整帧）。
- **编码**：`H264Capturer` 走 ffmpeg `gdigrab` + `nvenc / qsv / amf` 硬件编码；
  任一条件不满足（无 ffmpeg、无硬编、控制端解不动）一律回落 JPEG，
  并用 `screen-codec` 帧把回落原因告知对端——失败是显式的，不是静默降级。
- **渲染**：控制端"离屏底图 + rAF 原子贴屏"——整帧刷底图、脏块按坐标并进底图，
  与 Agent 的网格协议一一对应，两种帧可以混着来；H.264 走 WebCodecs（`AvcDecoder`），
  而 WebCodecs 与 WebCrypto 一样只在 secure context 存在，http + IP 访问时明确报错而非静默丢帧。
- **坐标**：客户端坐标归一化到 0~10000 上行，canvas 以 CSS 缩放显示按比例换算；
  手机伪全屏旋转 90° 时由 `pointFromClient` 做反向补偿，保证落点准确。

### 3.4 链路：三档阶梯、逐消息选路

| 档 | 通道 | 说明 |
|---|---|---|
| 1 | LAN-TCP `18924` | Agent 手搓 WebSocket 服务端（`LocalInfoServer` 做局域网发现），同网段直连 |
| 2 | UDP 打洞 `18925` | `RemotePunchService` 交换双方公网映射；原始 UDP socket 只有 Electron 主进程能开 |
| 3 | 中继 WS | **常开做兜底**；直连失败永不算错误，表现退回与未开直连完全一致 |

直连一旦建立就承载画面 + 输入 + 文件**全部**流量，中继退居备份。
链路档 `auto / relay / lan` 可手动指定，auto 下逐消息实时选路。

直连两档共用同一份报文抽象 **DXP**（`Dxp.java`，纯 JDK 零依赖）：

```
 0  u8   ver = 1
 1  u8   type    1=HELLO 2=HELLO_ACK 3=DATA 4=ACK 6=PING 7=PONG 8=CLOSE
 2  u8   channel 0=控制(握手/心跳，不 ARQ) 1=画面(不可靠) 2=可靠(指令+信封+文件)
 3  u8   flags   bit0=该报文的最后一个分片
 4  u32  msgId   消息序号（分片归属）
 8  u32  seq     包序号（仅可靠通道有意义）
12  ...  body    DATA 再带 6B：[u16 fragIdx][u16 fragCnt][u8 kind][u8 保留]
```

`channel` 的三分法正是业界"画面不可靠、指令可靠"的分级思想落到报文头里。
UDP 档自实现 Go-Back-N ARQ（WINDOW=64、RTO 250ms 翻倍封顶 1000ms、画面队列 4 且不重传）；
TCP / WebSocket 档握手时协商 mtu=1MB、不分片，同一段解析代码两种传输都能跑。
单分片可用载荷 = mtu − 18，mtu 默认 1200（加 UDP/IP 头正好一个以太网帧，避开路由器分片）。
鉴权是双门禁：一次性 token + 会话 aesKey 的 HMAC proof（无密钥时退化为 SHA-256）。
配置节 `im.remote.direct`，生产由 `IM_DIRECT_ENABLED` / `IM_DIRECT_PUNCH_HOST` 控制。

### 3.5 安全与审计

- 数据面 AES-256-GCM，两端同构（前端 `remoteCodec.js` / Agent `AesCipher.java`）；
  `im.remote.aes=false` 可关闭，仅用于局域网联调（顺带绕开 WebCrypto 的 secure context 限制）。
- 权限两档 `operate / readonly`；邀请方请求的档位只是上限，Agent 弹窗可再次降档，**最终权限以被控方授权为准**。
- `RemoteAuditLog` 落库：会话起止、权限、直连 / 中继各自字节量；
  桌面端另有录屏审计（Electron 主进程写本地目录，Web 端整体关闭该能力——浏览器不应在用户不知情下落录像文件）。

### 3.6 与业界方案的逐条对照

| 能力 | 业界主流 | 本仓库 |
|---|---|---|
| 反向长连接保活 | ✓ | ✓ Agent outbound 连 `/ws/remote/agent` |
| 识别码接入 | ✓ ToDesk 式 | ✓ 6~12 位访问码 + Redis TTL |
| 打洞直连优先 | ✓ UDP 打洞 | ✓ LAN-TCP 与 UDP 打洞两档，中继兜底 |
| 硬件编码 H.264 | ✓ 内置 SDK | ✓ 外挂 ffmpeg（nvenc/qsv/amf），不满足回落 JPEG |
| 网格脏块差分 | ✓ 32×32 / 64×64 | ✓ 64×64 |
| 画面/指令分级 | ✓ 双队列 | ✓ DXP channel 0/1/2 |
| 驱动级输入注入 | ✓ 虚拟驱动 | ✗ 仅 `java.awt.Robot` API 层 |
| 端到端加密 | ✓ ECDH 协商、服务端不可见 | △ AES-GCM，但密钥由服务端生成经中继下发 |
| 多人 / SFU | 会议类产品核心 | ✗ 一对一会话，不在本项目范围 |

### 3.7 已知边界（诚实清单）

- **输入进不了 UAC 弹窗、锁屏、管理员会话**：`Robot` 是 API 层注入，受会话隔离限制；
  业界靠虚拟键鼠驱动解决，本项目没有做驱动。
- **中继档下服务端理论上可见明文**：会话密钥由服务端生成并下发两端，而非两端 ECDH 协商；
  直连档密钥只存在于本机两端，不经服务端。若要达到业界"中继不可见"的水准，需要补密钥协商。
- **后端重启丢失进行中会话**：ticket / aesKey 在内存容器里，重启即失效（设计接受，见 3.2）。
- **一对一**：没有多人会议能力；会议类需求参考第二段的 SFU 体系，是另一套工程。
