**1. OkHttp 5.x 必须显式声明**
`minio:8.6.0` 依赖 `com.squareup.okhttp3:okhttp:5.1.0`，但 OkHttp 从 5.x 起改成了 Gradle 多平台产物，
Maven 仓库里那个 jar 只有几百字节、**不含任何 class**（POM 里还标着 `do_not_remove: published-with-gradle-metadata`），
真正的 JVM 实现被拆到了 `okhttp-jvm`。纯 Maven 构建必须在父 POM 里显式补上，
否则编译期报 `cannot access okhttp3.HttpUrl`，运行期直接 `NoClassDefFoundError`。

**2. Sa-Token JWT 不能用 Mixin 模式**
`StpLogicJwtForMixin` 把 `_logout` / `_logoutByTokenValue` / `replaced` / `searchTokenValue`
四个方法重写成了无条件 `throw new ApiDisabledException()`（默认文案 `this api is disabled`）。
而 `StpUtil.kickout(userId, device)`、`StpUtil.logout(userId)`、`StpUtil.logoutByTokenValue(token)`
最终都汇聚到这几个方法上。

用 Mixin 的症状非常隐蔽：**首次登录成功**（此时该设备的 token 列表为空，`kickSameDevice` 提前 return），
但只要 Redis 里留下了同设备的旧 token，**之后每一次登录都必然报错**。
本项目改用 `StpLogicJwtForSimple`——它只重写 token 的生成方式和 `getExtra`，
不禁用任何有状态 API，多端管理、顶号、注销、踢人全部正常，同时 token 依然是可离线验签的 JWT。

配套约束：`sa-token.is-share` 必须为 `false`（Simple 模式的 `isSupportShareToken()` 返回 false），
`sa-token.is-concurrent` 保持 `true`。历史版本在同设备重复登录时由 `AuthServiceImpl#kickSameDevice`
先推 `kickout` 报文再 `StpUtil.kickout` 注销会话；**现在登录已不再顶号**（多标签页各自拿独立 token），
`kickSameDevice` 已移除，`WsSessionManager#kickOut` 只保留给封号、改密码后全端下线这类管理操作，
顺序依然是「先推报文再注销」。

**3. 依赖树里会同时出现 Jackson 2 和 Jackson 3，这是正常的，不要排除**
Spring Boot 4 的 HTTP 消息转换器用的是 Jackson 3（`tools.jackson.core:jackson-databind:3.1.5`），
但 `mvn dependency:tree` 里依然能看到 Jackson 2（`com.fasterxml.jackson.core:jackson-databind:2.21.5`），
它只从两条第三方链进来，两条都不可缺：

```
im-common ─► knife4j-openapi3-boot4-spring-boot-starter:5.6.0
              └─► io.swagger.core.v3:swagger-core-jakarta:2.2.47 ─► Jackson 2
im-file    ─► io.minio:minio:8.6.0 ──────────────────────────── ─► Jackson 2
```

`swagger-core` 是构建 OpenAPI 文档模型的库，目前没有 Jackson 3 版本；MinIO 客户端内部也用 Jackson 2
做 XML/JSON 编解码。两者与 Jackson 3 的**包名完全不同**（`com.fasterxml.jackson` vs `tools.jackson`），
在同一个 classpath 上共存不会有任何类冲突；加 `<exclusion>` 反而会把 knife4j 和文件上传直接弄坏。

需要注意的是**注解包的归属**：Jackson 3 刻意把 `jackson-annotations` 留在 2.x 命名空间
（`tools.jackson.core:jackson-databind:3.1.5` 自己就依赖 `com.fasterxml.jackson.core:jackson-annotations:2.21`）。
所以本项目里 `@JsonValue` / `@JsonInclude` / `@JsonIgnore` 一律从
`com.fasterxml.jackson.annotation` 导入是**正确写法**，而 `ObjectMapper`、自定义序列化器、
`TypeReference` 这些则必须从 `tools.jackson.*` 导入。判断标准很简单：
**注解用 `com.fasterxml`，运行时类用 `tools.jackson`；整个项目里不应该出现 `com.fasterxml.jackson.databind`。**

**4. Knife4j 官方已停更**
最后一个官方版是 4.5.0，不支持 Spring Boot 4。Boot 4 要用维护分支
`com.baizhukui:knife4j-openapi3-boot4-spring-boot-starter:5.6.0`（groupId 不是 `com.github.xiaoymin`）。

**5. 自签证书的 SAN 赶不上 DHCP 重分的 IP：wss 被静默拒绝，后端却不留一行日志**
手机远程控制「授权成功、画面闪一下就退回设备列表」，后端日志里 `invite-by-code` 与
`session/{id}` 都正常、`ticket` 也发了，但 `ControlHandshakeInterceptor` **一次都没被调用**。
根因不在代码：`im-ui/certs/server.pem` 是上周生成的，SAN 写的是旧 IP（10.216.54.50），
今天笔记本换网段后拿到了新 IP（10.97.137.180）。浏览器把证书分成两类失败：
**不受信**与**主机名不匹配**，两者都会拒绝 wss，但 https 页面都能点「继续访问」绕过——
于是 fetch/XHR 全通、WebSocket 全挂，而且请求根本没出浏览器，服务端自然一行日志都没有。
这类「REST 通、WS 不通」的分裂签名，就是 TLS，不要去翻会话状态机。

两个长期修复：`scripts/gen-cert.cjs` 默认**复用已有根 CA**（只重签服务器证书，手机里那张
`ca.pem` 继续有效，不需要重装；连根重签要显式传 `--fresh-ca`），`vite.config.js` 起 dev server
时把本机 IPv4 与证书 SAN 对一遍，对不上就在控制台打印处置指引。另外
`RemoteControlSocket.connect()` 原先 `new WebSocket()` 后就直接 resolve，“已连接中继”是假的，
失败只表现为一次 `onclose`；现在把 open/close 收敛为 promise 并带 8 秒超时，错误能进 UI 提示。

**6. `flex:1` 不等于「留多少给我」：工具栏一换行，画面区就被压成 0 高**
手机浏览器里「连上了、流量在涨、编码也回落了，就是看不到画面」，日志与链路全正常，
因为根本不是链路问题：`.remote-body` 在 ≤900px 下竖向堆叠，画面区 `.remote-stage{flex:1}`
（`flex-basis:0` 且无 `min-height`）被换行成六七排的工具栏 + 定高 320px 的侧栏一起挤到 0 高。
本期只是新增了「链路/编码」两个下拉与流量行，让工具栏在 360px 宽下开始换行，
就把一个原本「勉强能看」的布局推成了「画面完全消失」——**改 UI 时新增一行文字，
也要回头看窄屏的 flex 分配**。

修复模式：窄屏下工具栏 `flex-wrap:nowrap;overflow-x:auto`（子项 `flex-shrink:0`、tag 截断），
画面区改恒定高度 `height:56vw;min-height:220px`，侧栏 `width:100%`，整页交给 `.remote-page` 滚动；
桌面端 `.remote-stage` 也补 `min-height:200px` 兜底。另一个坑是原生全屏且浏览器真转横时，
媒体查询里的 `height:56vw` 会照样命中 `:fullscreen` 元素把画面压成一条，需用
`.remote-stage:fullscreen{height:100%;min-height:0}`（优先级更高）复位。

**7. 「进了全屏」不等于「页面转横了」：X5 里 requestFullscreen 成功、orientation.lock 被拒**
微信/QQ/UC 内置浏览器点全屏后画面仍是竖着一条：`requestFullscreen()` 会成功（于是
`fullscreenElement` 有值），但系统不把网页转横，`screen.orientation.lock('landscape')` 一律 reject。
旧代码用 `rotateFs = 伪全屏` 判断要不要补 CSS 旋转，这种情况下恰好为 false——原生全屏成功了
反而不转。

修复模式：判断条件换成实测视口 `rotateFs = 已全屏(原生或伪) && innerHeight > innerWidth`，
旋转由内联样式驱动（`width:100dvh;height:100vw;transform-origin:0 0;rotate(90deg) translateY(-100%)`，
老内核认不了 dvh 会自动退回前面那条 vh），不靠 `@media`/`matchMedia` 猜方向；
浏览器真转横后视口变宽，条件自动失效不会多转一次。配套：`requestFullscreen` 要兼容
`webkit/ms` 前缀、按 `fullscreenElement` 实测同步状态（内置浏览器不一定补发 `fullscreenchange`）、
切换后延时重判方向，并监听 `resize`/`orientationchange`；
`teardownSession` 与 `onBeforeUnmount` 都必须退出全屏，否则伪全屏那层 fixed 黑壳会永久盖住设备列表。

**8. Electron IPC 结构化克隆：Vue 响应式 Proxy 传不过 `invoke`，报「An object could not be cloned」**
桌面端点「开播」、填好标题就弹 `An object could not be cloned.`，渲染进程栈里只指到
`ipcRenderer.invoke('live:startPush', ...)`。根因：`ipcRenderer.invoke` / `ipcMain.handle` 之间走的是
HTML **结构化克隆**算法，它只认纯数据——函数、类实例、DOM 节点、以及 **Vue 的响应式 Proxy**
一律克隆失败并抛这个错。旧代码图省事，把 `displays.value.find(d => d.id === form.displayId)`
（一个 Proxy 包裹的显示器对象）整个当参数传进主进程，克隆当场炸。

修复模式（首选，最稳）：**渲染端只传纯量标识，完整对象到主进程现查**。这里改成只传 `displayId`（数字），
主进程用 `screen.getAllDisplays().find(d => d.id === displayId)` 自己还原出显示器对象——
跨进程序列化天然安全，也不会因为 Proxy 结构变化而脆断。（退而求其次才是 `toRaw()` 或
`JSON.parse(JSON.stringify(x))` 手动脱壳，但字段一多就容易漏、还会丢方法。）

**9. 「重新打包了还报旧 bug」：装进 asar 的可能是旧 bundle，验证必须下探到 asar 层**
第 8 条源码修好、`npm run build:electron` 也跑了，用户重装完包**依旧报 `An object could not be cloned`**。
反复读源码却句句正确——因为**问题根本不在源码，在打包产物**。Electron 安装包打的是 `electron/dist`
里的渲染端 bundle，而它可能是旧的：① 修完源码没跑 `build:electron` 就直接打包；② 上一轮虽重建了
`electron/dist`，打包前又被旧内容回灌（例如走了「清空 `electron/dist` + 从 `im-ui/dist` 手动拷贝」的老流程，
而 `im-ui/dist` 本身是旧的 web 产物）。

验证范式（**不能只看源码和时间戳，要解包 asar 比对代码形态**）：把
`release/win-unpacked/resources/app.asar` 读成 latin1 字符串，搜关键调用点——比如 `.startPush({`
后面的实参到底是 `displayId`（新）还是 `display:x.value.find(...)`（旧 Proxy），并确认旧哈希 bundle 名
（`Live-Dpfq4TQf.js`）已消失、新名（`Live-B-FnaU__.js`）在位。**`electron/dist` 新 ≠ `asar` 新，两者都要验。**

配套坑：重打包报 `EBUSY: resource busy or locked, unlink ...\win-unpacked\icudtl.dat` 中断——是上一次
`win-unpacked` 里的程序（`productName` 是中文时 exe 名如 `IM通讯.exe`）还在跑并锁住目录。中文名进程用
`tasklist | findstr "IM通讯"` 因编码匹配不到、`Get-Process` 的 `ProcessName` 也是乱码，最可靠的是遍历
`Get-Process` 按 `$_.Path -like '*win-unpacked*'` 过滤（Electron 通常 1 主进程 + 多个渲染/GPU 子进程，全要清），
拿到 PID 后 `taskkill /F /PID ...` 再重打。

**10. 直播推流：ffmpeg 必须 `cwd` 到切片目录；建房成功但推流起不来会留「僵尸 ENDED 房」**
两个连带的坑，都出在「开播」这条链路上。

其一，`electron/live.js` 里 `spawn(ffmpeg, args)` 若不设 `cwd`，ffmpeg 用相对名写出的 `init.mp4` / 分片 /
`m3u8` 会落到 **Electron 主进程的工作目录**而不是本次直播的临时目录，上传泵在临时目录里 `fs.watch`
半天等不到文件，表现为「开播了但观众端一直转圈」。主 spawn 与「硬编失败回落软编」的第二处 spawn
**两处都要设 `cwd: dir`**，漏一处就在回落脚本上翻车。

其二，开播是「先 REST 建房拿 `streamKey` → 再 `startPush` 起 ffmpeg」。若建房成功、`startPush` 抛错
（ffmpeg 起不来、第 8 条的 IPC 克隆失败……），旧代码在 `catch` 里调 `stopLive` 把房间关成 `ENDED`；
而 ENDED 房在「聊天模式」下会挂 1 小时且大厅可点进去——一场从没推过流的直播就这么变成僵尸房。
根治办法是新增 `POST /api/live/{roomId}/abort`：对**从未推流成功**的房间直接 `DELETE`。安全护栏的关键
在于**不能用心跳键区分**——心跳键在 `start()` 建房时就播种了，分不清「推流端真跑过」和「建完房 ffmpeg
就没起来」。因此另立独立标记 `im:live:pushed:{roomId}`，只在推流端**首次调 `heartbeat()` 接口**时用
`setIfAbsent` 种下（TTL 24h 兜底）；`abort` 时若 pushed 键存在就降级成普通 `closeRoom`，
防止主播开播成功后立刻 abort 删掉真实直播记录。

**11. `im_schema.sql` 的 DROP 块漏表：脚本自称幂等，重跑却在最后一张表处中断**
对已有数据的库重跑 `sql/im_schema.sql`（想重置成干净结构），脚本跑到最后报
`Table 'im_db.im_live_room' already exists` 中断：前面 21 张表已被 DROP + 重建，直播表却原样留着，
库变成半新半旧。

根因是两件事叠加：① 头部「按依赖倒序清理，保证脚本幂等」的 `DROP TABLE IF EXISTS` 块只列了 21 张表，
唯独漏了后加的 `im_live_room`；② 本项目所有 `CREATE TABLE` 都**不写** `IF NOT EXISTS`，全靠前置 DROP 兜底。
于是「DROP 漏一张 + CREATE 不防御」碰在一起，重跑必然在建到这张漏网的表时撞「已存在」。
新增表时只往文件尾部追加 `CREATE TABLE`、忘了回头在 DROP 块补一行，是这类脚本最典型的漂移。

修复模式：在 DROP 块**首行**补 `DROP TABLE IF EXISTS im_live_room;`（倒序清理，最后建的表最先删）。

可复用边界：任何「前置 DROP + 后置 CREATE、且不写 `IF NOT EXISTS`」的建表脚本，每加一张表都要同步在
DROP 块补一行。核对办法：数脚本里 `CREATE TABLE` 与 `DROP TABLE` 的条数是否相等（本例 22 vs 21 一眼就看出
差一张），或查 `information_schema.tables` 与脚本对账。

**12. 连麦全程无声：远端流只挂离屏静音 `<video>`、WebAudio 只连了录制节点、`AudioContext` 没 resume**
症状是「连麦接通了、画面有、就是谁都没声音」，而且**三处都不报错**，控制台干净。它们互相独立，任修一处仍然没声：

① 主播侧——嘉宾的远端流只被 `liveComposer.addSource` 挂进一个**脱离 DOM 且 `muted = true`** 的内部 `<video>`
（那元素的职责只是给 canvas 取帧），音频侧只 `gain.connect(destNode)`；而 `destNode` 是
`MediaStreamAudioDestinationNode`——「参与录制/转发的那一路」，**不通扬声器**。于是主播把自己的麦混给了观众，
却永远听不到嘉宾。② 嘉宾侧——store 里 `guestRemoteStream` 早已导出，但 `Live.vue` **没有任何元素绑它**
（grep 零命中），上麦的嘉宾既看不到也听不到主播。③ 观众侧——`start()` 里 `new AudioContext()` 后从不 `resume()`，
它可能以 `suspended` 创建（自动播放策略/非用户手势路径），此时音频图不推进、`destNode` 恒输出静音，
录出的 WebM **有 opus 轨但全程无声**——不 `await` 就等于把静音录进分片，连头几帧都补不回来。

修复模式：观众侧在建 `destNode` 前 `if (audioCtx.state === 'suspended') await audioCtx.resume()`；
主播/嘉宾的本地监听交给**界面层未静音的对端 `<video>`**（浏览器原生 AEC 吃得到 media element 的 render stream，
比在 WebAudio 上直连 `audioCtx.destination` 更不易啸叫，而且不会与 composer 那一路叠成双倍音量）；
流用 `shallowRef` 暴露给界面绑 `srcObject`（不能用 `:src`，流对象不是 URL，写属性只能得到
`"[object MediaStream]"`；`v-for` 格子与流到达时机不定，要靠指令的 `updated` 钩子重绑）。
自己的画面那一格必须静音，否则自听回声。

可复用边界：凡用 WebAudio 混音 + `canvas.captureStream()`/`MediaRecorder` 做实时合成推流的场景，
都要先分清「录制路」与「扬声路」两条边——`connect(destNode)` 成功只代表参与录制，不代表能听见。
排查顺序：先看产物里到底有没有 opus 轨（`manifest.json` 的 mimeType 或 `ffprobe` 分片），
再分侧定位「谁听不到谁」（主播/嘉宾/观众三类出口各不相同），不要一上来就调 `GainNode` 的音量参数。

**13. 群通话（mesh）三个只会在多人下才暴雷的点：共享轨被停、投递不区分设备、拿锁前的旧花名册**
一对一那一套扩到多人时，这三个坑都是「1:1 下行为完全正确、搬过来就是错」的形状：

① **共享轨的所有权**。N 个人不能各采一次 `getUserMedia`（Windows 上重复打开同一摄像头不安全，还可能把设备占死），
所以本地只采一次、作为 `localStream` 传给 `N-1` 路引擎。此时若某一路 `close()` 里照旧写法
`getTracks().forEach(t => t.stop())`，**一人挂断就全房黑屏**，而且报错都摸不到（轨是真停了，只是不该停）。
修复模式：引擎记录 `ownsStream = !options.localStream`，只有自己采集的才自己停；停轨的权力归调用方（store 在所有路都关完之后才停）。

② **投递必须精确到设备**。1:1 时把信令推给本人全部设备无所谓，多人群通话里不行：
手机点了接听、电脑也收到 `roster`，它会以为自己也在这房里，于是**对空气发起 offer**，花名册里多出一个人、格子永远转圈。
修复模式：按花名册登记的 deviceId 推（`pushToMember(state, userId, payload)`，登记的 deviceId 缺失时才退化为全部设备），
并跳过 `fromUserId` 自己。函数名与行为不一致比缺函数更危险——原名 `pushToUserAllDevicesExcept` 就是这种误导。

③ **锁后不能再用改动前的 state**。花名册是一个 Redis JSON 整体，改态要抢 SETNX 短锁；
等锁期间完全可能已经排进了别人的 join，拿锁前的旧对象去组 `roster`/`member-join` 会播出重复名单（把刚进来的人当不存在）。
修复模式：`withState(...)` 只负责改与写，**帧一律用锁后重新 `load()` 出来的 `after` 组**。

另两个定式（不实施就必现「永久连不上」）：**协商方向恒定「后进房者对每个先到者发 offer」**，
两侧同时 `createOffer` 就是 glare，表现是信令都发了、格子永远「连接中」；**成员离场用 `fromUserId` 表达**
（reject/leave/timeout 三种同形），而不是给帧加一个 `leavingUserId` 字段——后者服务端要改四处、前端要写两套解析，
而且很容易出现“某个分支忘赋值”的空值 bug（本批自查时就撞到一个根本不存在的 setter，编译期直接挂）。

可复用边界：凡从「1 条链路」扩到「N-1 条链路」的实时功能，先逐项问三个问题——
共享资源谁拥有谁释放？投递粒度是不是从「人」变成了「设备」？并发改写后的响应用的是新态还是旧态？
三个问题的答案在 1:1 下全都不是问题，所以旧代码里找不到线索。

**14. 多档 HLS 阶梯：ffmpeg 命名模板与 `-var_stream_map` 的三个硬约束，错了全都不报错**
单档改多档（`split=N` → 逐档 `scale=-2:H` → `-var_stream_map` → `-master_pl_name`）时撞的四件事，
前三个都是**静默失败**（ffmpeg 退出码 0、日志干净，症状只是「观众一直转圈」）：

① **只有 1 路时 `%v` 在 `-hls_fmp4_init_filename` 里根本不展开**，会写出一个名字就叫 `init_%v.mp4` 的文件。
上传泵按 `init_480p.mp4` 去列文件，永远列不到——init 缺失时 hls.js 不报 404，它只是解不出码、
画面永不出现在屏幕上。修法：`n > 1` 才给 `init_%v.mp4`，单档直接给字面名 `init_{档}.mp4`。
② **输出清单名必须含 `%v`**（`index_%v.m3u8`）。写成 `index.m3u8` 时各档往同一个文件上盖，
只有最后一档能看，而目录里文件数量、字节量全都正常——从磁盘上完全看不出问题。
③ **`-var_stream_map` 只认 `v:i,name:x`**：手写 `bandwidth=`/`resolution=` 想控主清单属性，
直接 `Invalid keyval` 并以 -22 退出。主清单的 `BANDWIDTH`/`RESOLUTION`/`CODECS` ffmpeg 自己算得出来，本来就更准。
④ **阶梯下 `index.m3u8` 是主清单，里面没有 `EXTINF`**：上传泵原本靠读它记账分片时长（回放清单的
`#EXTINF` 就来自这份台账），不改就时长台账全空、回放的 `BANDWIDTH` 算不出均值。读清单要读**变体清单**。

配套的正则坑：`SEG_NAME_RE` 拆 `seg_2k_0.m4s` 的档位名时用 `[a-z0-9]+`，**不要用 `\w`**——
`\w` 含下划线，会把 `seg_2k_0` 里的分隔符吃掉导致错分档位（`2k_0` 被当成一档）。

可复用边界：凡用 ffmpeg 的 `var_stream_map` 做阶梯，**所有输出文件名模板都要先单跑一次 n=1**：
多档下能展开的占位符（`%v`）在单档下不一定展开，而测试环境里“只给一个分辨率”是常见分支。

**15. 生产 Nginx 把变体清单也签了名：单档自测全过，多档上线直接黑屏**
原配置是 `location ~ \.m3u8$ { secure_link ... }`，单档时代只有一个 `index.m3u8`，完全止得住。
多档后 hls.js 先从主清单拿各档 URI，再**按相对路径**去拉 `index_2k.m3u8`，**不会把主清单 query 上的
`?expire=&sign=` 带过去**，于是每一个变体清单都缺签名 → `secure_link` 为空 → 一律 403，直播黑屏。
修法是拆两个嵌套 `location`：只对 `~ /index\.m3u8$` 做签名鉴权，其余 `~ \.m3u8$` 只设
`Cache-Control: no-store` + CORS。两个关键细节：① Nginx 的正则 `location` **按书写顺序先到先得**，
更宽的 `\.m3u8$` 必须放在后面当“其余”兜底，放前面就把主清单也抢走了；② 嵌套 `location` 里只写了任何一条 `add_header`，
父层的 CORS 头就全失效，必须每层重写（Nginx 继承规则，不是冗余）。

最阴的地方在于**自测看不出来**：局域网自测用的 `electron/live-media-server.js` 本就不校验签名，
单档/多档都能跑。可复用边界：本地用“宽松替身”跑通的防盗链/鉴权，上线前必须单独拿真 Nginx
（或给替身加一个校验开关）把**新增的那几类 URI**重新验一遍；新增文件类型/命名时，
第一时间回头看服务器配置里的正则到底覆不覆盖它。

**16. 自测脚本本身也会坑你：`os.tmpdir()` 的 8.3 短路径把 `fs.watch` 直接炸掉**
写 Node 脚本真跑 `electron/live.js` 的采集与上传泵（给 `require('electron')` 打桩后走真 IPC handler），
当场崩在 libuv：`Assertion failed: !_wcsnicmp(filename, dir, dirlen), file src\win\fs-event.c, line 72`。
不是产品代码的问题：当前 shell 下 `os.tmpdir()` 返的是 **8.3 短路径** `C:\Users\ADMINI~1\...`，
而 `fs.watch` 回调里的文件名是长路径，两者前缀对不上，libuv 直接 abort（不是抛异常，`try/catch` 也接不到）。
修法：跑测前把 `$env:TMP` / `$env:TEMP` 显式指向一个**长路径**目录（本例 `D:\...\tmp\e2e`）。

另两个测试方法上的假阴性：
① **PowerShell 手拼 ffmpeg 参数不可靠**（反引号续行、`[0:v]`、`%v`、引号嵌套都会被 shell 吃掉），
不能拿它当“命令拼错了”的裁判；要验证参数就**从产品代码里 export 那个 args 数组**，
用 `node` + `spawnSync(ffmpeg, args)` 同构跑，两边完全一致才有结论。
② `node ... | Select-String ... | Select-Object -First 25` 会提前结束管道，把 ExitCode 变成 1，
看着像脚本崩溃——先把输出全量 `Out-File` 落盘，再去筛。

可复用边界：Windows 上写“临时目录 + 文件监听 + 原生进程”的自动化测试，先把 TMP/TEMP 定成已知长路径；
看到 `fs-event.c` 的断言失败，先查路径形态，不要去改 `fs.watch` 的选项。

**17. 按单文件 mtime 做保留期清理：会偷删「正在直播」那场老分片，而且不报错**
直播回放只留 1 天，看着最省事的写法就是 `find /data/live -mtime +1 -delete`（或 Node 里逐文件比 mtime 删）。
**这个写法是错的，而且错得很隐蔽：**一个房间目录里的文件 mtime 是天然拉开的——开播一小时后，同一个目录下
既有一小时前的分片、也有前一秒刚写的分片。直播滑窗只需要最近 12 片，所以老片删了**画面照旧、不报错**；
但关播时拼的回放 VOD 清单引用**全部分片**，老片被提前抽走→ 回放开头缺一段、或 `#EXT-X-DISCONTINUITY` 连成一串。
更糟的是这类事故只在回放时才会发现，而那时清理脚本已经跑了几天，现场早没了。

正确口径：**以「房间目录」为最小判定单位，看目录里最新一个文件的 mtime**；最新的那个都超过保留期了，
说明这场已经不会再有人往里写，才能整棵删。判定顺序也要反过来算账：先看目录自身 mtime（Linux 下新建
文件会带动它）→ 新的直接放行，省一次全量遍历；旧了再 `walk` 找文件 mtime，**find 到一个 fresh 就早退**（不把
几万个分片全 stat 一遍）；注意 **Windows 下目录 mtime 不保证随子文件更新**，所以目录 mtime 只能当“快路径”，
**不能作为唯一依据**。另两个护栏：`rmSync` 在 Windows 会碰上“播放器还在读这个文件”的 EBUSY，本轮失败就下一轮再删，
不能让一个房间卡住整个清理任务；清理脚本的 `--root` 要拒绝文件系统根（误传 `C:\` 会把整盘当房间目录）。

**18. 把「没得选」写成「不展示」：观众看不到切档入口，就等于这个功能不存在**
多档清晰度上线后，观众端选择器的渲染条件是 `qualityLevels.length > 1`，于是单档流、连麦合成流、
Safari 原生 HLS 三种场次下右上角**一个控件都没有**，而主播的开播面板里那排分辨率选项一直在——
用户直接反馈成「只有开播的界面有」。**错在把两个不同的问题用了同一个条件**：
「现在有没有画面可看」才决定控件该不该存；「本场铺了几档」只决定哪几个选项能点。
后者拿来控制整个控件的显隐，用户得到的结论就是「功能没做」，而且从代码里看不出毛病。

修正后的口径：**选项个数恒定（自动/480p/720p/1080p/1440p），不可用的那几项 `disabled` + 写明原因**
（本场无 / 单档 / 不支持 / 未标注），再配一句「本场 1080p/720p/480p」的汇总。
两个陷阱都不能跳：藏掉选项让人误判「这类房间压根不能切」，而给一个点了没反应的假可选项比藏掉更伤信任。
判定条件一旦不是「能不能渲染」而是「能不能点」，就必须能被解释——原因要上界面，不能只写在源码注释里。

同一次改动还挖出两个防递归变量写混的坑：`qualityPushed`（只记下发的目标）会让新档上线后的重算直接早退，
观众锁的 1080p 永远停在自动；而 `level.height` 在解析主清单那一刻可能是 0（单档流不写 RESOLUTION，
要等首分片解出 track info 才补），只听 `MANIFEST_PARSED`/`LEVELS_UPDATED` 会永远停在「未拿到档位信息」。
一个是「目标没变不代表环境没变」，一个是「事件清单漏了一个」——两者都只在真开播的头几秒暴露，
所以这类逻辑要抽成纯函数用假数据钉住，而不是靠真人开播碰运气。

**19. 拿 `canPlayType` 当引擎选择依据：把能切档的浏览器推进了没有档位 API 的分支**
接上一条的改动上线后，浏览器里选择器能出来但四个档位全灰、标「不支持」，汇总句写着
「本浏览器不支持手动切档」——用户合理地理解成「浏览器就是不行」。实际是 `setupPlayer()` 先问
`video.canPlayType('application/vnd.apple.mpegurl')`，非空就直接 `video.src = url` 走原生并 return，
hls.js 根本没机会初始化。**错在把一个很弱的信号当成了引擎选型依据**：不少国产浏览器 /
Android WebView / 内置带 HLS demuxer 的 ffmpeg 的 Chromium 系（含 Electron）对这个类型一律回 `maybe`，
它们既没有 Apple 那套 HLS 栈、也没有档位 API，能回个非空值只说明“照例不拒绝”。

修法是按 hls.js 官方推荐调顺序：**先试 `Hls.isSupported()`（MSE，能锁 `currentLevel`），
它为假才退回原生**。额外收益是 macOS Safari 也能锁档了（它支持 MSE）；真正只剩原生的只有 iOS。
可复用边界：两个引擎二选一时，**先试能力更强的那个**，而不是先试更省事/更轻的那个；
`canPlayType` 只能回答“这个格式能不能解码”，回答不了“这个引擎有没有我需要的 API”。

还有一笔值得记住：这个错误顺序是从 `md/直播.md` §5 的早期设计草稿搬进代码的。所以改完代码必须
回头改草稿，否则下一个入坑的人照着文档来就行，比自己写错更理直气壮。

**20. 把「自测拓扑」当物理事实写进代码：打包后的桌面端跨机直播必挂，而只有直播挂**
用户报的现象形状很说明问题：“互动、发礼物、点播视频都正常，就是看不了直播也开不了播”。
这种“只坏一面”的形状直接指向了答案：**只有媒体面（:8088）的地址是写死的**。

两处 127.0.0.1 各卡一头：
- 观众端：后端 `play-base-url=/hls` 下发相对路径，Electron 下由 `env.js` 的 `livePlayBase()` 补 host，
  旧实现直接 `return 'http://127.0.0.1:8088'` —— 观众去**自己那台机器**上要流，必然拒连；
- 主播端：后端 `push-base-url=http://127.0.0.1:8088/hls` 是绝对地址，原样下发到客户端，
  主进程拉起的 ffmpeg 把分片 `PUT` 到**主播自己本机的 8088** → 推不上去 → 开不了播。
而 `/api`、`/ws`、`/api/file/download` 全部走 preload 注入的后端绝对地址，跨机本来就正常，
所以登录/礼物/点播全都好——这个不对称的现象就是归因的最大线索，比任何日志都快。

两个坑叠在一起才致命：① `127.0.0.1` 隐含的前提是「客户端与媒体服务器同机」，这在开发期
（后端、vite、媒体脚本、浏览器全在一台）永远成立，所以自测根本暴露不了；② 文档里把它写成了「IP 免配、
换网换 IP 零改动」的普适结论，没人提醒它对跨机桌面端不成立。归因时先排除了三个错的假设：
包内前端过期（拿 `@electron/asar` 扫包内而非源码，确认新 bundle 在里面）、媒体服务器坏了（8088 在
`0.0.0.0` LISTENING，旧场次的主清单能 200 拉到合法内容）、防火墙拦截（`node.exe` 的 Private/Public
入站都是 Allow）。真正的决定性证据是 `im_user.last_login_ip`：登录来自 **192.168.1.3**，
而后端与媒体服务器在 192.168.1.2——拓扑是跨机的，`127.0.0.1` 就只能是错的。

修法分两层：代码上 `livePlayBase()` 改成从注入的后端 host 推导媒体 host（`<scheme>//<backendHost>:8088`，
拿不到才回落本机），新增 `remapPushUrl()` 只把 pushUrl 的**回环** host 换成媒体面 host（已是绝对域名/局域网
地址则原样返回，不插手运维显式配置），path 与 query 逐字保留——streamKey 与签名都在 path 里；
配置上把 `IM_LIVE_PLAY_BASE_URL` / `IM_LIVE_PUSH_BASE_URL` 直接给成绝对地址也能当场救急
（调用方走 `/^https?:\/\//` 分支，根本不经过 `livePlayBase()`，不用重打包）。

可复用边界：凡是拿回环地址/同机假设写的“免配置”，都要先问一句“客户端可不可能不在这台机器上”。
诊断这类问题先拿**账号侧的登录 IP / 连接源**定拓扑，再去查代码；而“只坏一个子系统”的不对称现象，
往往就是那个子系统绕开了公共基址、自己拼了一份地址。

**21. “登录成功但没有权限”：代码升到二期、库停在一期，而前端比后端宽**
用户报的是“im-admin-ui 用 admin 登录，提示成功，却又没权限”。两件事叠在一起才长成这个症状：

1) **后端升了、库没升**。二期把四个后台控制器的 `@SaCheckPermission` 从伞权限 `system:manage`
   拆到 `system:dashboard` / `system:user:manage` / `system:report:handle` / `system:role:manage`，
   可存量库的 `im_permission` 只到 107、`im_role_permission` 只到 6007（实测 2 / 7 / 12 行）。
   Sa-Token 的权限匹配是**按字符串精确命中**，`system:manage` 里那个 `:` 不是层级通配（只有 `*` 才是），
   所以拿着伞权限反而匹配不上任何一个细化后的点 —— 升级反而把全权管理员拦在了自己门外。
2) **前端的判定比后端宽**。`im-admin-ui` 的 `hasAdminPermission()` 与 `can()` 为了兼容历史配置，
   额外放行伞权限。于是登录能过、四个菜单全部可见、点进去全部 1003。
   **界面能看到菜单不等于有权**，这句听上去像废话，但它是本次归因的唯一突破口：
   “能进门却干不了活”直接把问题定到“数据/权限行”而不是“认证坏了”。

还有一层坑会把修复本身变成罗生门：**权限码缓存在 Redis 里**（`im:auth:perm:{userId}`，TTL 30 分钟），
而 `PermissionProviderImpl` 是“命中缓存就直接返回、未命中才回源”，`AuthServiceImpl.logout` 又只做
`StpUtil.logout()` 不碰这两个键 —— 所以**直接写库后“退出再登录”不管用**（文档里原本就这么错的写着；本轮实测到了这个现象：
   脚本跑完后再登一次，`/api/auth/me` 仍旧只回旧 7 串；删掉 key 立即回 11 串、四个端点变 200），
必须 `redis-cli DEL im:auth:perm:1000 im:auth:role:1000`，或者等半小时。不删 key 就会把“补了数据”
误判成“脚本没生效”，继而去动本来没坏的代码。

可复用边界：凡是“权限/菜单靠种子数据驱动”的升级，都要把“代码版本”与“库里的种子版本”当成
两个独立变量对账（一句 `SELECT COUNT(*)` 就能分开一期/二期），先查库再查代码；
而“前端能进门、后端拦得住”这种不对称，几乎一定是两边判定口径不一致，不是认证坏了。
改 RBAC 数据后先问一句“这个结果有没有缓存、谁负责弄脏它”，不然修好了也会看起来像没修。

**22. 请求体里漏一个 `.value`：computed 本体进了 axios，报错却长成“后端没起”**
用户原话的形状就是答案：“填好信息点注册，报『无法连接服务器请确认后端启动』，**但控制台网络里
没有发送任何请求**，其他功能正常，可以正常登录”。三个现象必须同时解释得通，少一条就不能结案：

1. 网络面板一个请求都没有 ⇒ 请求**根本没出浏览器**，不是后端拒绝的；
2. 报的是“无法连接服务器”这句 ⇒ 它来自 `request.js` 里“既没有 `error.response`、也没有
   `error.request`”的兜底分支；
3. 登录正常 ⇒ 坏的只是注册**独有的那个字段**（协议表态 `agreements`）。

根因是 `im-ui/src/views/Login.vue` 的 `submitRegister` 写了 `agreements: consentItems`，
而 `consentItems` 是 `computed`。`<script setup>` 里拿到的是 `ComputedRefImpl` 本体，
`{ ...form }` 这种浅拷贝**不会**帮你拆 ref；axios 默认 `transformRequest` 对对象做 `JSON.stringify`，
于是沿 `ComputedRefImpl.dep → Dep.computed` 成环，实测抛
`TypeError: Converting circular structure to JSON`。这一步发生在 `dispatchRequest` **之前**，
所以三个现象一次全中。修法除补 `.value` 之外，更要紧的是把错误文案从两层拆成四层：
**有 `error.request` 才准说“无法连接服务器”；连 `request` 都没有就报
“请求未能发出（前端错误）：`error.message`”**——本端序列化的锅不再往后端身上推。

这一条是被上一轮**盖住**的：当时 `GET /api/agreement/list` 确实回了 500，实测是 ImApplication
重启那 68 秒空窗里 vite 代理连不上 8080（日志 `15:06:04 Commencing graceful shutdown → 15:07:12 Started`），
结论“不是代码 bug”就下早了。那个空窗是真的，但它下面还压着一个真 bug。

可复用边界：**看到“连不上服务器”先分辨请求到底有没有出去**，没出去就不要碰后端、不要重启服务；
`im-ui` 里凡是把派生数据交给接口的地方，都要盯一眼是不是漏了 `.value`。
验证这类修复又不想真写库的手法：在页面里把 `XMLHttpRequest.prototype.send` 换成**只记录不调用原方法**
（`fetch` 同样包一层），就能拿到完整请求体做证据，而字节一个都不会到服务端
（实测拿到 `{"username":"probeuser01","agreements":[{"code":"terms","version":1,"accept":true},
{"code":"privacy","version":1,"accept":true}],"deviceId":"pc"}`，MySQL 零写入），完事 `reload` 卸桩。

**23. 公示页“排版全在、就是滚不动”：全局 `body{overflow:hidden}` 会传播到视口**
`/legal/terms` 三份法定文本“不能下滑查看全部内容”。CSS 看上去没毛病——`.legal` 是
`min-height:100vh` 的 flex 列，`.legal__main` 是 `flex:1`，按网页常识就该由浏览器滚整页。
实测数字却把常识打断：内容**完整排到了 2900px**，视口只有 490px，`document.scrollHeight > clientHeight`
也成立，但遍历全 DOM 找“`scrollHeight > clientHeight` 且 `overflow-y` 是 auto/scroll”的元素——**一个都没有**。

根因在全局基线：`im-ui/src/styles/index.css` 里 `body { overflow: hidden }`（聊天窗里气泡与拖拽选择
很容易触发视口滚动，从根上禁了）。而 CSS 的规则是 **`html` 为 `visible` 时，`body` 的 `overflow`
会向上传播给视口**，于是整页视口被锁成不可滚，页面自己又没有滚动容器，就长成“内容在、动不了”。
这类坑不会只咬公示页一次：**任何新加的整屏页面（帮助页、活动页、落地页）都不能指望文档级滚动条**。

修法是让这一页自带滚动容器，且沿用仓里已有的 `.im-dialog--fit` 口径（头尾钉住、只滚中间）：
`.legal` 改 `height:100vh; height:100dvh`（两行写法是有意的，老内核退回 vh、移动端地址栏伸缩用 dvh），
`.legal__main` 加 `min-height:0; overflow-y:auto`。三个细节不写就等于没修：
① **flex 项默认 `min-height:auto`**，不压成 0 的话内容会把容器顶高而不是让它滚，`overflow-y` 形同虚设；
② **`align-items` 默认 `normal`（在 flex 里等价于 `stretch`），而滚动容器的高度是确定的**（`flex:1`），
于是卡片被钉成容器的可见高度——实测 `.legal__card` 高 **335px** 而 `scrollHeight` **2838px**，
用户看到的现象就是“白色背景没盖住下面的文本”，后半段正文直接溢到灰底上。得写 `align-items: flex-start`
让卡片高度跟着内容走（修后 2886/2886，溢出 0；错误态下 `min-height:320px` 仍撑得住）；
③ `@media print` 里必须把 `height` 放开、`overflow` 改回 `visible`，否则“保存留档/打印”会把整份协议
裁在第一页里——这一页的页脚明写着欢迎打印，不顺手处理就是自己挖坑。
另外三份文本共用同一个组件实例（只换 `:code`），容器不会自己归零，所以切文本时要显式 `scrollTop = 0`，
否则从“用户协议”读到一半点“隐私政策”，会直接落在对方中段。

★ 值得单独记一笔的是：② 这个钉高度其实是**一开始就在的**，只是被“整页滚不动”盖住了——
滚不了也就看不到溢出，修完滚动才把它暴出来。所以“修 A 后冒出来 B”不等于“修 A 修坏了”：
锁死的布局会掩盖同一块上的其它错误，改完一处要把这个面重新看一遍，而不是直接结案。

可复用边界：`body{overflow:hidden}` 的项目里，“页面看起来内容齐全却滚不动”几乎必然是**缺滚动容器**，
不要先去查数据有没有截断；诊断动作是遍历一遍 DOM 找可滚元素，空列表就直接定性。

**24. dev 期后端没起时，vite 代理回的是“空 body 的裸 500”，什么信息都不带**
`GET https://localhost:5173/api/agreement/list 500 (Internal Server Error)`——浏览器只能看到状态码，
前端只能拼出“服务异常（HTTP 500）”，读不出“后端没起”还是“这个接口真坏了”。

翻 `node_modules/vite/dist/node/chunks/config.js`（im-ui 实装 7.3.6，另核 im-admin-ui 实装 7.3.7，
**不要假设两边一致**）确认：target 连不上时 vite 只在自己终端打一行 `http proxy error`，然后
`res.writeHead(500, { 'Content-Type': 'text/plain' }).end()` —— **body 是空的**。而且
`opts.configure(proxy, opts)` 的执行（L21997）**早于**它自己注册 `proxy.on('error')`（L21998），
所以在 `configure` 里先把响应写完就能接管（vite 因 `headersSent` 为真不再覆盖，它的日志仍然保留）。

改法是 `devProxy(target, hint)`：上游连不上时回 **502 + 与后端 `Result` 同形状的 JSON**，
把 target、errno 和“该去检查哪个服务”写进 message（502 才是 Bad Gateway 的真实语义，不假装 200；
做成 `Result` 形状是为了让前端既有的错误信封判据直接复用）。`hint` 必须按前缀给：`/api` 指
ImApplication:8080，`/hls` 指 `live-media-server.js`:8088——都用同一句话的话，直播服务挂了会把人
支去重启后端。顺手刷掉一条看着很像成因的假设：`target: 'http://localhost:8080'` 会不会被 Node
解成 `::1` 而 Java 只听 IPv4？本机 `node -e` 实测 `dns.resolve('localhost')` = `['127.0.0.1']`，
`host:'localhost'` 与 `host:'127.0.0.1'` 各打一次都 200 ⇒ **不存在 IPv6/IPv4 错配，别往这个方向耗时间**。

可复用边界：dev 期“整个 `/api` 都 500 / 都连不上”九成不是代码问题，而是那个时刻没人监听 8080。
30 秒三步：① 看后端日志 `Started ImApplication` / `Graceful shutdown` 的时间 vs 报错时间
（日志目录由键 `im.log.home` 定，默认 `D:/rizi1/IM`，**不是仓内 `im-bootstrap/logs`**，那里面可能是几周的陈迹）；
② `curl -s http://localhost:8080/接口` 直连；③ `curl -k https://localhost:5173/接口` 经代理再打一次。
两条都 200 就是那个空窗过去了，不用改代码。注意 PowerShell 的 `Invoke-WebRequest` 走自签 https 会报
“基础连接已经关闭”（客户端 TLS 问题，不是服务端坏了），要证 HTTP 状态就用 `curl.exe -k`。
